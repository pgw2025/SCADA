# SCADA 系统全项目 Code Review 报告

> 审查日期：2026-09-23
> 审查范围：`Server/`（ASP.NET Core 8 + EF Core + MySQL，约 540 个 .cs 文件）+ `Client/`（Vue 3 + Vite + TS + Tailwind，84 个 .vue 文件）
> 审查方式：只读静态分析（未修改任何代码），关键结论已通过 grep/交叉引用二次核实。
> 审查维度：认证与安全 / 数据访问与并发 / 运行时与采集链路 / 前端代码质量

---

## 一、结论总览

系统整体架构分层清晰（Domain / Application / Infrastructure / Runtime / WebApi），
运行时后台服务设计成熟（普遍使用 CancellationToken、有界 Channel 背压、WAL 落盘、挂死看门狗、停止时排空）。
但存在 **7 个严重问题**、**约 14 个中等问题**，需按优先级处置。

| 严重度 | 数量 | 核心主题 |
|--------|------|----------|
| 🔴 严重 | 7 | 明文密码入库、默认 JWT 密钥、WAL 重放死代码（数据丢失）、Timer 泄漏、无并发控制、Jint 无内存配额、React 依赖残留 |
| 🟠 中等 | 14 | 无 HTTPS/防爆破、开放网关匿名、sync-over-async、Repository 逐条提交、大表无分页、跨线程竞态、快照写入放大、前端 any/localStorage/大列表等 |
| 🟡 轻微 | 若干 | 死代码事务方法、缓存抖动、index key、错误提取器重复等 |

## 二、严重问题（🔴 建议优先修复）

### S1. 明文数据库密码 + 开发 JWT 密钥已入库且被 git 跟踪

- **文件**：`Server/ScadaServer.WebApi/appsettings.json:7,13`
- **证据**：`"Password": "Pgw15221236646"`（MySQL root 口令）、`"Key": "dev-only-jwt-signing-key-do-not-use-in-production-0123456789"`（JWT 签名密钥）。
  两值均已 `git ls-files` 确认入库；`.gitignore` 只忽略了 `appsettings.dboverride.json` 和 `appsettings.Development.json`，**未忽略 `appsettings.json`**。
- **风险**：任何拿到仓库/镜像/历史的人可直接获得 MySQL `root` 口令读取/篡改全部数据；若生产未覆盖 `Jwt__Key`，攻击者可用默认密钥伪造任意用户（含 Admin）的 JWT，`RequireAdmin` 授权形同虚设。
- **建议**：
  1. 立即轮换数据库口令；
  2. 凭证改为环境变量/密钥保管库（代码已支持 `SystemDbConfig__Password` / `Jwt__Key` 覆盖）；
  3. 从仓库删除明文，并用 `git filter-repo`/BFG 清理历史；
  4. 启动期校验 JWT 密钥非默认值 + 长度 ≥32，否则快速失败。

### S2. 历史数据 WAL 落盘重放是死代码 —— 数据可能被静默丢弃

- **文件**：`Server/ScadaServer.WebApi/HostedServices/HistoryRecorder.cs:809`
- **证据**：`ReplaySpillDirectoryAsync` 方法仅在定义处（809 行）和注释（249、658 行）出现，**全项目无任何调用点**（grep 确认）。
- **风险**：设计声称 Influx+MySQL 双后端失败、内存补偿队列溢出时批次落盘（WAL），进程重启后由该方法重放补写。但该方法从未接入启动流程 → 落盘文件永久堆积，直到 `EnforceSpillBudget` 触顶删除最旧文件时**静默丢失数据**；停止阶段 `DrainRetryBufferToSpill()` 写盘的数据同样永不恢复。
- **建议**：在 `HistoryRecorder.StartAsync` 等 DB 就绪后、启动 `ProcessAsync` 前，调用一次 `ReplaySpillDirectoryAsync`（插入幂等，重复调用安全）。

### S3. AlarmRuleEngine 的 Timer 永不释放，类未实现 IDisposable

- **文件**：`Server/ScadaServer.Runtime/Alarms/AlarmRuleEngine.cs:23,49`
- **证据**：类 `public class AlarmRuleEngine : IAlarmRuleEngine`（未实现 `IDisposable`/`IAsyncDisposable`），构造函数第 49 行 `_refreshTimer = new Timer(...)`，全类无 `Dispose`。
- **风险**：Timer 每 30s 触发，在宿主关闭、DI 根容器释放后仍可能触发 → `CreateScope()` 抛 `ObjectDisposedException`（虽被 catch 成 Warning，但造成关闭期日志刷屏）；Timer 本身是资源泄漏，回调内 `.GetAwaiter().GetResult()` 还阻塞线程池 Timer 线程。
- **建议**：实现 `IDisposable` 并在 `Dispose` 中 `_refreshTimer?.Dispose()`；回调改为 `_ => _ = ReloadSilentAsync()` 去同步阻塞。

### S4. 全局无乐观并发控制（无并发令牌），存在更新丢失

- **文件**：`Server/ScadaServer.Infrastructure/Persistence/ScadaDbContext.cs`（612 行 OnModelCreating 无任何并发令牌）
- **证据**：全仓无 `IsRowVersion()`/`ConcurrencyCheck()`/`[Timestamp]`；无 `DbUpdateConcurrencyException` 处理。EF 默认 last-writer-wins。
- **风险**：设备状态、变量实时值、报警确认、数据模型绑定等高频并发写，后到者静默覆盖前者。
- **建议**：给 `Device`/`DeviceDataModel`/`AlarmRecord`/`DataPointMapping` 等核心实体加 RowVersion 行版本列 + 乐观并发；`RepositoryBase.UpdateAsync` 捕获 `DbUpdateConcurrencyException` 做重试或报冲突。

### S5. `GetByIdForUpdateAsync` 名不副实（无真实行锁）

- **文件**：`Server/ScadaServer.Infrastructure/Repositories/DeviceRepository.cs:43-47` 等
- **证据**：命名为 "ForUpdate" 的方法实现只是普通 `FirstOrDefaultAsync`（快照读），全仓无 `SELECT ... FOR UPDATE`。
- **风险**：给人"已加锁"的错误安全感，read-modify-write 非原子。
- **建议**：改用乐观并发（推荐，见 S4）或原生 `FromSqlRaw("... FOR UPDATE")`（需置于事务内）；至少重命名为 `GetByIdTrackedAsync` 消除误导。

### S6. Jint 系统脚本无内存/语句配额，存在 OOM 风险

- **文件**：`Server/ScadaServer.Runtime/Scripting/ScriptSandbox.cs:47-52`
- **证据**：仅设 `LimitRecursion(100)` + `TimeoutInterval`（协作式超时），**未设 `MaxStatements`**；对比 `ScaleExpression.cs:105` 换算求值器设了 `MaxStatements(64)`，系统脚本路径却没设。
- **风险**：`TimeoutInterval` 拦得住 CPU 死循环，但拦不住无界内存分配（如 `let a=[]; while(true){a.push(a)}`），一次巨型分配可在超时检查前撑爆进程内存 → 整个 SCADA 服务 OOM。
- **建议**：给 `ScriptSandbox` 加 `MaxStatements(n)` 硬上限；对不可信脚本考虑进程级隔离。

### S7. 前端 React 依赖全部为遗留未清理

- **文件**：`Client/package.json:2,17,21-25`
- **证据**：`react`/`react-dom`/`@vitejs/plugin-react`/`lucide-react`/`motion`/`@google/genai` 六个包在 `src` 中零引用（grep 确认），`name` 仍为 `react-example`，`tsconfig.json` 的 `jsx: react-jsx` 也是模板残留。实际是纯 Vue 3 应用。
- **风险**：构建体积膨胀、依赖树混乱、扩大供应链攻击面（多一份依赖多一份 CVE）。
- **建议**：删除上述无用依赖（`express`/`dotenv`/`tsx` 等 Node 辅助服务需保留）；改 `name`；移除 `jsx: react-jsx`；重新 `npm install` 并验证构建。

## 三、中等问题（🟠）

### M1. 默认管理员弱口令 `123456`（认证安全）
- `DatabaseInitializer.cs:161` 首次启动写入 `admin/123456`，仅 LogWarning 提示，无强制改密阻断。→ 生成随机强口令并仅输出一次，或首次登录强制改密。

### M2. HTTPS 重定向被注释，无 HSTS
- `WebApplicationExtensions.cs:31` `// app.UseHttpsRedirection();`。登录口令与 JWT 明文传输可被窃听。→ 启用 HTTPS + HSTS，或配置反向代理 TLS 终止 + ForwardedHeaders。

### M3. 登录无防爆破/限流
- `AuthController.cs:38-59` 无限流、锁定、验证码。→ 对 `/api/Auth/login` 加限流中间件 + 失败锁定。

### M4. `/open` 开放 API 网关完全匿名
- `WebApplicationExtensions.cs:35` 在认证中间件之前挂载，`ExposedApiMiddleware` 命中即匿名返回实时设备变量值/拓扑。→ 确认业务必要性；加 API Key/IP 限制。

### M5. JWT 无吊销/刷新，有效期 8 小时
- `SystemUserAppService.cs:72` `Expires = 8h`；`Logout` 仅审计不失效。→ 缩短有效期 + 刷新令牌 + 登出/改密作废短名单。

### M6. Repository 逐条 SaveChanges，破坏 UoW 边界
- `RepositoryBase.cs:75-128` 每个 Insert/Update/Delete 各自提交。→ 多步操作部分提交无法回滚；且与 `EnableRetryOnFailure` 重试重放叠加时，对无唯一约束的表（SystemLog/AlarmRecord）可能产生重复行。→ 改为仓储只改跟踪图、UoW 统一提交；历史写入保持幂等（`InsertIdempotentAsync` 已正确）。

### M7. sync-over-async（阻塞异步）热路径
- 高频点：`ScriptRuntimeAccess.cs:145`（脚本写变量桥）、`VariableValueProcessor.cs:209`（实时值处理）用 `.WaitAsync().GetAwaiter().GetResult()`；另有 `ExposedApiRegistry.cs:82`、`ScheduledTaskAppService.cs:165/180`、`ScriptEngineHost.cs:523`、`AlarmRuleEngine.cs:49`。→ 改 `await`；Timer 场景改 `PeriodicTimer`。

### M8. 大表无分页
- `RepositoryBase.GetListAsync()` 无 `Take`；`SystemLogAppService.cs:54`、`AlarmRecordAppService.cs:57`、`DeviceAppService.cs:90/441`（多重 Include）全量加载。→ 大表强制分页。

### M9. 跨线程共享字段无 volatile / 双写者竞态（运行时）
- `DeviceRuntime` 的 `ConnectionState`/`SuccessCount`/`AverageResponseTime` 被 DeviceWorker、ConnectionSession、RuntimeManager 快照读取多线程访问，无锁/volatile。`ConnectionState` setter 有副作用（触发事件），存在真实竞态窗口。→ 加 volatile/Interlocked；收敛 ConnectionState 写者。

### M10. RealtimeSnapshotService 每 1s 全量重写快照（写入放大）
- 无论是否变化，每 1s 把整个快照集合 `INSERT ... ON DUPLICATE KEY UPDATE`。→ 维护脏集合，只刷变更项。

### M11. 前端硬编码内网地址与业务邮箱
- `Client/src/store/configStore.ts:18-22` 写死 `10.120.44.15:1883`、`opc.tcp://10.120.44.12:4840`、`ops_alerts@iota-factory.com`。→ 移出源码，改环境变量/后端下发。

### M12. 前端 tsconfig 未开 strict，约 200 处 any
- 类型安全保障弱。→ 开启 `strict` + `noImplicitAny`，为 API DTO/SignalR 载荷补最小接口。

### M13. JWT 存 localStorage（XSS 可窃取）
- `Client/src/api/http.ts:7`。→ 改 httpOnly Cookie 或严格 CSP 约束。

### M14. 前端大列表无虚拟滚动/分页
- `DeviceManagementView.vue:775/888`、`DataPointMappingView.vue`、`AlarmManagementView.vue`、`DataModelView.vue`、`CanvasPanel.vue` 整表渲染。工业点位可达数千，DOM 卡顿。→ 引入虚拟滚动或分页。

## 四、轻微问题（🟡）

- **L1**：`EfUnitOfWork` 的 `BeginTran/CommitTranAsync/RollbackTranAsync`（`EfUnitOfWork.cs:25-47`）未包执行策略，且全仓无调用点（死代码/潜伏缺陷）。
- **L2**：`ScaleExpression` 静态缓存 `Cache.Clear()` 无锁无 LRU（`ScaleExpression.cs:49,124`），并发下缓存抖动。
- **L3**：`DeviceScheduler.SchedulerLoopAsync` 每 50ms 全量 `.ToList()`（`DeviceScheduler.cs:110`），轻微 GC 压力。
- **L4**：`RuntimeManager.WriteVariableAsync` check-then-act 竞态（`RuntimeManager.cs:1086/1134`），已被 catch 兜底，建议提前判空。
- **L5**：`MqttReconnectHostedService` 首轮延迟 15s 且 `ReconnectAsync` 未传 token（`:29-30`）。
- **L6**：前端两套错误提取器并存（`http.ts:53` vs `errorHandler.ts:14`），逻辑重复。
- **L7**：个别列表用 index 作 `:key`（实时日志/历史查询等），追加删除场景可能错位。
- **L8**：前端 `SystemLogsView`/`AlarmManagementView` 等 `:key` 用 index；`sw.ts` 的 fetch 不带 Authorization（需确认后端续订端点确属公开设计）。

## 五、正面结论（本次审查确认无误的部分）

1. **无 SQL 注入**：所有原生 SQL 均参数化/白名单（`VariableHistoryRepository`、`AlarmRecordRepository`、清理任务等）。
2. **DbContext 生命周期合规**：注册为 Scoped，单例服务均经 `IServiceScopeFactory` 在作用域内解析，无单例捕获 Scoped DbContext。
3. **密码哈希正确**：用 ASP.NET Core `PasswordHasher`（PBKDF2），非明文/弱哈希。
4. **JWT 校验完整**：开启 ValidateIssuer/Audience/Lifetime/IssuerSigningKey 全套；全局 FallbackPolicy 要求认证，无漏加 `[Authorize]` 的敏感接口。
5. **运行时背压设计成熟**：HistoryRecorder/AlarmRecorder 用有界 Channel + DropWrite、停止排空带超时、WAL 落盘与预算清理；ScriptEngineHost 有线程隔离、挂死看门狗、写桥超时；设备驱动释放下沉统一兜底。
6. **前端 axios 封装质量高**：单一实例、拦截器注入 Bearer、统一 401 处理、paramsSerializer 处理数组绑定；事件监听/定时器基本都在 onUnmounted 清理，store 订阅用引用计数防泄漏。
7. **大写入正确分批**：`VariableHistoryRepository.DeleteBeforeAsync`、`ScriptExecutionRecordRepository.DeleteOlderThanAsync` 均按 LIMIT/Take 分批删除。
