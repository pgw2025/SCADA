## 一、TL;DR

1. **原方案准确性**：对现状的描述**基本准确**。R1–R4/N1–N6/C1 的判定依据（字段缺口、行号引用、机制描述）经逐项对照代码核实，全部成立（行号存在 ±1\~2 行的漂移，不影响结论）。
2. **但原方案存在 3 个会导致功能失效的设计缺陷**（详见第三节 P1–P3）：

   - P1：`ReconnectCount` 挂在 `DeviceRuntime` 上，而重连流程会**整体重建 runtime 对象**，计数永远无法跨重连累计；

   - P2：`HasAlarm` 由 `DeviceWorker` 打点，而 Worker 每次派发都是**新实例**、runtime 重建后报警聚合归零，与 `AlarmRecords` 表中未恢复报警**不一致**；

   - P3：`RunState` 未设计持久化，服务重启后管理员置位的「维护中/停机」状态丢失，存在**误操作安全风险**。
3. **重构范围与原方案一致**（改「建模缺口」，不改「工程实现」），但在实施细节上做了 8 处修正/增强（P1–P10），并将批次顺序调整为 **R2 先行 → R1 → R3 → 清理回归**（风险从低到高）。
4. **阶段划分**：0 准备基线 → 1 通信状态补全（R2）→ 2 设备运行状态建模（R1）→ 3 聚合快照 API（R3）→ 4 清理收尾与回归验收。共 5 个阶段、18 个步骤。

## 三、原方案问题分析（P1–P10）

### P1（严重）：ReconnectCount 挂 DeviceRuntime 会跨重连丢失 —— 计数永远失效

**原方案设计**（R2 打点位置）：

> 「重连计数：RuntimeManager.ReconnectDeviceAsync（L261–282）通过重入门闸后 `runtime.ReconnectCount++`；BuildAndRegisterDeviceAsync 连接失败路径（L439–450）也应 +1」

**缺陷分析**：`ReconnectDeviceAsync` 的实际流程（RuntimeManager.cs:261–282）：

```
TryRemove(deviceId, out runtime)   ← 旧 runtime 从字典移除
  → StopWorkerAndDisposeDriverAsync(runtime)   ← 旧 runtime 即将销毁
  → RegisterDeviceAsync(deviceId)
      → BuildAndRegisterDeviceAsync(device)   ← new Devices.DeviceRuntime(device) 全新对象
```

- 在 `ReconnectDeviceAsync` 里对 `runtime.ReconnectCount++`：**写的是即将销毁的旧对象**，值随对象一起丢弃；

- 即使在 `BuildAndRegisterDeviceAsync` 占位路径（L439–450）+1：占位对象在下一次重连时同样被销毁重建；

- 重连成功后正式 runtime 的计数从 0 开始。

**结论**：该字段若按原方案实现，「重连次数」语义退化为「当前对象生命周期内的重连尝试」——而当前对象生命周期恰好终止于每次重连，**计数在用户可见层面永远是 0 或 1**。

**修正**（并入阶段 1）：ReconnectCount 的存储必须脱离 DeviceRuntime 实例，由 **RuntimeManager 维护进程级字典** `ConcurrentDictionary<int, DeviceConnectionStats>`（与既有 `_lastPushedStatus` 同模式），在 `ReconnectDeviceAsync` 门闸通过（TryRemove 成功）后递增。语义明确为「**进程启动以来自动重连发起次数**」。详见 `02-阶段1-通信状态补全.md` 步骤 1.3。

***

### P2（严重）：HasAlarm 在 Worker/runtime 重建后与 DB 报警记录不一致 —— 幽灵报警/漏报

**原方案设计**（R1 设计要点 3）：HasAlarm 由 DeviceWorker 在 FireEvent / CheckMinMaxLimit 出口调用 `SetAlarmState(bool)`。

**缺陷分析**：两层丢失：

1. **Worker 重建**：`DeviceScheduler.RunWorkerAsync`（L242–274）每次派发 `new DeviceWorker(...)`，报警去重状态机 `_ruleStates`/`_alarmStates` 是实例字段。Worker 退出（断线判定/注销/重载）→ 新 Worker 从零开始。若设备只有一个报警处于 Active，Worker 重建后该报警**不会重触发**（值仍在越界，去重状态却已清零——实际会因状态清零而重触发一次 Triggered，依赖 F6 既有行为），但**恢复事件取决于值变化**，中间窗口 HasAlarm 语义不稳定。
2. **Runtime 重建**：`ReconnectDeviceAsync` / `RegisterDeviceAsync`（重载）都会 `new DeviceRuntime`。挂在 runtime 上的 HasAlarm/计数**归零**，而 `AlarmRecords` 表中该设备可能存在 `RecoveredAt IS NULL` 的活跃报警（例如报警发生在上一连接周期、设备断线期间值未知无法判定恢复）。前端看 HasAlarm=false，报警中心却有未恢复记录——**状态不一致**。

**修正**（并入阶段 2）：DeviceRuntime 维护 `ActiveAlarmCount`（int 计数）而非裸 bool；`BuildAndRegisterDeviceAsync` 注册时**从 AlarmRecords 批量初始化**（启动时一次 `GROUP BY`，单台重载时按 DeviceId 查询）；Worker 的 FireEvent 单点打点 `+1/-1`（clamp ≥ 0）。HasAlarm = ActiveAlarmCount > 0。详见 `03-阶段2-设备运行状态建模.md` 步骤 2.3/2.4。

***

### P3（重要）：RunState 未设计持久化 —— 重启丢失维护状态，有安全风险

**原方案**只提了「RunState 由管理员显式置位（D2-A/C）」与「不推送、快照轮询」，未讨论**服务重启后的恢复**。

**风险场景**：管理员将设备置为 `Maintenance`（检修中）→ 晚上服务重启/发布 → RunState 回到 `Unknown` → 夜班操作员看到设备无运行状态标记，对检修中的设备执行启停/写入 → **人员/设备安全风险**。

**修正**（并入阶段 2）：RunState 持久化到 `Devices` 表（新增 `RunState` + `RunStateChangedAt` 两列，参照 `LastKnownStatus` 先例 F2）：

- 置位端点写库 + 同步更新内存；

- `BuildAndRegisterDeviceAsync` 构建运行时从实体回读初始 RunState（启动/重载天然恢复）；

- 不引入新的事件订阅者/推送通道，保持最小改动。

详见 `03-阶段2-设备运行状态建模.md` 步骤 2.5。

***

### P4（中）：RunState.Fault 与 DeviceStatus.Fault 命名冲突未讨论

`DeviceStatus.Fault` = 通信故障（ConnectionState=Error 映射而来）；构想中的 `DeviceRunState.Fault` = 机器自身故障。两者语义完全不同但同名。快照 DTO 同时输出双状态时，前端/接口文档必须显式区分（`connectionState` vs `runState` 字段名 + 注释），否则消费方极易混淆。修正：在 DTO 与枚举 XML 注释中写明语义边界（见阶段 3 DTO 设计），不改名。

### P5（中）：遗漏 DeviceRuntimes 公开字典的既有直接消费方

`TelemetryDataController`（遥测读值）与 `ExposedApiMiddleware`（对外暴露接口）绕过 `IRuntimeStatusProvider` 直接读 `RuntimeManager.DeviceRuntimes`。新增快照接口后存在**三套并行的运行时读取路径**。修正：阶段 3 将快照接口设计为唯一的聚合读取入口，并登记「评估两处既有消费方迁移」为可选任务（不强求本轮迁移，避免扩大回归面——它们读的是变量值不是状态，语义不同）。

### P6（低）：快照读取的线程安全设计决策未写明

快照从 DeviceRuntime 读多个字段（string/int/double/DateTime?）无锁读取：.NET 保证单字段读写原子性，但**字段间一致性不保证**（可能读到 LastError 新值 + ConsecutiveFailureCount 旧值）。对可观测快照可接受，但必须在代码注释与本方案中写明「容忍字段间微小不一致」的设计决策，防止后续维护者当 bug 修复而引入锁（锁住采集路径是明确要避免的）。

### P7（低）：ConfigUpdating 死枚举值未提及

`DeviceStatus.ConfigUpdating` 后端无产生路径（F3）。保留（前端已兼容映射），在架构文档中注明「预留：配置热更新期间可置位」，不在本轮启用。

### P8（低）：R1 打点位置可简化

原方案建议在 `FireEvent`（L735）**与** `CheckMinMaxLimit`（L689）两处打点。核实发现 MinMax 兜底报警最终也统一走 `FireEvent`（L697/L703/L710），**只需在 FireEvent 单点打点**即可覆盖规则报警 + 兜底报警两条路径，减少一处改动点与遗漏面。

### P9（低）：D2-B（约定变量自动推导）成本估计偏高

原方案认为选项 B「需动 DataPoint/DataPointMapping 定义 → 成本上升」。实际上存在更轻路径：新增独立映射表（如 `DeviceRunStateMappings`：DeviceId / RunState / VariableKey / MatchValue / IsDefault），由 DeviceWorker 在采集成功后评估（位置紧邻 TryCheckAlarm），**完全不动模板体系**。成本可控。本轮仍按「先 A 后 C」节奏，但 B 的立项门槛比原方案描述的低，修正其评估结论。

### P10（低）：实施批次顺序建议调整

原方案 B1 将 R1+R2 混为一批。R2（补字段+打点）风险显著低于 R1（新语义+持久化+DB 初始化），拆开并让 R2 先行可先用最小改动验证「打点不伤采集循环」这一共同风险面。新阶段划分见下节。

## 四、重构方案总览

### 4.1 目标与原则（继承原方案，增补两条）

1. **改「建模缺口」，不改「工程实现」**：不动采集主循环的逐变量调度、设备级锁语义、EF 热注册机制、SignalR 消息协议。
2. **每个新增状态字段必须回答「跨重建生命周期」问题**：runtime 对象会被重连/重载整体重建（P1/P2 教训）。字段挂实例（接受重置）还是挂进程级容器（跨重建存活），必须在设计时显式决策并写入注释。
3. **管理员置位的状态必须持久化**（P3 教训）：内存态 + 落库 + 启动回读，参照 LastKnownStatus 模式。
4. **打点调用必须 try/catch 包裹**：与 FireEvent 自身模式一致（L720），打点异常绝不影响采集与报警主链路。
