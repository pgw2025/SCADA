## 步骤 0.2 现状行为基线记录

**目的**：阶段 1/2 改动后逐条比对，证明「连接态映射与推送时序未回归」。

**任务清单**：

1. **启动一台 S7 真实/仿真设备**（或 Virtual 设备），开启 Info 级日志，记录以下时序各一次：

   - a) 正常启动：`BuildAndRegisterDeviceAsync` 成功 → ConnectionState=Connected → DeviceStatus=Online 的日志顺序与时间戳；

   - b) 人为断开 PLC（拔网线/停仿真）→ 连续 3 轮失败 → `NeedsReconnect=true` → Worker 退出（ConnectionState=Disconnected）→ 调度器 5s 退避 → `ReconnectDeviceAsync` → 占位注册（ConnectionState=Error → DeviceStatus=Fault）→ 恢复 PLC → 重连成功 → Online 的完整日志序列；

   - c) 设备禁用（IsEnabled=false）：`RemoveDeviceAsync` → Offline 推送。

2. **记录 SignalR 推送序列**（前端浏览器 Network → WS 帧或后端日志）：

   - ReceiveDeviceStatus 的触发次数与顺序（对应上述 a/b/c 三场景，重点验证：状态未变化时**不**重复推送——`_lastPushedStatus` 去重生效）；

   - ReceiveVariableUpdate 在断线期间的行为（质量降级推送一次：Good→CommunicationError 仅推 1 次）。

3. **记录报警行为基线**：

   - 配置一条上限规则（如 Temperature > 80）→ 触发 → 恢复，确认 AlarmRecords 各产生一条 Triggered/Recovered，SignalR ReceiveAlarm 各推一次；

   - **记录既有缺陷行为**（作为 P2 的对照，不修复）：设备断线重连后，Worker 重建导致 `_ruleStates` 清零——若值持续越界，重连后首个采集轮会**再触发一次 Triggered**（形成第二条未恢复记录的边界情况）。本方案的 ActiveAlarmCount 初始化（步骤 2.4）会让 HasAlarm 在重连后立即正确反映「有活跃报警」。

4. **记录写值基线**：HTTP 写入一个可写变量 → 审计日志 + SignalR 回拨 + 实时表更新各一次。

**产出**：`docs/runtime-refactor/_baseline/行为基线-阶段0.md`（日志摘录 + 时序编号列表），供阶段 4 回归比对。
