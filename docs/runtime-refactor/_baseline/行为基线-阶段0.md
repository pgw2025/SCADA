## 2. 场景 b：S7 断线/重连循环（占位注册 + 退避重试）

依据：`backend_baseline.log` 行 46–338（S7 设备启动即不可达，持续产生重试循环）。

| 序号 | 日志（缩写） | 语义 |
|---|---|---|
| b1 | `S7 PLC 连接失败 Device=PLC-DEV-3115 Ip=192.168.1.60:102 Rack=0 Slot=1` + `TimeoutException` | 连接超时（5s） |
| b2 | `S7 驱动释放 Device=PLC-DEV-3115` | 驱动清理 |
| b3 | `设备 PLC-DEV-3115 (S7) 连接失败，已注册为待重连，调度器将按退避窗口自动重试` | **占位注册（Error → Fault）** |
| b4 | （b1→b3 按 ~5s 退避窗口反复循环，数百行） | 自动重试循环 |
| b5 | 偶发 `OperationCanceledException`（重试取消） | 新一轮重试启动前的取消 |

**关键时序结论**：
- 启动即不可达时，走 `BuildAndRegisterDeviceAsync` 连接失败分支 → 占位注册 → `ConnectionState=Error` → 对外 `DeviceStatus=Fault`；
- 之后调度器按 `reconnectIntervalMs=5000` 退避反复重试，每次均 `连接失败 → 驱动释放 → 已注册为待重连`；
- REST 实测：设备 2 未注册期间 `runtimeStatus=Offline`（`TryGetRuntimeStatus` 对不在册设备返回 Offline）；**重新启用后立即 `Fault`**（占位 Error→Fault 生效）。

> ⚠️ **基线缺口（需人工补录，Phase 4 前完成）**：本环境 S7 设备（192.168.1.60）不可达，无法采集「先 Connected 后断线 → NeedsReconnect → Worker 退出(Disconnected) → 退避 → ReconnectDeviceAsync → 占位(Fault) → 恢复 PLC → Online」的完整闭环。该闭环的基线时序须在具备真实/仿真 S7 PLC 时补录，作为 Phase 4 回归比对项。

## 3. 场景 c：设备禁用/启用 → 状态推送

依据：`obs_status_push.log`（device 1，VIRTUAL Online）+ REST 实测（`PUT /api/device/{id}/enabled?enabled=bool`）。

| 时刻 | 动作 | 观察到的 SignalR 推送 | REST runtimeStatus |
|---|---|---|---|
| 23:06:27.939 | 禁用 device 1 | `ReceiveDeviceStatus deviceId=1 status=Offline` | Offline |
| 23:06:36.073 | 启用 device 1 | **无 Online 状态推送**；推送全量 6 变量 `ReceiveVariableUpdate`（kg1/kg2/sw/dy_a/dy_b/dy_c，Good） | Online |

**关键时序结论（回归红线）**：
- 禁用走 `RemoveDeviceAsync`：移除 `_lastPushedStatus` 后**无条件推送 Offline**（即使原状态已是 Offline 也会再推一次）；
- 启用后新 runtime 注册：初始状态写入 `_lastPushedStatus`（去重），**不重复推送 Online**；
- 启用后 VIRTUAL 设备首轮采集即推送全量变量值（Worker 首次读取后逐变量 `ReceiveVariableUpdate`）。

## 5. SignalR 推送序列基线

### 5.1 去重行为（回归红线）

| 场景 | 推送 | 结论 |
|---|---|---|
| VIRTUAL 静态值（12s 观察，无写入） | **0 条** `ReceiveVariableUpdate` | 值未变化不推送（`_lastPushedStatus`/变更检测去重生效） |
| 写 kg1=false（原 true） | 1 条 `ReceiveVariableUpdate kg1=false Good` | 变化即推 1 次 |
| 写 kg1=true（恢复） | 1 条 `ReceiveVariableUpdate kg1=true Good` | 变化即推 1 次 |
| 禁用 Online 设备 | 1 条 `ReceiveDeviceStatus Offline` | 无条件推 |
| 启用 Online 设备 | 0 条 `ReceiveDeviceStatus` | 初始状态去重，不推 |

依据：`obs_write_push.log`、`obs_status_push.log`。

### 5.2 变量值推送帧格式（接收载荷）

```
ReceiveVariableUpdate: { deviceId, variableKey, value, quality: "Good", updateTime(UTC ISO) }
ReceiveDeviceStatus:   (deviceId: number, status: "Online"|"Offline"|"Fault"|"Connecting"|"ConfigUpdating")
ReceiveAlarm:          { eventType: "Triggered"|"Recovered", deviceId, variableKey, level, actualValue, source, message, ... }
```

> `ReceiveDeviceStatus` 为 `Clients.All` 广播（`SignalRNotificationService.NotifyDeviceStatusAsync`），非分组定向。

## 6. 报警行为基线

### 6.1 触发 → 恢复闭环（规则 1：`sw > 60`，sw 原值 50）

依据：`obs_alarm_push.log` + `GET /api/alarmrecord`。

| 时刻 | 动作 | SignalR 推送 | AlarmRecords |
|---|---|---|---|
| 23:08:04.551 | 写 sw=80 | `ReceiveVariableUpdate sw=80 Good` | — |
| 23:08:04.683 | （触发） | `ReceiveAlarm message=水位 大于 60`（eventType=Triggered） | 新记录 id=8：`triggeredAt=23:08:04.668`，`actualValue=80` |
| 23:08:09.589 | 写 sw=40 | `ReceiveVariableUpdate sw=40 Good` | — |
| 23:08:09.687 | （恢复） | `ReceiveAlarm message=水位 大于 60`（eventType=Recovered） | 同记录 id=8：`recoveredAt=23:08:09.686`，`recoveryValue=40` |

**结论**：触发/恢复各推 1 次 `ReceiveAlarm`；AlarmRecords 单条记录内同时写 `TriggeredAt` + `RecoveredAt`；恢复后无活跃报警。

### 6.2 既有缺陷行为登记（P2 对照，本阶段不修复）

- AlarmRecords 中存在多条「Triggered 后长期未 Recovered」的历史记录（id=1/3/4，恢复时间被启动巡检批量补写）；
- 启动期 `AlarmRecoveryStartupService` 会巡检并补恢复遗留未恢复报警（本次补 0 条，`backend_baseline.log` a9）；
- 断线重连后 Worker 重建 → `_ruleStates` 清零 → 值持续越界时首轮会**再次触发 Triggered**（预期既有行为，Phase 2 的 ActiveAlarmCount 初始化将修正 HasAlarm 一致性）。
