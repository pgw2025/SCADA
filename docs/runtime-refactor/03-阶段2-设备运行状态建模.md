## 设计总览

### 双状态正交模型（After）

```
DeviceRuntime
 ├── ConnectionState      （既有，连接态 → DeviceStatus 映射与推送链路完全不变）
 ├── RunState             （新增，机器状态：Unknown/Stopped/Running/Paused/Fault/Maintenance）
 ├── StateChangedAt       （新增，RunState 最近变更时刻，UTC）
 ├── HasAlarm             （新增，派生只读 = ActiveAlarmCount > 0）
 └── ActiveAlarmCount     （新增，设备级活跃报警计数，private set）
```

### 语义边界声明（P4：两个 Fault 不得混淆）

| 维度  | 字段                                   | Fault 语义                  | 数据来源                    |
| --- | ------------------------------------ | ------------------------- | ----------------------- |
| 连接态 | ConnectionState → DeviceStatus.Fault | **PLC 通信故障**（连续 3 轮采集全失败） | DeviceWorker 轮次判定       |
| 运行态 | RunState.Fault                       | **机器自身故障**（如设备报故障码/急停）    | 管理员置位（本轮）/约定变量（D2-B 后续） |

> 该声明必须写入 `DeviceRunState` 枚举与快照 DTO 的 XML 注释，并在 API 文档中显式区分 `connectionState` 与 `runState` 字段。

### HasAlarm 聚合模型（P2 修正）

```
                 ┌──────────────────────────────────────────────┐
                 │  DeviceRuntime.ActiveAlarmCount (int)        │
                 └──────────────────────────────────────────────┘
                     ▲ +1                          ▲ 初始化（重建时）
                     │ -1                          │
        DeviceWorker.FireEvent              BuildAndRegisterDeviceAsync
        (Triggered +1 / Recovered -1)        (查 AlarmRecords: RecoveredAt IS NULL)
                     │                              │
        ┌────────────┴───────────┐      ┌───────────▼─────────────┐
        │ 报警触发/恢复既有出口    │      │ 启动批量 / 单台重载查询   │
        │ (规则报警 + MinMax 兜底) │      │ (P2: 跨 Worker/Runtime   │
        └────────────────────────┘      │  重建与 DB 记录一致)      │
                                        └─────────────────────────┘
```

**规则**：

- `HasAlarm` 为派生只读属性（`ActiveAlarmCount > 0`），不提供直接 setter；

- 计数 clamp 下界 0（防重复 Recovered 导致负数）；

- **计数语义 = 未恢复报警条数**（不论是否已被操作员 Ack 确认——Ack 是「已知晓」，Recovered 才是「已恢复」；与 AlarmRecords 表 Ack/Recover 双状态语义对齐）。

### RunState 持久化模型（P3 修正，D8-a）

```
PUT /api/devices/{id}/runtime/runstate （阶段 3 提供端点）
   │
   ├─► 写 DB: Devices.RunState / RunStateChangedAt
   └─► 更新内存: runtime.SetRunState(state)
   
进程启动 / 设备重载（BuildAndRegisterDeviceAsync）
   └─► 从 Device 实体回读 RunState 初始化 runtime（EF Include 链已含 Device，零额外查询）
```

## 步骤 2.1 新增 DeviceRunState 枚举（Domain）

**文件**：`Server/ScadaServer.Domain/Enums/DeviceRunState.cs`（新建）

```csharp
namespace ScadaServer.Domain.Enums;

/// <summary>
/// 设备运行状态（机器状态，与 PLC 通信状态正交）。
/// <para>
/// 语义边界（勿与 DeviceStatus.Fault 混淆）：
/// 本枚举描述"机器现在在干什么"（运行/停止/检修…）；
/// DeviceStatus 描述"与 PLC 的通信是否正常"。
/// PLC 连接正常（Online）但机器停止（Stopped）是合法组合，反之亦然。
/// </para>
/// </summary>
public enum DeviceRunState
{
    /// <summary>未知（默认，未置位）。</summary>
    Unknown = 0,

    /// <summary>停机。</summary>
    Stopped = 1,

    /// <summary>运行中。</summary>
    Running = 2,

    /// <summary>暂停（临时停线，预期恢复）。</summary>
    Paused = 3,

    /// <summary>机器故障（设备自身故障/急停，非通信故障）。</summary>
    Fault = 4,

    /// <summary>检修/维护中（禁止远程启停与写入操作的建议状态）。</summary>
    Maintenance = 5
}
```

**要点**：

- 数值稳定（持久化到 DB 的 int），后续只增不改不删；

- `Maintenance` 的存在使「检修中设备」在 UI 可标记，配合前端禁写是后续演进（本轮后端先行）。

**验收**：build 通过。

## 步骤 2.2 DeviceRuntime 新增运行状态字段与收口方法

**文件**：`Server/ScadaServer.Runtime/Devices/DeviceRuntime.cs`

**任务**：新增字段区 + 收口方法：

```csharp
// ===================== 设备运行状态（阶段 2 新增，与连接态正交） =====================

private DeviceRunState _runState = DeviceRunState.Unknown;
private int _activeAlarmCount;

/// <summary>机器运行状态（Unknown/Stopped/Running/Paused/Fault/Maintenance）。
/// 与 ConnectionState（PLC 通信态）正交：Online+Stopped、Fault+Running 均为合法组合。
/// 持久化于 Devices.RunState，启动/重载时回读初始化（方案 P3）。</summary>
public DeviceRunState RunState
{
    get => _runState;
    private set { /* 经 SetRunState 收口 */ }
}

/// <summary>RunState 最近一次变更时刻（UTC）。仅经 SetRunState 推进。</summary>
public DateTime? StateChangedAt { get; private set; }

/// <summary>设备级活跃（未恢复）报警计数。FireEvent 打点 ±1；重建时从 AlarmRecords 初始化（方案 P2）。</summary>
public int ActiveAlarmCount
{
    get => _activeAlarmCount;
    private set { /* 经 ApplyAlarmDelta / InitializeAlarmCount 收口 */ }
}

/// <summary>是否存在未恢复报警（派生只读）。</summary>
public bool HasAlarm => _activeAlarmCount > 0;

/// <summary>
/// 置位机器运行状态：仅值变化时更新并推进 StateChangedAt。
/// 不触发任何推送（D10-a：RunState 变化不进 SignalR，由快照轮询读取）。
/// </summary>
public void SetRunState(DeviceRunState state)
{
    if (_runState == state) return;
    _runState = state;
    StateChangedAt = DateTime.UtcNow;
}

/// <summary>
/// 报警计数增量打点（Worker FireEvent 出口调用）：Triggered 传 +1，Recovered 传 -1。
/// 下界 clamp 0，重复 Recovered 不会产生负计数。
/// </summary>
public void ApplyAlarmDelta(int delta)
{
    var newValue = _activeAlarmCount + delta;
    _activeAlarmCount = newValue < 0 ? 0 : newValue;
}

/// <summary>
/// 报警计数初始化（BuildAndRegisterDeviceAsync 重建 runtime 时从 AlarmRecords 查询结果回填）。
/// 与 ApplyAlarmDelta 互斥使用：仅注册路径调用一次。
/// </summary>
public void InitializeAlarmCount(int count)
{
    _activeAlarmCount = count < 0 ? 0 : count;
}
```

**要点**：

- **不引入 DeviceStatusRuntime 子对象分区**（原方案 R1 设计要点 2 已判定，字段直挂 DeviceRuntime，避免大改引用方）；

- `SetRunState` 不推送、不发事件（D10-a），与 ConnectionStateChanged 事件机制完全隔离，确保「连接态推送链路零改动」红线；

- 线程模型：`_runState`（枚举）/`_activeAlarmCount`（int）单字段读写原子；跨字段一致性（RunState+StateChangedAt）容忍微小撕裂（快照为可观测用途，同 00 总览 P6 决策）。

**验收**：build 通过；既有代码零改动（纯新增成员）。

## 步骤 2.4 BuildAndRegisterDeviceAsync 初始化报警计数（P2 修正）

**文件**：`Server/ScadaServer.Runtime/RuntimeManager.cs`

**任务 2.4a**：新增按设备查询活跃报警数的方法（复用 scope 隔离模式）：

```csharp
/// <summary>
/// 查询设备当前未恢复（活跃）报警条数（方案 P2：runtime 重建后与 AlarmRecords 对齐）。
/// 查询失败返回 0 并告警——不阻塞设备注册主流程（与报警规则加载失败同容错等级）。
/// </summary>
private async Task<int> CountActiveAlarmsAsync(ScadaDbContext db, int deviceId)
{
    try
    {
        return await db.AlarmRecords
            .CountAsync(a => a.DeviceId == deviceId && a.RecoveredAt == null);
    }
    catch (Exception ex)
    {
        _logger.LogWarning(ex, "查询设备 {DeviceId} 活跃报警数失败，报警计数从 0 开始。", deviceId);
        return 0;
    }
}
```

> 注：`AlarmRecords` 的 DbSet 属性名以 `ScadaDbContext` 实际定义为准（实施时核对，若为 `AlarmRecords` / `AlarmRecord` 集合名差异需对齐）；`RecoveredAt` 字段已核实存在（AlarmRecord.cs:104）。

**任务 2.4b**：`BuildAndRegisterDeviceAsync`（L381–495）在 `RegisterDevice(runtime)` 之前（连接成功路径与占位路径均可，建议放在 L454 `runtime.ConnectionState = Connected` 之后、变量装配之前）插入初始化：

```csharp
// 设备级报警计数初始化（方案 P2）：从 AlarmRecords 回填未恢复报警数，
// 使 HasAlarm 在 runtime 重建（重连/重载/重启）后立即与数据库记录一致，
// 消除「Worker 重建丢状态 → HasAlarm 卡 false/true」的幽灵报警窗口。
runtime.InitializeAlarmCount(await CountActiveAlarmsAsync(db, device.Id));
```

> 注意：`BuildAndRegisterDeviceAsync` 当前签名不持有 DbContext（device 实体由调用方加载传入）。两个选择：
>
> - **选择 A（推荐）**：方法内部临时 `using var scope = _scopeFactory.CreateScope();` 取 db——仅多一次轻量 scope 开销，每次注册/重连一次查询，频率极低；
>
> - 选择 B：由调用方（InitializeAsync 批量启动时先做一次 `GROUP BY DeviceId` 全量字典、RegisterDeviceAsync 单台查询单个）传入。实现更省但侵入两个调用点。
>   实施时按 A 执行，保持 BuildAndRegisterDeviceAsync 自包含（该方法本就是「启动与运行期注册共用，避免两份实现漂移」L379）。

**任务 2.4c（可选优化）**：`InitializeAsync`（L163–219）启动路径可改为一次批量查询替代 N 次单查（设备多时收益明显）：

```csharp
// 启动期批量：一次 GROUP BY 取所有设备的活跃报警数
var activeAlarmCounts = await db.AlarmRecords
    .Where(a => a.RecoveredAt == null)
    .GroupBy(a => a.DeviceId)
    .Select(g => new { g.Key, Count = g.Count() })
    .ToDictionaryAsync(x => x.Key, x => x.Count);
```

随后逐设备 `BuildAndRegisterDeviceAsync` 时从字典取（缺失则 0）。若嫌复杂可先不做（每台一次 COUNT 查询，启动期可接受），登记为实施时的可选优化。

**验收**：

1. 制造一条未恢复报警（触发规则后停止采集，使 RecoveredAt 保持 null）→ 重启服务 → 该设备 HasAlarm 立即 true；
2. 设备重载（编辑设备触发 ReloadDeviceAsync）→ HasAlarm 保持与 DB 一致；
3. 报警恢复 → 计数归零。
