### 4.3.5 回归发现与修复（快照重连窗口 404）

**现象**：对持续断线（占位待重连）的设备，快照端点在重连 connect 期间几乎总是 404。实测命中率 ≈ 1/60（约 1.6%）——因为 `ReconnectDeviceAsync` 先 `TryRemove` 再从在册表移除设备，connect（约 5s）期间不在 `DeviceRuntimes`，`TryGetRuntimeSnapshot` 返回 false。

**评估**：D5-a 决策"未注册（禁用/初始化失败/重连窗口）→ 404"与 N-1"断线期间快照可观测"冲突；持续断线设备的诊断快照几乎不可达，削弱 N-1 验收意图。**决定修复**（评审确认，非搁置）。

**修复方案（D5-a 回退，最小改动）**：

- `RuntimeManager` 新增 `_reconnecting: ConcurrentDictionary<int, DeviceRuntime>`，在 `ReconnectDeviceAsync` 移除后、connect 期间保留占位运行时引用；

- `TryGetRuntimeSnapshot` 在不在册时回退读 `_reconnecting`，保证重连窗口仍返回断线诊断快照（ConnectionState/LastError/ReconnectCount 等）；

- `finally` 中清除该引用，连接成功后新运行时权威接管。

**验证**：修复后设备 2 快照密集轮询 HIT=25/25（100%），connectionState=4(Error)/status=2(Fault)/reconnectCount 进程级累计；设备 1 无回归（Online、runState 持久化保持）。新增代码 0 警告。

**已知局限（基线缺口，非本次改动引入）**：

- 初始连接失败的占位设备 `LastError`/`ConsecutiveFailureCount` 恒为 null/0（未经历 connected→断线，Worker 未打点）；"LastError 非空"需设备先连接成功再断线方可复现，受 192.168.1.60 不可达限制无法在本环境验证，留待人工接入真实 PLC。

- N-3 HasAlarm 与 AlarmRecords 对齐需真实报警触发场景，本环境无活跃报警，仅确认 hasAlarm=false 一致。
