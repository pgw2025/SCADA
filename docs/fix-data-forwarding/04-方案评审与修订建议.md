# 04 方案评审与修订建议

> 本文对 [02-修复方案设计.md](./02-修复方案设计.md) 进行复审，指出其中**可能导致回归或无法真正解决问题**的设计缺陷，并给出修订建议。
> 结论基于对 `VariableBindingEngine` / `RuntimeManager.WriteVariableAsync` / `VariableValueProcessor` 的实际代码复核。

---

## 一、总体评价

- 方向正确：按 A/B/C/D 四类根因分层修复、分阶段落地、每阶段带验收与回归，结构清晰、可执行性强。
- 根因 A、B、C 的修复思路基本成立，但**若干实现细节未定义**会导致语义歧义（见下文 P2/P3）。
- **根因 D 的原方案存在一个 P0 级设计缺陷**：D2（Source 语义修正）会让**多跳链断链**；D1（值匹配 + 一次性消费）**不能**真正解决"旧值污染"问题。需整体修订。

---

## 二、P0 级问题（必须修订，否则引入回归）

### P0-1：D2 会让多跳链 A→B→C 断链

#### 现状机制（关键事实）

`RuntimeManager.WriteVariableAsync` 写入成功后**恒以 `Source = UserWrite` 发布事件**（`RuntimeManager.cs:929-938`）。而 `VariableBindingEngine.OnVariableChanged` 只跳过 `Source == BindingWrite`（`VariableBindingEngine.cs:182`）。

**结论：当前多跳传播恰恰依赖"绑定写入 → 发布 UserWrite 事件 → 再次进入引擎 → 查目标出边 → 立即写下游 C"这条链。** `BindingWrite` 分支是死代码，但这不是 bug，而是多跳"立即传播"的既成机制。

#### D2 的后果

原方案 D2 要求"把绑定写入的 Source 改为 `BindingWrite`，并激活 `OnVariableChanged` 的跳过分支"。一旦实施：

```
A 变化 → 引擎写 B=X → Source=BindingWrite → OnVariableChanged 直接 return
      → B 的出边（B→C）不再被触发 → C 永远收不到值
```

多跳链退化为单跳，**数据在下游完全断流**。这不是"改变时序"，而是功能性破坏。

#### 修订建议

**放弃 D2（Source 语义修正）**，保留当前 `UserWrite` 传播机制不动。若确有理由需要区分"绑定写入"与"用户写入"事件，也必须配套"绑定引擎在写入成功后自行触发下游转发"（写入 `WriteTargetAsync` 成功路径里，对目标变量的出边再入队一次），不能依赖事件总线被跳过。综合权衡，**本批次不建议动 Source 语义**。

---

### P0-2：D1"值匹配 + 一次性消费"不能解决根因 D 的真实场景

#### 真实失效时序（回顾根因 D）

绑定写 B=X（内存 B.Value=X，LastBindingWriteValue=X）后，B 的设备写入**有生效延迟**：

| 轮次 | 回读值 | 原逻辑（值匹配） | 原逻辑后果 |
|---|---|---|---|
| t1 | Y（设备尚未生效，旧值） | `ValueEquals(Y,X)=false` → 非回声 → **IsChanged=true** | 发布 Polling(B=Y) → **覆盖 C=Y（污染）** |
| t2 | X（已生效） | `ValueEquals(X,X)=true` 且窗口内 → 回声 → IsChanged=false | 抑制 → C 无法纠正回 X |

#### 原 D1 的缺陷

原 D1 只是把 t2 的"抑制"改为"一次性消费"，**对 t1 的旧值 Y 污染完全不设防**——`ValueEquals(Y,X)=false` 时 `isEcho` 仍为 false，Y 照常发布并污染 C。销毁旧值污染问题**没有被修复**。

#### 修订建议（核心）

回声抑制应改为**绑定写入后的静默窗口**：绑定写 B=X 成功后，在窗口内（`now - LastBindingWriteTime <= echoWindowMs`）对目标变量的**任何回读值（无论 X 还是 Y）都不发布变化事件**（`IsChanged=false`），窗口过后恢复正常传播。

效果：
- t1 回读 Y（窗口内）→ 静默，不污染 C ✓
- t2 回读 X（窗口内）→ 静默，不重复 ✓
- 窗口过后 B 若真实变化 → 正常转发 ✓

实现要点：
- 判定条件从 `ValueEquals(newValue, LastBindingWriteValue)` 改为**仅窗口判断**（不再比对值），即窗口内一律视为"绑定写入过渡态"。
- 保留 `LastBindingWriteValue` 仅作观测/审计用，不再作为抑制的硬条件。
- 副作用权衡：窗口内若 B 被"外部真实源"改到新值 Z，也会被短暂静默（最长 `2×轮询间隔`）。该副作用远小于"多跳卡陈旧/断链"，可接受；如需更精细，可后续用"窗口 + 首次命中期望值后结束静默"升级，但首版以"窗口静默"为基线最简且正确。

## 三、P1 级问题（会导致语义歧义或竞态，需补设计）

### P1-1：重试阻塞单消费者队列 + 同目标积压

A2 重试（500ms/1s/2s ≈ 3.5s）在单消费者 `DispatchLoopAsync` 内执行，期间同一目标的后续条目全部排队。A3 仅提"保留最新值"，但未定义如何合并。

**修订**：消费者出队时按目标 `(DeviceId, VariableKey)` 合并——处理某目标前，先**窥视队列丢弃该目标的更早条目**（或写入侧用 `ConcurrentDictionary` 目标级去重 + 版本号），保证"重试期间同一目标只保留最新一条"。这同时缓解根因 F（DropOldest 丢旧值）。

### P1-2：越限 Clamp 的落点未定义

A4 说"夹取到 [Min,Max] 后写入"，但 `WriteVariableAsync` 的越限校验（`RuntimeManager.cs:869-875`）发生在 `ToRaw`（:879）**之前**，且成功路径回写内存 `vr.Value = value`（:909）用的是**未夹取**的 `value`。

**需明确**：
- Clamp 作用于 `value`（工程值）还是 `rawValue`（原始值）？建议 Clamp 工程值 `value`，再走 `ToRaw`。
- Clamp 后的值是否回写 `vr.Value` / 是否作为事件 `Value` 发布 / 是否写入审计日志（应写明"写入值 = 夹取值"，前端/审计一致）。
- `vr.Min/Max` 为 null 时不做 Clamp（原样写入）。

### P1-3：B1 频繁重载与环报警重复推送

每次设备注册/重连成功触发 `LoadAsync`，其 `DetectAndRejectCycles` 对每条环调用 `NotifyCycleAlarm`（`VariableBindingEngine.cs:343-353`）。多设备并发重连会导致**同一环被重复推送系统报警**。

**修订**：环报警增加"进程内已推送去重集合"（按环节点组合或绑定名去重），或仅当环集合较上次加载发生变化时才推送。

### P1-4：保存期校验的可写性判定需与运行时一致

C1 校验目标可写，但运行时 `IsReadOnly` 用 `EffectiveAccessMode`（`VariableRuntime.cs:78-84`），其语义是 `Instance.AccessModeOverride` **优先**，回退 `Definition.AccessMode`。保存期校验必须**复用同一判定**（Override 优先 + `== "Read"`），否则会出现"保存期判定可写、运行期判只读"（或反向）的不一致。

## 四、P2/P3 级优化建议

### P2-1：补写与正常转发对同一目标的串行化

A3 补写扫描与正常入队写可能并发命中同一目标，`ConcurrentDictionary` 只保证字典原子，不保证"旧值不覆盖新值"。建议对所有"实际落盘写入"统一收口到 `DispatchLoopAsync`（补写也走队列），由单消费者天然串行化，避免另起扫描线程写驱动。

### P2-2：`LoadAsync` 全量重建的性能与节流

B 触发重载后 `LoadAsync` 每次 `CreateScope` 全量读库 + 全量遍历。设备频繁重连时产生不必要 DB 开销。建议：100ms 去抖基础上，增加**最小重载间隔**（如 1s），或按"涉及设备"增量重建。

### P2-3：回声静默窗口的上限

现有 `echoWindowMs = max(PollingIntervalMs, 1000) * 2`，轮询 60s 时窗口达 120s，静默期内目标变量的真实变化会长达 2 分钟不被传播。建议静默窗口设为 `min(echoWindowMs, 5000ms)` 或引入可配置上限，在"防污染"与"传播时效"间取平衡。

### P2-4：测试用例需落到位

03 文档测试偏集成，建议补充**单元测试用例表**：回声静默窗口（含旧值 Y→新值 X 时序）、重试分类矩阵（7 类失败 × 可重试/不可重试）、Pending 转正、Clamp/Reject 边界、"窗口静默"与"外部真实变化"的取舍用例。

### P2-5：命名与文档口径统一

方案中 `BindingStatus`/`SkipReason`/`OutOfRangePolicy`/`BindingEchoPending` 等新字段需与现有 DTO/实体命名风格（camelCase 映射、`Active` 等）统一，并在 01 文档补充根因 E 的**重新定性**（旧文档将 Source 硬编码视为缺陷，实为多跳传播机制，不宜当作 bug 修复）。

---

## 五、修订后的根因 D 最终建议（替换原 D1/D2）

1. **D1′（替换原 D1）**：回声抑制改为"绑定写入后的静默窗口"——窗口内目标变量任何回读一律不发布变化事件（P0-2），判定仅用窗口、不再比对值。
2. **D2′（替换原 D2）**：**不做 Source 语义修正**，保留 `UserWrite` 传播机制（P0-1）。若未来确需区分事件来源，须同时实现"绑定引擎写入成功后自行触发下游转发"的配套机制，且独立回归多跳。
3. 静默窗口上限按 P2-3 设 cap。
4. 回归重点：单跳 / 多跳 / 一源多目标 / 多源一目标四类拓扑 + 写入生效延迟场景（旧值先回读）+ 窗口内外部真实变化取舍。

## 六、结论

- 根因 A、B、C 的修复方向可保留，按 P1/P2 补全实现细节即可。
- **根因 D 原方案必须整体修订**：D2 去掉（否则多跳断链），D1 改为"静默窗口"（否则旧值污染无法解决）。
- 建议落地顺序不变（C → A → B → D），但 D 阶段开工前先按本文第五节确认修订设计。
