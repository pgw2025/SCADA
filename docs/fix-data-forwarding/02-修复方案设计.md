# 02 修复方案设计

> 逐根因给出修复设计：目标、设计思路、具体改动点（文件/类/方法/字段）、影响面与风险。
> 本方案**不修改代码**，仅设计。所有改动建议按 [03-执行计划与验证.md](./03-执行计划与验证.md) 分阶段落地。

## 根因 C：保存期强校验 + 前端过滤 + 加载状态可见（先做，低风险）

### 目标

非法规则（源/目标设备或变量缺失、目标只读）**在保存时即被拒绝**，存量非法规则**可见**而非静默。

### C1 后端保存期校验

**改动点**：`ScadaServer.Application/Services/DataConversionAppService.cs`（`CreateAsync` / `UpdateAsync`）

- 注入 `ScadaDbContext`（或 `IDeviceRepository` + 设备变量查询服务），在持久化前执行校验：
  1. 源设备存在且 `IsEnabled`
  2. 源变量存在且启用（按 `DataPoint.Key` 匹配）
  3. 目标设备存在且 `IsEnabled`
  4. 目标变量存在且启用
  5. 目标变量可写（判定复用运行时 `EffectiveAccessMode` 语义：`Instance.AccessModeOverride` 优先、回退 `Definition.AccessMode`，最终 `== "Read"` 视为只读拒绝，避免保存期与运行期判定不一致）
- 任一失败 → 抛出业务异常（自定义 `BusinessException` 或 `ValidationException`），错误信息中文明确，如：
  `目标变量 [key] 为只读，禁止作为数据转换目标`
- **控制器**（`DataConversionController.cs`）异常由全局过滤器转 400（项目已有统一异常处理约定，无需新增）。

**注意**：目标设备"未连接/未运行"不拦截（属运行态，交给根因 B 的 pending 机制），只校验静态配置合法性。

### C2 前端过滤与提示

**改动点**：`Client/src/components/DataConversionView.vue`（:96-100 targetVariables）、`Client/src/types.ts`

- 目标变量下拉数据源扩展为携带 `accessMode`（设备变量列表接口已含变量定义信息，前端 `dev.variables` 需确认字段来源；若缺失则从变量列表接口补齐 `accessMode` 字段）。
- 目标下拉**过滤掉只读变量**，并禁用"目标变量为只读"的选项。
- 保存按钮点击前二次校验 + 错误 toast（复用现有 `addLog` / toast 机制）。

### C3 加载状态可见（与 B3 共用，见根因 B）

存量非法规则经 `LoadAsync` 跳过时，将 (规则Id, 跳过原因) 记录到引擎内存字典，规则列表接口返回补充字段 `bindingStatus`（`Active` / `Skipped` + `skipReason`），前端规则卡片展示"未生效（原因）"徽标。

**改动点**：
- `VariableBindingEngine`：`LoadAsync` 收集跳过明细到 `IReadOnlyDictionary<int, string> SkipReasons`（volatile 快照）。
- `DataConversionController.GetAll`：返回 DTO 增加 `BindingStatus` / `SkipReason` 字段（由引擎快照填充）。
- `DataConversionDto`：增加 `BindingStatus`、`SkipReason` 两个可选字段。
- `DataConversionView.vue`：卡片/列表展示状态徽标。

## 根因 A：失败分类 + 有限重试 + 离线补写 + 越限策略 + 失败告警

### 目标

偶发失败可自愈：瞬时故障有限重试、目标离线期间保留**最新值**并在恢复后补写、越限值按策略处理、失败可见可告警。

### A1 写入失败分类

**改动点**：`RuntimeManager.WriteVariableAsync` 失败路径返回结构化结果。

- 新增枚举 `VariableWriteFailureKind`：`DeviceNotRunning` / `VariableNotExist` / `VariableDisabled` / `VariableReadOnly` / `DriverNotReady` / `DeviceNotConnected` / `OutOfRange` / `Timeout` / `DriverError` / `Unknown`。
- `WriteVariableAsync` 失败时在返回结果中携带 `FailureKind`（保留现有 `(bool Success, string? ErrorMessage)` 签名兼容，新增重载或扩展元组字段，避免破坏现有调用方）。

### A2 有限重试（瞬时类）

**改动点**：`VariableBindingEngine.WriteTargetAsync`（`VariableBindingEngine.cs:231-268`）

- 重试分类：
  - **可重试**：`DriverNotReady` / `DeviceNotConnected` / `DeviceNotRunning`（重连窗口）/ `Timeout` / `DriverError`
  - **不可重试**：`VariableNotExist` / `VariableDisabled` / `VariableReadOnly` / `OutOfRange`（确定性配置问题，交给 C 类校验拦截）
- 可重试失败：指数退避重试（如 500ms → 1s → 2s，共 3 次），全部失败后进入 A3 补写通道（同时 `LogWarning`）。
- 不可重试失败：保持现状记日志（根因 C 落地后此类应在保存期被拦截，此处为兜底）。
- **重试期队列合并**：重试会占用单消费者（≈3.5s），同一目标的后续条目会堆积。消费前对同目标 `(DeviceId, VariableKey)` 做"只保留最新值"合并（出队时窥视丢弃同目标旧条目，或写入侧用 `ConcurrentDictionary` 目标级去重 + 版本号），确保重试结束后只落一次最新值。

### A3 离线补写（每目标最新值）

**改动点**：
- `VariableBindingEngine`：新增 `ConcurrentDictionary<(int,string), (object? Value, DateTime At)> _pendingWrites`（每目标仅保留**最新值**，避免补写风暴）。
- 补写触发：
  - 方案一（推荐，事件驱动）：订阅 `RuntimeManager.StatusChanged`（`RuntimeManager.cs:103`），目标设备转为 `Online` 时触发一次补写扫描（对 `_pendingWrites` 中该设备条目执行 `WriteTargetAsync`，成功即移除）。
  - 方案二（定时兜底）：`DispatchLoopAsync` 或独立轻量定时器（如 1s tick）扫描 `_pendingWrites`，对目标设备已 `Connected` 且条目存在超过退避期的执行补写。
- 补写幂等：补写成功后清除条目；失败保留并重置时间戳（进入下一轮退避），避免热循环。
- 队列丢弃（DropOldest）的条目同样落入 `_pendingWrites`，由补写机制兜底（缓解根因 F）。

### A4 越限值策略（Clamp / Reject）

**改动点**：`WriteVariableAsync`（`RuntimeManager.cs:869-875`）+ `DataConversion` 实体 + DTO

- 默认行为改为 **Clamp**（夹取到 `[Min, Max]` 后写入，日志记录夹取前后值），消除"值一超限就不转发"的偶发丢失。
- **Clamp 落点明确**：Clamp 作用于**工程值 `value`**（夹取到 `[Min,Max]` 后再走 `VariableScaling.ToRaw`）；夹取后的值需**统一回写** `vr.Value`、作为事件 `Value` 发布、写入审计与实时快照（三者一致为夹取值）。`Min/Max` 为 null 或值为 bool 时不 Clamp（原样写入）。
- 提供规则级开关：`DataConversion` 增加 `OutOfRangePolicy`（`Clamp` / `Reject`，默认 `Clamp`），DTO 同步、前端规则弹窗可选。
- `Reject` 模式下：记录失败 + 可选告警（见 A5）。

### A5 失败指标与告警

**改动点**：`VariableBindingEngine`

- 现有 `GetStats()`（`VariableBindingEngine.cs:176-177`）增加 `Pending`（补写队列长度）/ `Dropped` 计数返回。
- 连续失败阈值告警：目标 (设备,变量) 连续失败 ≥ N 次（如 10）→ `_notificationService.NotifySystemAlarmAsync(..., "变量绑定连续写入失败", ...)`（复用 `NotifyCycleAlarm` 模式，fire-and-forget + 兜底）。
- 可选：`DataConversionController` 增加只读监控端点 `GET api/DataConversion/stats` 暴露引擎指标。

### 影响与风险

- 重试会延长单条转发的最长耗时（3 次重试 + 退避 ≈ 3.5s），但队列为单消费者 + 有界，仅影响该目标后续条目的处理延迟；建议重试期间**跳过后续同目标条目**（保留最新值语义，见 A3 合并）。
- Clamp 改变数据语义（写入值 ≠ 源值），需前端/文档明示；默认开启但可在规则级关闭。

## 根因 B：设备注册/恢复后触发绑定重载 + pending 规则重试

### 目标

设备启动/重连完成后，此前因"设备未运行"被跳过的规则自动补加载；加载状态对用户可见。

### B1 设备就绪触发重载

**改动点**：
- `RuntimeManager`：
  - `RegisterDeviceAsync` 成功注册设备后（`BuildAndRegisterDeviceAsync` 返回 true 处，`RuntimeManager.cs:275` 附近）触发 `_bindingEngine.LoadAsync()`；
  - `ReconnectDeviceAsync` 恢复路径（会话重连成功/重新注册完成）同样触发。
- **去抖**：启动批量注册场景下多次触发会全量重建索引，采用 100ms 去抖窗口合并（复用 `ConnectionSession.ScheduleSync` 的去抖模式，或引擎内置去抖：`LoadAsync` 内部若距上次加载 < 100ms 则合并到一次）。
- **最小重载间隔**：设备频繁重连时 `LoadAsync` 每次 `CreateScope` 全量读库 + 遍历，建议在 100ms 去抖之上设最小重载间隔（如 1s），压降 DB 开销。
- **环报警去重**：`LoadAsync` 的 `DetectAndRejectCycles` 会对每条环推送 `NotifyCycleAlarm`，频繁重载会重复推送；需增加"进程内已推送环集合"去重（按绑定名/环节点组合），仅当环集合较上次变化时推送。
- 补充（可选，B2 的兜底）：`DeviceScheduler.SchedulerLoopAsync`（`DeviceScheduler.cs:104`）tick 中检测引擎存在 pending 规则且对应设备已就绪时，调用引擎 `RetryPendingAsync()`。

### B2 pending 规则机制

**改动点**：`VariableBindingEngine`（`LoadAsync` :78-111）

- 区分跳过原因：
  - **瞬时**（设备未运行 / 驱动未就绪）：规则进入 `_pending` 列表（含跳过原因与时间），**不丢弃**；
  - **确定性**（变量不存在 / 目标只读）：不进入 pending（属根因 C，由保存期校验拦截 + 状态可见展示）。
- 新增 `Task RetryPendingAsync()`：对 pending 中"设备现已就绪"的规则执行与 `LoadAsync` 相同的单条校验后并入索引；成功移出 pending，失败保留。
- pending 条目持久化不需要（进程内存即可）；服务重启后 `LoadAsync` 自然重载。

### B3 加载状态可见（与 C3 合并实施）

- 见 C3：`LoadAsync` 产出 `SkipReasons`（含 pending 与拒绝），规则列表接口返回 `BindingStatus` / `SkipReason`，前端展示"未生效（原因）"。
- pending 状态在规则卡片显示"等待设备就绪…"。

### 影响与风险

- 重载是全量重建 `_index`（volatile 原子替换），与事件发布无锁竞争问题；但重载瞬间新规则生效、旧规则失效，需确认**在途队列**（已入队未处理条目）不受影响（不受影响：队列独立于索引）。
- 去抖窗口需覆盖"设备批量注册"（启动场景），避免 N 台设备触发 N 次全量重建。

## 根因 D：绑定写入后静默窗口（回声抑制修正）

### 背景与关键事实

`RuntimeManager.WriteVariableAsync` 写入成功后**恒以 `Source = UserWrite` 发布事件**（`RuntimeManager.cs:929-938`），而 `OnVariableChanged` 只跳过 `Source == BindingWrite`（`VariableBindingEngine.cs:182`）。当前多跳 A→B→C 的传播**依赖**这条链：绑定写 B → 发布 UserWrite 事件 → 再次进入引擎 → 立即写 C。

**因此 Source 语义不做修正**——激活 `BindingWrite` 跳过会使多跳断链（评审 P0-1）。

### 问题本质

绑定写 B=X 后，B 的设备写入有生效延迟，回读时序为「先旧值 Y（未生效）→ 后新值 X（已生效）」。现有回声抑制仅当"回读值 == `LastBindingWriteValue`"才抑制，导致：

| 回读 | 现有判定 | 后果 |
|---|---|---|
| Y（≠X） | 非回声 → 发布 | 发布 Polling(B=Y) → 覆盖 C=Y（**旧值污染**） |
| X（==X） | 回声 → 抑制 | C 无法纠正回 X，**卡陈旧值** |

原 D1（值匹配 + 一次性消费）无法阻断"回读 Y 污染"（`ValueEquals(Y,X)=false` 时 `isEcho` 仍为 false），故整体废弃。

### D1 静默窗口（核心）

**改动点**：`VariableValueProcessor`（`ApplyPolledAsync` 与 `ApplySubscribedAsync` 两处回声判定）+ `VariableRuntime`（时间戳字段语义调整）

- 判定从"值匹配"改为**仅窗口判断**：绑定写 B 成功后，在窗口内（`now - LastBindingWriteTime <= echoWindowMs`）目标变量的**任何回读值（无论 X 还是 Y）一律不发布变化事件**（`IsChanged=false`），窗口过后恢复正常传播。
- 内存值照常更新（`vr.Value` 反映真实回读），仅抑制**事件发布**，不影响历史/实时/报警链路（与现有 `IsChanged=false` 语义一致）。
- `LastBindingWriteValue` 降级为观测/审计字段，**不再作为抑制的硬条件**。
- 窗口上限（评审 P2-3）：`echoWindowMs = min(max(PollingIntervalMs, 1000) * 2, 5000)` 或引入可配置上限，避免轮询间隔大时静默过久。

### 语义效果

- t1 回读 Y（窗口内）→ 静默，不污染 C ✓
- t2 回读 X（窗口内）→ 静默，不重复 ✓
- 窗口过后 B 真实变化 → 正常转发 ✓

### 权衡与取舍

- 窗口内若 B 被**外部真实源**在绑定写入后立即改为新值 Z，会被短暂静默（最长窗口时长）。该副作用远小于"多跳卡陈旧/断链"，首版接受；如需更精细，可后续升级为"窗口 + 首次命中期望值后提前结束静默"。
- 明确**不做** Source 语义修正（评审 P0-1），保留 `UserWrite` 传播机制。

### 影响与风险

- 单跳（目标无出边）：静默仅影响"回读不重复发布"，行为不变。
- 多跳：值最终一致、不再卡陈旧；下游传播仍由"绑定写入即触发"保证，**不依赖回读确认**，无额外延迟。
- 回归重点：单跳/多跳/一源多目标/多源一目标 + 写入生效延迟场景 + 窗口内外部真实变化取舍（见 03 文档阶段 4）。
