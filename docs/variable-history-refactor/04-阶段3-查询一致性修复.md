# 04-阶段3-查询一致性修复

> 解决问题：**P1-3**（MySQL 路径无聚合）、**P1-4**（导出上限矛盾）、**P2-7**（前端 2000 条限制）、**P2-9**（索引缺 DeviceKey）、**P3-15**（批量上限前后端不一致）
> 前置依赖：阶段 1（验证聚合行为需要 Influx 正常生效做对照）
> 粗估工作量：4~5 人日

---

## 1. 目标

1. MySQL 回退路径支持与 Influx 相同的聚合语义（mean/max/min/first/last + 窗口降采样）。
2. 导出上限真正达到 50000，且内存可控。
3. 前端"所有数据"取数上限提升到后端上限，明细分页基于完整数据集。
4. `VariableHistories` 索引覆盖 `(DeviceKey, VariableKey, Timestamp)` 查询模式。
5. 批量变量上限前后端对齐（前端 6 → 8，对齐后端 `MaxBatchVariables`）。

## 2. 现状与根因回顾

- `HistoryAppService.QuerySingleAsync` MySQL 分支调 `GetLatestAsync`，`aggregateWindowMs/aggregateFn` 被忽略；仓储无聚合方法。
- `MaxLimit=10000`（`HistoryAppService`）与 Controller 导出 50000、`InfluxStore.QueryLatestAsync` 内另一处 10000 clamp，三处不一致。
- 前端 `historyApi.ts` 硬编码 `limit ?? 2000`。
- 索引 `ix_variablehistory_key_timestamp (VariableKey, Timestamp)` 不含 DeviceKey。

## 3. 步骤明细

### 步骤 3.1 MySQL 聚合支持

**任务**：MySQL 路径实现窗口聚合，语义与 Flux `aggregateWindow(every, fn, createEmpty:false)` 对齐。

**涉及文件**：
- `Server/ScadaServer.Domain/Interfaces/Repositories/IEntityRepositories.cs`：`IVariableHistoryRepository` 接口定义所在（**该接口无独立文件**，与其它实体仓储接口共用此文件），在其中新增 `Task<List<VariableHistory>> GetAggregatedAsync(string deviceKey, string variableKey, DateTime? start, DateTime? end, long windowMs, string fn, int limit)`
- `Server/ScadaServer.Infrastructure/Repositories/VariableHistoryRepository.cs`：实现
- `Server/ScadaServer.Application/Services/HistoryAppService.cs`：`QuerySingleAsync` MySQL 分支接入

**SQL 设计**（MySQL 8，原生 SQL 参数化，避免 EF 表达式翻译限制）：
```sql
-- windowSec = windowMs / 1000（向上取整为整数秒；与 Flux every 精度差异可接受）
SELECT FROM_UNIXTIME(FLOOR(UNIX_TIMESTAMP(Timestamp) / {windowSec}) * {windowSec}) AS bucket,
       {AGG} AS Value
FROM VariableHistories
WHERE VariableKey = {variableKey}
  AND ({deviceKey} = '' OR DeviceKey = {deviceKey})   -- 或 C# 端拼两条分支
  AND Timestamp >= {start} AND Timestamp <= {end}
GROUP BY bucket
ORDER BY bucket DESC
LIMIT {limit}
```
- `{AGG}` 白名单映射：`mean→AVG(Value)`、`max→MAX(Value)`、`min→MIN(Value)`；
- **first/last**：窗口函数方案（值与时间戳都要）：
```sql
WITH b AS (SELECT ..., FLOOR(UNIX_TIMESTAMP(Timestamp)/{w})*{w} AS bucket,
           ROW_NUMBER() OVER (PARTITION BY bucket ORDER BY Timestamp ASC) AS rn   -- first；(DESC) 为 last
           FROM VariableHistories WHERE ...)
SELECT FROM_UNIXTIME(bucket) AS bucket, Value FROM b WHERE rn = 1 ORDER BY bucket DESC LIMIT {limit}
```
- 聚合函数名走白名单拼接（与 `NormalizeAggregateFn` 一致），其余参数全部 `FromSqlInterpolatedAsync` 参数化，杜绝注入。
- `RawValue/Quality` 在聚合行无意义：返回 null（DTO 端已可空）。

**AppService 接入**：
```
QuerySingleAsync MySQL 分支：
  if (aggregateWindowMs > 0) → records = GetAggregatedAsync(...)  → 升序返回
  else                       → 现状 GetLatestAsync(...)
```
- 返回 `Id=0`（聚合行无主键，与 Influx 分支一致）。

**注意事项**：
- 谓词禁止 `string.Equals(xx, StringComparison)`（EF/原生迁移工具约束）；deviceKey 为空时的跨设备聚合行为**保持与现状 GetLatestAsync 一致**（不限定设备，含同名变量混合）——现状如此，本阶段不改变语义，仅补聚合能力。
- `windowMs` 上限校验（如 ≤ 30 天）防异常大窗口除零/溢出（windowSec ≥ 1）。

### 步骤 3.2 导出与查询上限统一到 50000

**任务**：消除三处上限矛盾。

**涉及文件**：
- `Server/ScadaServer.Application/Services/HistoryAppService.cs`：`MaxLimit` 10000 → 50000
- `Server/ScadaServer.Infrastructure/Influx/InfluxStore.cs`：`QueryLatestAsync` 内 `limit > 10000 → 10000` clamp 同步改为 50000（与 AppService 常量保持一致——建议把上限常量收敛到一处，如 `IInfluxStore` 侧引用共享常量或各自同步注释）

**内存测算**（决策依据）：
- 单行 DTO ≈ 200 B（字符串字段引用），8 变量 × 50000 行 = 40 万行 ≈ 80 MB 峰值 + CSV `StringBuilder` ≈ 单行 60 B × 40 万 ≈ 24 MB。**总峰值 ≈ 100~120 MB，短期可接受但不宽裕**。
- **决策：本阶段直接统一为 50000**（一次性构建），验证清单中包含内存实测；若实测超预算或后续要支持更大导出，再做**流式导出**（`ExportCsvAsync` 改 `IAsyncEnumerable<HistoryRecordDto>` + Controller `File(stream)` 分批写）——列入 backlog，接口签名预留。

**配套**：导出响应头建议增加 `X-Total-Rows`（或保持现状，backlog）。

### 步骤 3.3 前端取数上限与明细分页

**任务**：前端利用提升后的后端上限。

**涉及文件**：
- `Client/src/api/historyApi.ts`：`fetchHistory`/`fetchHistoryBatch` 的 `limit` 保留参数但**默认值 2000 → 由调用方显式传入**（接口默认 100 不变，仅前端调用侧显式化）
- `Client/src/components/HistoricalQueryView.vue`：
  - 聚合模式：limit 维持较小值（聚合后行数本就少，2000 足够）；
  - **原始数据模式**：单变量传 10000、批量按 `10000 / 变量数` 下取整（避免总量爆内存），并在查询结果提示"已加载最近 N 条，更早数据请缩小时间范围、开启聚合或使用导出"；
  - 明细表格分页改为基于完整数据集的页码跳转（前端内存分页，无需后端改动）；
  - 统计条（最大/最小/平均）基于全量数据集计算。

**决策说明**：不做后端游标分页（改动大、现有场景"最近 N 条 + 聚合 + 导出"可覆盖），列 backlog。

### 步骤 3.4 索引优化

**任务**：索引匹配真实查询模式。

**涉及文件**：
- EF 迁移（`ScadaServer.Infrastructure/Persistence` 下新增迁移）：
  1. 新增 `ix_variablehistory_device_variable_timestamp (DeviceKey, VariableKey, Timestamp)`；
  2. （若阶段 2 未做）新增 `ix_variablehistory_timestamp (Timestamp)` 供清理；
  3. **保留** `ix_variablehistory_key_timestamp` 先不删（改名/删除需确认无其他依赖；本阶段仅新增，观察一个版本后在收尾阶段评估删除，避免锁表与回归风险）。
- `Server/ScadaServer.Infrastructure/Persistence/ScadaDbContext.cs`：实体配置同步。

**注意事项**：
- 新增索引在 MySQL 上为 **ONLINE DDL**（InnoDB 默认 `ALGORITHM=INPLACE, LOCK=NONE` 对二级索引适用），大表执行时间与表大小成正比，需在低峰执行迁移；迁移脚本中不强制 LOCK 子句。
- 迁移 Down 方法删除新索引即可回滚。
- 验证：`EXPLAIN SELECT ... WHERE DeviceKey=? AND VariableKey=? ORDER BY Timestamp DESC LIMIT ?` 走新索引。

### 步骤 3.5 批量变量上限前后端对齐（P3-15）

**任务**：前端多变量对比上限从 6 提到 8，对齐后端能力。

**涉及文件**：
- `Client/src/components/HistoricalQueryView.vue`：L26 `const MAX_SELECTED = 6` → `8`，同步注释（原注释标注 D2 决策，需更新为对齐后端 `MaxBatchVariables` 的说明）
- 相关 UI 文案（L702"最多 {{ MAX_SELECTED }} 条对比"）与校验提示（L144-145）引用常量，改常量即全部生效，无需逐处修改

**设计说明**：
- 选择 **前端放宽到 8**（而非后端收紧到 6）：后端 8 是批量接口与 CSV 导出的统一上限（两处 `Take(MaxBatchVariables)`），收紧后端是能力倒退；前端 6 是早期 UI 决策，无性能依据（8 变量 × 聚合模式数据量仍很小）。
- 批量模式下每变量 limit 按步骤 3.3 的 `10000 / 变量数` 下取整策略，8 变量时单变量 1250 条，内存可控。
- 后端 `MaxBatchVariables` 常量保持不变；建议后续若再调整上限，以控制器 XML 注释为准同步前端（约束分散问题在 backlog 的 API 契约统一中一并解决）。

**验收**：前端可选 8 个变量批量查询/导出成功；选第 9 个被拦截且提示"最多 8 条"。
