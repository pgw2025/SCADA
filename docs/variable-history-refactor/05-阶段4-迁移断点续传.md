# 05-阶段4-迁移断点续传

> 解决问题：**P2-6**（迁移无断点续传、无进度、中断后数据部分可见）
> 前置依赖：阶段 1（配置生效已自动化，迁移不再是 Influx 生效的唯一入口）
> 粗估工作量：3~4 人日

---

## 1. 目标

1. 迁移进度持久化：中断（失败/进程重启/主动取消）后可从断点续传，不再从 0 重来。
2. 迁移后台化：HTTP 请求即时返回，提供进度查询与取消接口；前端显示进度条。
3. 缓解"迁移中断期间数据部分可见"：查询页给出明确提示（完整合并查询列 backlog）。

## 2. 现状与根因回顾

`HistoryMigrationService.MigrateAsync()`：
- 从 `lastId=0` 全量扫描，任何一片 Influx 写入失败即 return（Message 指出中断 Id，但无恢复入口）；
- 进度仅存在于本次方法调用内（`migrated/total`），无持久化；
- `POST /api/scada/history/migrate` 同步等待整个迁移完成；前端干等；无取消；
- 进程重启后无任何"上次迁移到哪"的记忆；
- 查询语义"Influx 有数据即不回退 MySQL"导致迁移中断后旧数据界面不可见。

## 3. 步骤明细

### 步骤 4.1 迁移状态持久化

**任务**：记录迁移断点与状态。

**涉及文件**：
- `Server/ScadaServer.Domain/Entities/DatabaseConfig.cs`：新增可空字段
  - `MigrateLastId`（`long?`，默认 null）
  - `MigrateStatus`（`string?`，取值 `Running/Completed/Interrupted`，默认 null）
  - `MigrateUpdatedAt`（`DateTime?`，默认 null）
- EF 迁移（默认值 null，可回滚；遵守项目"新字段必须带默认值"约束——string 可空默认 NULL 即满足）

**设计决策**：状态放在生效的 Historical `DatabaseConfig` 行上（一配置一状态），不建独立表——迁移本质是该历史库配置的附属状态，且查询门禁（阶段 2 步骤 2.4 的"迁移未完成不清理"）也要读它。缺点是语义略混杂，接受。

**写入时机**：迁移主循环每完成一个 `ReadBatchSize`（2000 条）批后，更新 `MigrateLastId` + `MigrateUpdatedAt`（每 2000 条一次 UPDATE，写放大可忽略）。状态流转：
```
启动迁移   → MigrateStatus = Running
批循环推进 → MigrateLastId 更新
全部完成   → Completed（MigrateLastId = 最后 Id）
失败/取消/崩溃 → Interrupted（保留 LastId）
```
- 进程崩溃场景无法写入 Interrupted：**启动恢复逻辑**（步骤 4.2）发现 `Running` 但单例内无活动任务（`IsRunning()==false`）时，视为 Interrupted 并修正落库。

### 步骤 4.2 迁移后台化与进度/取消 API

**涉及文件**：
- `Server/ScadaServer.Infrastructure/Services/HistoryMigrationService.cs`：重构 `MigrateAsync`
- `Server/ScadaServer.Application/Interfaces/IHistoryMigrationService.cs`：接口扩展
- `Server/ScadaServer.WebApi/Controllers/HistoryController.cs`：端点调整
- `Client/src/components/DatabaseManagementView.vue` + `Client/src/api/`（或直接调用处）：进度条与取消

**接口设计**：
```
POST /api/scada/history/migrate          → 立即返回 { started: true } 或 { started: false, reason: "已有任务运行中" }
                                          （要求 InfluxStore.IsConfigured 或先 Rebuild 生效配置，复用阶段 1 逻辑）
GET  /api/scada/history/migrate/status    → {
        status: "Running|Completed|Interrupted|NeverStarted",
        migrated, total, lastId,
        startedAt, updatedAt,
        currentSpeedPerSec, etaSeconds,      // 由迁移服务滑动计算
        message
      }
POST /api/scada/history/migrate/cancel    → 请求取消（下一片边界生效），幂等
```

**实现要点**：
- `MigrateAsync` 拆为：`StartAsync()`（校验 `_lock.WaitAsync(0)`，占用后启动内部 `Task.Run` 包裹的 `ExecuteMigrationAsync`）+ 内存进度对象（`Interlocked` 更新 migrated/lastId，`CancellationTokenSource` 支持取消）。
- 循环改造：
  - 起点改为 `MigrateLastId ?? 0`（断点续传）；
  - `total` 计数（现状 `historyRepo.CountAsync()`，L83）**保留全表 COUNT 一次**（InnoDB 大表 COUNT 慢但仅启动时执行一次；若实测不可接受，可改 `EXPLAIN` 估算行数或复用上次落库的 total，列入 backlog，不阻塞本阶段）；
  - 每片写入成功后 `token.ThrowIfCancellationRequested()` 检查（取消在片边界生效，保证已写数据一致）；
  - 每批结束更新落库断点（步骤 4.1）+ 内存进度 + 速度/ETA；
  - Influx 写失败：不直接 return，改为**有限重试**（3 次，间隔 2s，复用阶段 2 的退避思路），仍失败 → 状态 Interrupted + 保留断点 + 返回错误消息（下次触发从断点继续）。
- **幂等性**：Influx 相同 series+timestamp(ns) 覆盖写，断点重传即使有重叠批次（LastId 之后边界取开区间 `Id > lastId`，实际无重叠）也安全。
- 兼容：`POST /history/migrate` 的旧响应字段 `IsRunning/Migrated/Total/Message` 保留在新响应中映射，避免前端既有判断破坏。

### 步骤 4.3 前端迁移进度 UI

**涉及文件**：`Client/src/components/DatabaseManagementView.vue`（现 `doMigrate` 调用处）

**设计**：
- 点击迁移 → 调 `POST /migrate` → 立即转入"迁移中"状态；
- 5 秒轮询 `GET /migrate/status`：进度条（migrated/total）、速度、ETA、当前状态徽标；
- 「取消」按钮 → `POST /migrate/cancel` → 等待状态变 Interrupted；
- 状态为 Interrupted 时按钮文案变"从断点继续迁移（已完成 N 条）"；
- Completed 显示成功摘要；离开页面停止轮询（onUnmounted 清理）。

### 步骤 4.4 "部分可见"缓解与清理门禁

**任务 A：查询页提示**。
- `Client/src/components/HistoricalQueryView.vue`：进入/查询时调 `GET /migrate/status`，非 Completed 且 `migrated>0` 时顶部提示条："历史数据迁移中（N/Total），当前仅显示已迁移部分，完成后自动恢复完整历史"。
- **不做查询合并**（Influx 结果 ∪ MySQL `Id > MigrateLastId`）：实现复杂（排序、去重、聚合窗口跨界），列为 backlog；提示条已把"数据变少"从静默变为显式。

**任务 B：清理门禁**（回填阶段 2 的 TODO）。
- `VariableHistoryCleanupHostedService` 执行前读取生效配置的 `MigrateStatus`：`Running/Interrupted` 时跳过本次清理并 LogWarning"存在未完成迁移，跳过 MySQL 历史清理"。

**任务 C：运维顺序文档化**（写入本目录 README 或运维手册）：
```
启用 InfluxDB 的推荐顺序：
1. 配置并激活 InfluxDB 历史库（阶段 1 后即时生效，新数据双轨?否——生效后仅写 Influx）
2. 触发迁移，等待 Completed（可断点续传）
3. 验证历史查询完整后，再开启 MySQL 保留期清理（History:MySqlRetentionDays）
```

## 5. 本阶段验证清单

- [ ] 正常迁移：进度条推进、ETA 合理、Completed 后断点字段 = 最后 Id
- [ ] 中断续传：迁移中途 kill 服务 → 重启后 status=Interrupted（自动修正）→ 再次触发从 LastId 继续，最终数据完整（总数与 MySQL 对账）
- [ ] 写失败续传：停止 Influx 触发中断 → 启动 Influx → 续传完成
- [ ] 取消：点击取消后 ≤ 1 个片周期内停止，状态 Interrupted，断点保留
- [ ] 并发防护：迁移中重复 POST /migrate 返回 started=false；取消接口幂等
- [ ] 迁移期间查询页显示提示条；Completed 后提示消失
- [ ] MigrateStatus=Running/Interrupted 时 MySQL 清理被跳过并告警
- [ ] 旧响应字段兼容（IsRunning/Migrated/Total/Message 仍存在）

## 6. 风险与回滚

| 风险 | 缓解 |
|---|---|
| 断点字段与实际进度不一致（崩溃在 UPDATE 前） | Influx 覆盖写幂等 + `Id > LastId` 开区间，最多重传极少重叠，无害 |
| 后台任务异常无人感知 | 进度对象记录 message；status 轮询可见；服务内 catch-all 落 Interrupted |
| Running 状态僵尸（崩溃后未修正） | 启动恢复逻辑修正；status 接口读取时二次校验（`IsRunning()==false && status==Running` → 按 Interrupted 呈现） |
| 回滚 | 新字段可空默认 NULL，EF Down 删列；后台化接口新增端点不影响旧端点；回滚后恢复同步迁移旧行为（从 0 全量） |
