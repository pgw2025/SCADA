# 02-阶段1-配置生效链路修复

> 解决问题：**P1-1**（InfluxDB 配置不自动生效，重启后回退 MySQL）
> 前置依赖：无（本阶段是阶段 3/4 验证的前提）
> 粗估工作量：2~3 人日

---

## 1. 目标

1. 服务启动时自动恢复生效的 InfluxDB 历史库配置（`DatabaseConfigs` 中 Type=Historical 且 IsActive 的记录）。
2. 配置的保存/激活/删除在运行期即时联动 `InfluxStore`，无需手动触发迁移。
3. 当前生效后端对用户可见（API + 前端展示），消除"以为在用 Influx 实际在用 MySQL"。

## 2. 现状与根因回顾

- `InfluxStore.Rebuild(DatabaseConfig config)` 全项目唯一调用点：`HistoryMigrationService.MigrateAsync()`（注释自述"同时修复运行期客户端未被初始化的问题"——说明作者已知此缺口，只是未做独立修复）。
- `DatabaseConfigAppService` 的 `CreateAsync/UpdateAsync/DeleteAsync` 均不触碰 `IInfluxStore`。
- 启动链路（`Program.cs` → DI → 各 HostedService）无人加载历史库配置。

## 3. 步骤明细

### 步骤 1.1 新增 `HistoryStoreInitializer` 托管服务（启动恢复）

**任务**：服务启动时把生效配置灌入 `InfluxStore`。

**涉及文件**：
- 新建 `Server/ScadaServer.WebApi/HostedServices/HistoryStoreInitializer.cs`
- 修改 `Server/ScadaServer.WebApi/Extensions/Application.Extensions.cs`（**已核实**：`HistoryRecorder` 的单例 + `IHistoryRecorder` + `AddHostedService` 三连注册在此文件 L78-80，新服务紧随其后注册）

**设计**：
- 实现 `BackgroundService`（仿 `SystemLogCleanupHostedService` 的骨架）：
  1. `ExecuteAsync` 中先 `await _dbReady.WaitAsync(token)`（`DatabaseInitializationStatus`，与 `HistoryRecorder` 同一协调机制），失败则记日志退出（回退 MySQL 模式，不阻塞启动）；
  2. 通过 `IServiceScopeFactory` 解析 `IDatabaseConfigRepository`，复用 `HistoryMigrationService.ResolveActiveInfluxConfigAsync` 的筛选逻辑（Type=Historical、BackendType=InfluxDB、IsActive；注意谓词用 `==`，在内存中用 `FirstOrDefault` 过滤，与现状一致即可）；
  3. 找到则 `_influxStore.Rebuild(config)`，未找到则记一条 Information（"未配置生效的 InfluxDB 历史库，历史数据落 MySQL"）。
- **注册顺序**：放在 `HistoryRecorder` 注册之前，尽早生效。即使晚于 HistoryRecorder 首批 flush，最多前几批写 MySQL（本就是回退目标），无害。

**注意事项**：
- `Rebuild` 失败（如网络不通）时 `IsConfigured` 仍可能为 true（客户端构造成功、连接失败在写入时才暴露）。启动时可选做一次 `PingAsync` 并将结果写入 `DatabaseConfig.LastStatus/LastCheckedAt`（字段已存在），失败仅告警不回滚。

**验收**：重启服务后 `IsConfigured=true`，无需任何手动操作。

### 步骤 1.2 配置变更联动（运行期生效）

**任务**：`DatabaseConfigAppService` 的写路径联动 `InfluxStore`。

**涉及文件**：
- `Server/ScadaServer.Application/Services/DatabaseConfigAppService.cs`（`UpdateAsync`/`CreateAsync`/`DeleteAsync`）
- `Server/ScadaServer.Application/Interfaces/IInfluxStore.cs`（需新增方法，见下）
- `Server/ScadaServer.Infrastructure/Influx/InfluxStore.cs`（实现新方法）

**设计**：
- **新增 `IInfluxStore.Reset()` 接口方法**：将当前 holder 置空并 MarkRetired（复用 `Dispose()` 的内部逻辑但不设 `_disposed`），使"取消生效/删除配置"能立即回到 MySQL 模式。现有 `Rebuild(null)` 是空操作，无法表达"停用"——这是必须补的接口。
- `UpdateAsync`：
  - 若该记录 `Type == "Historical" && BackendType == "InfluxDB" && IsActive`：保存成功后调用 `Rebuild(updatedEntity)`；Rebuild 后 `IsConfigured == false`（如缺 Bucket）时在响应/日志中给出"配置已保存但 Influx 客户端初始化失败"的明确提示（LastStatus=Failed）。
  - 若该记录原本是生效历史库、更新后 `IsActive` 变为 false 或 BackendType 改变：调用 `Reset()`。
  - 同 Type 仅一条 IsActive 的约束维护逻辑（若 `UpdateAsync` 已处理激活互斥，需在互斥切换处同步 Rebuild/Reset 两条路径）。
- `CreateAsync`：创建即为生效历史库配置时 `Rebuild`（若现有语义允许创建即激活）。
- `DeleteAsync`：删除的是当前生效历史库时 `Reset()`。
- **依赖方向确认**：`IInfluxStore` 定义于 `ScadaServer.Application.Interfaces`（`HistoryAppService` 已注入），Application 层引用无障碍。

**设计决策**：
- 保存前是否强制连接测试？**决策：不强制**（保持现状"可先保存后修网络"），但 `UpdateAsync` 返回体或日志中携带 Rebuild 结果。若后续希望严格，可加"激活前必须测试连接通过"开关，列入 backlog。
- 判定 Type 的字符串比较使用 `==` / `string.Equals(x, y, StringComparison.OrdinalIgnoreCase)` 均可（内存比较，非 EF 谓词），沿用 `HistoryMigrationService` 现有写法保持一致。

### 步骤 1.3 生效状态可见性（API）

**任务**：暴露当前历史库生效状态。

**涉及文件**：
- `Server/ScadaServer.WebApi/Controllers/HistoryController.cs`（新增端点）
- `Server/ScadaServer.Application/Interfaces/IHistoryAppService.cs` + `HistoryAppService.cs`（或直接在 Controller 注入 `IInfluxStore` + `IDatabaseConfigAppService` 组装，推荐前者保持分层）

**设计**：`GET /api/scada/history/status`（无需管理员权限，与查询权限一致），返回：
```json
{
  "backend": "InfluxDB | MySQL",
  "influxConfigured": true,
  "influx": { "name": "...", "url": "...", "bucket": "...", "org": "...", "lastStatus": "Ok" },
  "writePath": { "queueDepth": 0, "droppedCount": 0 }
}
```
- `backend` = `IsConfigured ? "InfluxDB" : "MySQL"`；
- `writePath` 字段依赖阶段 2 的指标（本阶段先返回占位 0，或本阶段仅返回前半部分，阶段 2 补全——推荐后者，避免接口字段变更）。
- 阶段 2 会在 `HistoryRecorder` 上暴露统计，本端点预留合并位置。

**注意**：Token/Password 等敏感字段不得出现在响应中（只回 Name/Host/Port/Bucket/Org/LastStatus）。

### 步骤 1.4 前端展示生效状态

**涉及文件**：
- `Client/src/api/historyApi.ts`：新增 `fetchHistoryStatus()`
- `Client/src/components/DatabaseManagementView.vue`：历史库配置区顶部显示"当前生效后端：InfluxDB（bucket/名称）或 MySQL（未启用时序库）"徽标。
- `Client/src/components/HistoricalQueryView.vue`（可选，本阶段轻量）：查询结果区角落标注数据来源（依赖 status 接口）。

### 步骤 1.5 单元测试

**涉及文件**：`Server/ScadaServer.WebApi.Tests`（或项目既有测试工程）新增用例。

用例清单：
1. `HistoryStoreInitializer`：有生效配置 → Rebuild 被调用；无生效配置 → 不调用且不抛错；DB 未就绪 → 退出不阻塞。
2. `DatabaseConfigAppService.UpdateAsync`：更新生效历史库 → Rebuild(新配置)；停用 → Reset；删除生效配置 → Reset；更新非 Historical 配置 → 不触碰 InfluxStore。
3. `InfluxStore.Reset()`：调用后 `IsConfigured=false`，进行中的请求不受影响（引用计数保护，可仅测状态位）。

## 4. 本阶段验证清单

- [ ] 配置生效的 InfluxDB → 重启服务 → `GET /api/scada/history/status` 返回 `backend=InfluxDB`，无需手动迁移
- [ ] 修改生效配置的 Bucket（指向错误值）→ 保存 → status 立即反映（或 LastStatus=Failed）
- [ ] 停用/删除生效配置 → status 返回 `MySQL`，写入落 MySQL
- [ ] 无任何生效配置 → 启动日志出现"历史数据落 MySQL"提示，服务正常启动
- [ ] 迁移接口 `POST /api/scada/history/migrate` 行为不变（阶段 1 不改动其语义；其内部 Rebuild 调用保留，幂等无害）
- [ ] 前端库管理页显示当前生效后端徽标

## 5. 风险与回滚

| 风险 | 缓解 |
|---|---|
| 启动时 DB 不可用导致初始化失败 | 初始化失败仅告警、回退 MySQL，不阻塞启动（与现状一致） |
| 配置错误（如 Bucket 空）在运行期被激活 | Rebuild 内已有缺 Bucket 保护（返回未配置 + 日志），再加 LastStatus 标记 |
| 回滚 | 纯行为修复无 DB 变更；回滚代码即回到旧行为（手动迁移触发生效） |
