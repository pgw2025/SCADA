# 01-现状问题清单

> 审查日期：2026-09-12。本清单为阶段方案的问题依据，所有结论均基于当前代码逐行核对。

---

## 0. 功能现状速览

```
采集（DeviceWorker 轮询 / MQTT 订阅）
   │  VariableValueProcessor.TryRecordHistory（StoreMode 判定：None/Change/Cycle，
   │  周期到期或变化超死区时数值化并入队；质量降级不写历史）
   ▼
HistoryRecorder（单例 HostedService）
   │  Channel 容量 20000（DropWrite），满 100 条或 500ms 刷一批
   ├─ InfluxDB（InfluxStore.WriteAsync，失败重试 3 次：1s/2s/3s）
   └─ 回退 MySQL（VariableHistories.AddRange + SaveChangesAsync，失败直接丢弃）
   ▼
查询（HistoryController → HistoryAppService.QuerySingleAsync）
   ├─ InfluxDB（QueryLatestAsync，支持 aggregateWindow 降采样 mean/max/min/first/last）
   └─ Influx 无数据/未配置 → MySQL（GetLatestAsync，仅倒序取最近 N 条，无聚合）

配置：DatabaseConfigs 表（Type=Historical, BackendType=InfluxDB, IsActive）
迁移：HistoryMigrationService.MigrateAsync（MySQL 按 Id 升序 2000/批 → Influx 500/片）
清理：ClearHistoryTaskExecutor（仅 Influx DeleteBeforeAsync）
备份：BackupTaskExecutor（Influx ExportAllAsync 全量 CSV + MySQL 业务表 JSON）
```

---

## P1-1 InfluxDB 配置不会自动生效，重启后回退 MySQL（严重）

- **现象**：配置并激活 InfluxDB 历史库后，数据仍写 MySQL；手动点一次"迁移"后才切换；服务重启后又回到未配置状态。
- **根因**：`InfluxStore.Rebuild(DatabaseConfig)` 的全项目唯一调用点在 `HistoryMigrationService.MigrateAsync()`（`Infrastructure/Services/HistoryMigrationService.cs` L74）。启动流程（`Program.cs`、各 HostedService）不加载 `DatabaseConfigs`；`DatabaseConfigAppService.CreateAsync/UpdateAsync/DeleteAsync` 保存/激活/删除配置后均不联动 Rebuild。
- **影响**：`InfluxStore.IsConfigured` 在重启后为 false，写入与查询都静默回退 MySQL，用户无感知。
- **修复阶段**：阶段 1。

## P1-2 落库失败静默丢弃，无补偿（严重）

- **现象**：Influx 抖动或 MySQL 故障时采样点丢失，运行期不可感知。
- **根因**：`HistoryRecorder.FlushAsync`（`WebApi/HostedServices/HistoryRecorder.cs` L209-249）：
  - Influx 写失败（重试 3 次后）回退 MySQL；
  - MySQL 写入异常 catch 后仅 LogWarning（"历史记录批量写入失败（丢弃 N 条）"），**不重试**；
  - 队列满 `DropWrite` 丢弃并 `_droppedCount` 计数，但该计数仅在停止时输出一条汇总日志；
  - 无任何运行期指标接口。
- **影响**：高频采样（<1s）或 Influx 抖动期间数据不可追溯丢失。
- **修复阶段**：阶段 2。

## P1-3 MySQL 回退路径不支持聚合，UI 与结果不一致（严重）

- **现象**：未配置 InfluxDB 时，历史查询页选择聚合粒度（如 1 分钟均值），返回的仍是最近 N 条原始点。
- **根因**：`HistoryAppService.QuerySingleAsync`（`Application/Services/HistoryAppService.cs` L124-169）MySQL 分支调用 `_repository.GetLatestAsync(...)` 不接收 `aggregateWindowMs/aggregateFn`；`VariableHistoryRepository` 亦无聚合方法。聚合降采样仅在 Influx 分支的 Flux `aggregateWindow` 中生效。
- **影响**：曲线形态、统计条（最大/最小/平均）与所选聚合粒度不符，且无提示。
- **修复阶段**：阶段 3。

## P1-4 导出行数上限自相矛盾（严重）

- **现象**：CSV 导出声称上限 50000，实际每变量最多 10000 行，静默截断。
- **根因**：`HistoryController.ExportHistory`（`WebApi/Controllers/HistoryController.cs` L69-105）允许 `limit` 上限 50000，并传给 `ExportCsvAsync`；但 `QuerySingleAsync` 内 `MaxLimit = 10000`（`HistoryAppService.cs` L17、L134）把 limit clamp 到 10000。`InfluxStore.QueryLatestAsync` 内还有一处独立的 `limit > 10000 → 10000` clamp（`InfluxStore.cs` L247-250）。
- **修复阶段**：阶段 3。

## P2-5 MySQL 历史数据无保留期清理，表无限增长（中等）

- **根因**：
  - `ClearHistoryTaskExecutor`（`Runtime/Tasks/ClearHistoryTaskExecutor.cs`）只调 `_influxStore.DeleteBeforeAsync`，且未配置 Influx 时 `DeleteBeforeAsync` 返回失败 → 任务直接抛 `InvalidOperationException`（执行失败）；
  - 对照 `SystemLogs`/`AlarmRecords`/`ScriptExecutionRecords` 均有对应 CleanupHostedService（每天 3 点分批删除），`VariableHistories` 没有任何清理机制；
  - `VariableHistory` 表仅有 `(VariableKey, Timestamp)` 索引，无 Timestamp 单列索引，按时间 DELETE 走全表扫描。
- **修复阶段**：阶段 2。

## P2-6 迁移无断点续传；中断后数据部分可见（中等）

- **根因**：`HistoryMigrationService.MigrateAsync()`（`Infrastructure/Services/HistoryMigrationService.cs`）：
  - 迁移从 `lastId=0` 全量重来，无进度持久化；某片写失败即中断并返回，无恢复手段（只能整个重来）；
  - 查询语义是"Influx 有数据即返回，不回退 MySQL"（`QuerySingleAsync` L139-149），迁移中断后 Influx 只有部分数据，**MySQL 中未迁移的旧数据在界面"消失"**；
  - 迁移在 HTTP 请求内同步执行（`POST /api/scada/history/migrate` 等待完成），大库易超时；前端 `DatabaseManagementView.doMigrate` 干等无进度；无取消手段。
- **修复阶段**：阶段 4。

## P2-7 前端"所有数据"最多 2000 条（中等）

- **根因**：`Client/src/api/historyApi.ts` 中单变量（L66）与批量（L98）查询均硬编码 `limit: params.limit ?? 2000`，后端上限 10000；明细表格分页仅上一页/下一页，无法翻到更早数据；统计条基于这 2000 条计算。
- **修复阶段**：阶段 3。

## P2-8 运行时趋势图无历史回填（中等）

- **根因**：`TrendChartWidget` 只消费 `Client/src/utils/trendHistory.ts` 的内存滚动缓冲（约 120 点），页面刷新/画面切换后曲线从零开始；与后端历史查询 API 完全不打通。
- **修复阶段**：阶段 5。

## P2-9 索引缺少 DeviceKey，跨设备同名变量查询放大（中等）

- **根因**：`VariableHistories` 索引 `ix_variablehistory_key_timestamp (VariableKey, Timestamp)`（`ScadaDbContext`）。查询先按 `VariableKey` 等值扫描，再对 `DeviceKey` 残留过滤。多设备共用变量键名时扫描行数按设备数放大。
- **修复阶段**：阶段 3。

## P3-10 前端查询失败静默清空（轻微）

- **根因**：`HistoricalQueryView.executeHistoryQuery` 的 catch 只清空序列，图表显示"未查询到任何时序"空态，通讯失败与真实无数据不可区分。
- **修复阶段**：阶段 5。

## P3-11 "所有数据"依赖显式 2000-01-01 起点（轻微）

- **根因**：`InfluxStore.BuildQuery` 在 `start` 为空时使用 Flux 默认 `range(start: -30d)`（L777-780）。前端已用显式 `2000-01-01` 规避；任何直接调 API 的第三方/调试场景可能意外只拿到 30 天。隐式行为未文档化。
- **修复阶段**：阶段 5。

## P3-12 历史只记录 Good 质量值（轻微）

- **根因**：`VariableValueProcessor` 质量降级（Bad/CommunicationError）路径直接 return 不写历史，`Quality` 字段实际几乎恒为 Good；通讯中断在曲线上表现为缺口（靠前端"中位间隔 ×2"猜测断线），而非带质量标记的点。
- **修复阶段**：阶段 5（可选项，默认保持现状，见该文档决策）。

## P3-13 CSV 导出转义不完整（轻微）

- **根因**：`HistoryAppService.EscapeCsv`（L171-176）只处理双引号翻倍；未处理换行符/制表符；`DeviceKey/VariableKey/Quality` 列直接包引号但未转义内部引号（L108-113）；`Value` 列不包裹，NaN/Infinity 原样输出。变量名含换行时 CSV 行结构被破坏。
- **修复阶段**：阶段 5。

## P3-14 备份 Influx 全量导出无分片（轻微）

- **根因**：`InfluxStore.ExportAllAsync`（L543-646）用 `range(start: 0)` 一次性 `QueryRawAsync` 拉全量 CSV 并整体写文件；大库时内存/超时风险高；Influx 未配置时 `InfluxExported=false`，而 MySQL 历史表又在备份排除清单中——历史数据完全不进备份且无告警。
- **修复阶段**：阶段 5。

## P3-15 批量变量上限前后端不一致（轻微）

- **现象**：历史查询页多变量对比上限 6 条，后端批量接口与 CSV 导出实际支持 8 条（`MaxBatchVariables = 8`）。
- **根因**：前端 `HistoricalQueryView.vue` L26 `const MAX_SELECTED = 6`（注释标注 D2 决策），与后端 `HistoryAppService` L14 `MaxBatchVariables = 8` 各自维护、未对齐。导出走 `POST /history/export` 时同样受后端 8 上限约束，前端 6 只是人为收紧。
- **影响**：能力浪费（后端支持 8 前端只给 6）且约束分散，后续调整需两处同步，易再漂移。
- **修复阶段**：阶段 3（随步骤 3.3 前端取数改造一并处理）。

## P3-16 NaN/Infinity 值导致 Influx 整批写入失败抖动（轻微）

- **现象**：脚本/表达式计算产生 NaN 或 Infinity（如除零）时，该采样点所在**整批** Influx 写入失败回退 MySQL，造成写入路径抖动与统计口径漂移（正常值批次落 Influx、异常值批次落 MySQL）。
- **根因**：InfluxDB 行协议不支持 NaN/Inf field 值；`HistoryRecorder.FlushAsync` 的 Influx 分支不做值预检，批次中只要混入一个非法值，整批 `WriteAsync` 报错 → 触发重试 → 穷尽后整批回退 MySQL（MySQL `double` 列可存 NaN/Inf，能落库）。查询侧 Influx 有数据即不回退，导致 NaN 点所在时间段在"Influx 有部分数据"时不可见。
- **影响**：低频但确定性发生（取决于脚本质量）；每发生一次，最多 100 条正常采样点被连累改走 MySQL。
- **修复阶段**：阶段 2（随写入可靠性改造一并处理）。

## P3-17 历史库与主库配置机制割裂（轻微，文档性）

- **现象**：主库连接走 `appsettings` / `dboverride.json`，重启生效；历史库（InfluxDB）走 `DatabaseConfigs` 表 + 界面管理。两套机制并存，运维心智负担。
- **根因**：历史演进形成——主库是启动必需依赖（EF DbContext），历史库是运行期可选后端。
- **修复阶段**：不单独开发。阶段 1 落地后（历史库配置保存/重启即生效），两套机制的"生效语义"差异已消除大半；完整的统一（主库也进 `DatabaseConfigs` 表热切换）列 backlog（涉及启动依赖重构，收益/成本比低）。

## 附：审查中确认无误（无需改动）的部分

- `InfluxStore` 的线程安全设计（引用计数 ClientHolder、Volatile/Interlocked）严谨，Rebuild/Dispose 竞争处理正确；
- `HistoryRecorder` 的生命周期处理（优雅停止、停止前排空、超时兜底）正确；
- Influx 行协议设计（低基数 tag、series 身份 = device_key + variable_key）合理；
- 写入路径等待 `DatabaseInitializationStatus`，避免迁移未完成时写缺失表；
- MySQL 迁移按主键升序 2000/批 + Influx 500/片的分片策略合理（缺的只是进度与续传）。
