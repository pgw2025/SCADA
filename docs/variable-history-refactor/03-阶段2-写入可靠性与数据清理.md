# 03-阶段2-写入可靠性与数据清理

> 解决问题：**P1-2**（落库失败静默丢弃）、**P2-5**（MySQL 无保留期清理）、**P3-16**（NaN/Infinity 整批回退抖动）
> 前置依赖：无（与阶段 1 无代码耦合，可并行）
> 粗估工作量：3~4 人日

---

## 1. 目标

1. MySQL 回退写入具备重试能力（指数退避），重试仍失败的批次进入补偿队列而非直接丢弃。
2. 丢弃（队列满/双后端失败）通过运行期指标接口可感知。
3. `VariableHistories` 表具备保留期自动清理（默认关闭），且清理任务支持双后端。
4. NaN/Infinity 采样点不再连累整批 Influx 写入失败，消除写入路径抖动（P3-16）。

## 2. 现状与根因回顾

- `HistoryRecorder.FlushAsync`：MySQL 写入异常 → catch → LogWarning"丢弃 N 条"，不重试；队列满 DropWrite 只累计 `_droppedCount`，仅停止时汇总输出。
- `VariableHistories` 无任何清理服务（对照 SystemLogs/AlarmRecords/ScriptExecutionRecords 均有）；`ClearHistoryTaskExecutor` 只清 Influx，未配置 Influx 时抛错。
- 清理相关索引缺失：按 `Timestamp` 删除无单列索引。

## 3. 步骤明细

### 步骤 2.1 MySQL 回退写入重试

**任务**：`FlushAsync` 的 MySQL 分支加指数退避重试。

**涉及文件**：`Server/ScadaServer.WebApi/HostedServices/HistoryRecorder.cs`

**设计**（对齐项目已有的数据转换写入重试模式 500ms/1s/2s）：
```
尝试 1：AddRange + SaveChangesAsync
失败 → Delay 500ms → 尝试 2（重新 CreateScope 取新 DbContext，实体已脱钩需重新 Add；或整批重建）
失败 → Delay 1s    → 尝试 3
失败 → Delay 2s    → 尝试 4
仍失败 → 批次进入步骤 2.2 的补偿队列
```
- 重试间使用 `token`（服务停止时中断重试直接进入补偿路径）。
- 注意：EF `DbContext` 基础设施异常（连接断开）时复用同一 scope 重试无意义，**每次重试重新 `CreateScope` + `AddRange`**。
- 停止排空路径（`StopAsync` 触发的最后一次 Flush）中重试时间要受 `WaitAsync(30s)` 总超时约束，超时则转补偿队列并记日志。

**验收**：模拟 MySQL 短暂不可用（重启 MySQL）期间产生的批次在恢复后自动落库。

### 步骤 2.2 失败批次补偿队列

**任务**：双后端均失败的批次保留在内存重试队列，周期性重放。

**涉及文件**：`Server/ScadaServer.WebApi/HostedServices/HistoryRecorder.cs`

**设计**：
- 新增字段 `List<VariableHistory> _retryBuffer`（上限 50000 条，约 200KB×N 量级，内存可控）+ 溢出计数 `_overflowDroppedCount`。
- `FlushAsync` 末路（MySQL 重试穷尽）→ 若 buffer 未满则并入，否则丢弃并计数（此时才真正丢弃）。
- 重放策略：`ProcessAsync` 主循环空闲窗口（每次 FlushInterval tick）检查 buffer 非空 → 取一批（FlushBatchSize）按原优先级重放（Influx 优先）。重放成功即出队；仍失败留待下轮，连续失败达 10 轮后放弃该批并计数（防毒丸批次永久占用）。
- **幂等性说明**：
  - Influx：相同 measurement+tags+timestamp(ns) 写入为覆盖，天然幂等；
  - MySQL：无唯一索引，重放可能产生重复行。**决策：容忍重复**（同批次重放重复概率低、统计影响小），避免引入唯一索引（存量重复数据会使加索引失败）。文档与响应中说明该语义。
- 服务停止时 buffer 不落盘（进程级内存补偿，不追求重启后恢复；文件级死信队列列入 backlog）。

### 步骤 2.3 写入指标暴露

**任务**：运行期可观测。

**涉及文件**：
- `Server/ScadaServer.WebApi/HostedServices/HistoryRecorder.cs`：`IHistoryRecorder` 接口新增 `HistoryRecorderStats GetStats()`（或独立接口 `IHistoryRecorderStats`，避免污染采集端依赖——推荐后者，仅 WebApi/查询侧依赖）。
- `Server/ScadaServer.WebApi/Controllers/HistoryController.cs`：`GET /api/scada/history/stats`，`[Authorize(Policy = "RequireAdmin")]`，合并阶段 1 的 status 端点或并列（推荐并入 status，`writePath` 字段补全）。

**指标项**：
```json
{
  "writePath": {
    "queueDepth": 0,            // Channel 剩余
    "enqueuedTotal": 123456,    // 累计入队
    "droppedQueueFull": 0,      // 队列满丢弃
    "droppedAllBackendFailed": 0, // 双后端重试穷尽且补偿溢出丢弃
    "invalidValuePoints": 0,    // NaN/Infinity 分流计数（改道 MySQL，非丢弃；步骤 2.6）
    "influxWriteBatches": 1200, "influxWriteFailedBatches": 3,
    "mysqlWriteBatches": 12,   "mysqlRetriedBatches": 5,
    "retryBufferDepth": 0,
    "lastFlushAt": "2026-09-12T03:00:00Z",
    "lastWriteSucceededAt": "..."
  }
}
```
- 全部 `Interlocked` 计数，读取零锁。

**验收**：人为停 Influx + MySQL 数秒 → stats 中 `mysqlRetriedBatches`/`retryBufferDepth` 上升，恢复后归零、无 `droppedAllBackendFailed`。

### 步骤 2.4 MySQL 历史数据保留期清理

**任务**：新增 `VariableHistoryCleanupHostedService`。

**涉及文件**：
- 新建 `Server/ScadaServer.WebApi/HostedServices/VariableHistoryCleanupHostedService.cs`（仿 `SystemLogCleanupHostedService`）
- 新建 `Server/ScadaServer.Application/Options/HistoryRetentionOptions.cs`：`History:MySqlRetentionDays`（默认 **0 = 不启用**，保证升级无副作用）
- `Server/ScadaServer.WebApi` DI 注册 + appsettings 默认段
- EF 迁移：`VariableHistories` 新增 **`ix_variablehistory_timestamp (Timestamp)` 单列索引**（清理谓词走索引；与阶段 3 的索引调整合并为一次迁移亦可，见阶段 3 步骤 3.4——若两阶段同期实施，迁移只做一次）

**设计**：
- 触发：每天本地 3:00（与其他清理服务错峰可改为 3:30），小时轮询"当天未执行"模式照抄现有实现。
- 删除：`DELETE FROM VariableHistories WHERE Timestamp < {cutoff} ORDER BY Id LIMIT 2000` 循环 + 批间 200ms（`ExecuteSqlInterpolatedAsync` 参数化，与 `SystemLogCleanupHostedService.CleanupAsync` 完全同构）。
- cutoff 用 `DateTime.UtcNow.AddDays(-days)`，与写入侧 UTC 一致。
- **运维顺序强约束（写入文档与日志）**：若用户计划"MySQL 迁移到 Influx 后清理 MySQL"，必须先完成迁移（阶段 4 的断点续传完成后）再开启本配置，否则未迁移数据被清掉。清理执行前若存在未完成的迁移状态（阶段 4 的 `MigrateStatus=Running/Interrupted`），**跳过本次清理并告警**（此校验在阶段 4 落地后补上，本阶段先记录 TODO）。

**验收**：造 3 天前旧数据，配置 `MySqlRetentionDays=2` → 手动触发（或等窗口）后旧数据清除、新数据保留、清理日志记录条数。

### 步骤 2.5 清理计划任务双后端

**任务**：`ClearHistoryTaskExecutor` 在未配置 Influx 时不再失败，转而清理 MySQL。

**涉及文件**：
- `Server/ScadaServer.Runtime/Tasks/ClearHistoryTaskExecutor.cs`
- Application 层暴露清理能力：`IHistoryAppService`（或新建 `IHistoryMaintenanceAppService`，推荐后者语义清晰）新增 `Task<(bool, string)> CleanupMySqlBeforeAsync(DateTime cutoffUtc)` → Infrastructure 实现（复用步骤 2.4 的分批删除循环，抽公共方法）。

**设计**：
```
ExecuteAsync:
  if (_influxStore.IsConfigured) → 清 Influx（现状）
      → 若同时希望清 MySQL：按 ParamsJson 可选参数 mysqlAlso=true 双清

```
- `retentionDays` 参数语义与校验保持不变（≥1）。
- 注意 Runtime → Application 的引用方向已存在（现有 executor 已注入 Application 层接口）。

### 步骤 2.6 NaN/Infinity 采样点分流（P3-16）

**任务**：Influx 写入前剥离非法浮点值，避免整批失败回退。

**涉及文件**：`Server/ScadaServer.WebApi/HostedServices/HistoryRecorder.cs`（`FlushAsync` Influx 分支入口）

**现状根因**：InfluxDB 行协议不接受 NaN/Infinity field 值；批次中混入一个即整批 `WriteAsync` 失败 → 重试穷尽 → **整批（最多 100 条正常点）连累回退 MySQL**。MySQL `double` 列可存 NaN/Inf，回退本身能落库，但造成写入路径抖动与存储割裂（同批正常值跟着进 MySQL，Influx 该时段缺数据）。

**设计**：
```
FlushAsync Influx 分支入口：
  batch 分为 normalPoints 与 invalidPoints（double.IsNaN || double.IsInfinity）
  invalidPoints 非空：
    → 直接走 MySQL 写入路径（AddRange + SaveChangesAsync，复用步骤 2.1 的重试）
    → Interlocked 计数 _invalidValueCount（新增 stats 字段 invalidValuePoints）
  normalPoints 走原 Influx 优先链路（不变）
```
- 剥离在内存 List 上一次 `RemoveAll`/分区完成，开销可忽略；
- NaN 点写 MySQL 时 `RawValue`（原始字符串）照常保留，前端明细表仍可展示原始报文；
- **不丢弃**（NaN 本身可能是脚本计算结果，有排障价值），只改道；
- stats 新增 `invalidValuePoints` 计数，与 `droppedAllBackendFailed` 区分（前者是分流不是丢弃）。

**可见性取舍（明确记录）**：分流解决的是**写入路径**抖动（整批连累回退）；NaN 点在**查询侧**仍受"Influx 有数据即不回退"语义影响——该时段 Influx 有正常点时，前端查询看不到 MySQL 中的 NaN 行。接受该取舍，理由：
1. 前端趋势图本就过滤 NaN（`!isNaN`），曲线呈现无差异；
2. NaN 行的排障价值主要在 `RawValue` 原始报文（直接查 MySQL 表/DBA 排查），非日常浏览场景；
3. 若需前端可见，依赖"查询合并"（阶段 4 backlog），不值得为边缘场景提前引入。

**验收**：造一个除零脚本变量连续产生 NaN → stats `invalidValuePoints` 递增；同期正常变量批次全部落 Influx（不再整批回退）；MySQL 中 NaN 行 `RawValue` 完整。

### 步骤 2.7 单元测试

1. MySQL 写入失败 N 次后成功（重试计数与延迟断言，延迟可注入）。
2. 补偿队列：双后端失败 → buffer 增长 → 后端恢复 → 重放成功出队；毒丸批次 10 轮后放弃计数。
3. 指标原子性：并发 Record 下计数不丢。
4. 清理循环：cutoff 边界（恰好等于/大于）、分批退出条件（deleted < BatchSize）、`MySqlRetentionDays=0` 不执行。
5. 双后端清理任务：Influx 配置/未配置两条路径的任务结果消息。
6. NaN/Infinity 分流：批次混入非法值 → normalPoints 走 Influx、invalidPoints 落 MySQL 且 RawValue 完整；计数正确；全 NaN 批不触发 Influx 调用。

## 5. 风险与回滚

| 风险 | 缓解 |
|---|---|
| 补偿队列重放造成 MySQL 重复行 | 容忍语义已决策；统计影响小；如需严格幂等后续加 `(DeviceKey,VariableKey,Timestamp)` 唯一索引（需先清洗存量，backlog） |
| 重试占用 flush 循环导致队列堆积 | 重试总时长上限（500+1000+2000ms + buffer 重放限批），队列满仍 DropWrite 保护采集 |
| 保留期清理误删未迁移数据 | 默认 0 关闭；阶段 4 落地后加迁移状态门禁；文档强调运维顺序 |
| 回滚 | 清理配置默认关、行为开关化；重试/补偿为纯内存逻辑，回滚代码即恢复旧行为；索引保留无害 |
