## 1. 问题定性

现有唯一索引为 `(VariableKey, Timestamp)`，**缺少设备维度**。溯源结论（见 2026-09-21 工作日志）：

1. 该索引 2026-08-25 建表时是**普通查询索引**，非唯一；
2. 2026-09-12 阶段3 的 P2-9 已识别"缺 DeviceKey 导致跨设备同名变量查询放大"，但归类为**性能问题**，且明确决定**保留**该二列索引待观察；
3. 文档 backlog（`03-阶段2:178`、`07:79`）规划的严格幂等键一直是 **`(DeviceKey, VariableKey, Timestamp)` 三列**；
4. 2026-09-14 落地 1062 幂等写入时，**复用了这个"待删"的二列索引**改为 UNIQUE，设备维度就此丢失。

**定性：意图正确（防重试/补偿重放重复入库），索引粒度选错，属实现偏差而非有意设计。**

---

## 2. 设计依据：两个后端对"样本身份"的定义必须一致

同一条写入链路的两个后端，对"什么是一条唯一样本"的定义目前不一致：

| 后端 | 样本唯一身份 | 代码位置 | 现状 |
|---|---|---|---|
| **InfluxDB** | `device_key` + `variable_key` + `time` | `InfluxStore.cs:27`（"series 身份 = device_key + variable_key"）、`:844-849` tag 定义 | ✅ 正确 |
| **MySQL** | `variable_key` + `timestamp` | `ScadaDbContext.cs:432-435` | ❌ 缺设备 |

**本方案的目标不是"给索引加一列"，而是让 MySQL 的样本身份与 Influx 对齐。** 这是修复的正当性来源，也顺带消除"MySQL 作为 Influx 回退/迁移源"时的语义割裂（阶段4 断点续传依赖两者语义一致）。

补充依据：表内 `DeviceId` 是现成 `int`（`ScadaDbContextModelSnapshot.cs:1784`），且对照表 `VariableRealtime` 主键恰为 `(DeviceId, VariableKey)`（snapshot:1851）—— 正确范式项目内已有先例。

## 3. 方案对比

| # | 唯一键 | 存量清洗 | 索引数量变化 | 是否影响无设备查询 | 结论 |
|---|---|---|---|---|---|
| **A** | `(VariableKey, Timestamp, DeviceId)` | **零**（放宽约束） | 不变（原地扩列） | **不退化** | ✅ **推荐** |
| B | `(DeviceId, VariableKey, Timestamp)` | 零 | 需额外保留二列索引 | **退化**（见 §4.2） | ❌ 否决 |
| C | `(DeviceKey(191), VariableKey, Timestamp)` | 零 | 需额外保留二列索引 | 不退化 | ⚠️ 备选（见 §3.1） |
| D | 不加唯一索引，仅写侧 `INSERT IGNORE` | 零 | 减少 1 | 不退化 | ❌ 否决（丧失数据库级兜底） |

### 3.1 关于方案 C（文档原计划）

文档原计划用 `DeviceKey`，落地时被 longtext 挡住。技术上可行（`191×4 + 255×4 + 6 ≈ 1798` 字节 < 3072 上限），但否决理由：

1. **前缀唯一索引存在语义风险**：只比较前 191 字符，两个设备键若前 191 字符相同会被误判为冲突（虽罕见，但属正确性风险）；
2. 索引体积大近一倍（764 字节 vs 4 字节的设备维度），历史表写入密集，放大写开销；
3. `DeviceKey` 是冗余业务键，**理论上可被用户修改**；`DeviceId` 不可变，唯一性判定更稳定。

方案 A 使用 `DeviceId` 即可获得与 Influx `device_key` **等价**的语义（`Device.Id ↔ Device.Key` 一一对应），且无前缀风险。

## 4. 推荐方案：方案 A

### 4.1 键设计

```
UNIQUE (VariableKey, Timestamp, DeviceId)
```

### 4.2 为什么列顺序必须是 `(VariableKey, Timestamp, DeviceId)`

这是本方案的关键论证点。全部现有查询的最左等值列都是 `VariableKey`（`VariableHistoryRepository.cs:27-57`、`:102-185`），`DeviceKey` 是**可选**条件：

| 查询形态 | 代码位置 | 走 `(VariableKey, Timestamp, DeviceId)` | 走 `(DeviceId, VariableKey, Timestamp)` |
|---|---|---|---|
| `VariableKey=? [AND DeviceKey=?] AND Timestamp BETWEEN ? ORDER BY Timestamp DESC LIMIT n` | `GetLatestAsync` `:42-56` | ✅ 前缀有序，可直接反向扫描取 n 条 | ❌ 最左列 DeviceId 缺失 → 全表扫描 |
| 分桶聚合（`PARTITION BY bucket ORDER BY Timestamp`） | `GetAggregatedAsync` `:146-155`、`:173-178` | ✅ 前缀有序，扫描范围限于该 variableKey | ❌ 同上 |

**结论**：列顺序取 `(VariableKey, Timestamp, DeviceId)` 时，该唯一索引可**原地替代**现有二列索引的全部查询职责，性能不退化；而把 `DeviceId` 放最左会导致 `LIMIT 2000` 类查询从"有序扫描直接截断"退化为"全量扫描 + filesort"，历史表数据量大时不可接受。

**唯一性语义与列顺序无关**，故该顺序在正确性与性能上同时最优。

### 4.3 迁移 DDL

```sql
-- Up
DROP INDEX `ix_variablehistory_key_timestamp` ON `VariableHistory`;

CREATE UNIQUE INDEX `ux_variablehistory_key_timestamp_deviceid`
    ON `VariableHistory` (`VariableKey`, `Timestamp`, `DeviceId`);

-- Down（注意 §4.5 的回滚风险）
DROP INDEX `ux_variablehistory_key_timestamp_deviceid` ON `VariableHistory`;

CREATE UNIQUE INDEX `ix_variablehistory_key_timestamp`
    ON `VariableHistory` (`VariableKey`, `Timestamp`);
```

对应 EF 侧同步改动（编码阶段执行，本次未动）：

| 文件 | 改动 |
|---|---|
| `ScadaDbContext.cs:432-435` | `HasIndex(h => new { h.VariableKey, h.Timestamp, h.DeviceId }).IsUnique().HasDatabaseName("ux_variablehistory_key_timestamp_deviceid")` |
| 新增迁移文件 | 上述 DDL（`ScadaDbContextModelSnapshot.cs` 由 EF 自动生成） |

顺带收口 `04-阶段3:107` 遗留的"评估删除 `ix_variablehistory_key_timestamp`"——该索引被本方案**原地升级**而非并存，索引总量不变，历史包袱自然消解。

### 4.4 为什么零存量清洗（数学论证）

- 旧约束：`(VariableKey, Timestamp)` 唯一
- 新约束：`(VariableKey, Timestamp, DeviceId)` 唯一

任意两行若满足旧约束，则二者 `VariableKey` 或 `Timestamp` 必有一处不同 → 三元组必然不同 → **新约束自动成立**。

**约束是放宽的，放宽约束不可能违反既有数据，因此无需任何存量的、代价高昂的 self-join 清洗。**

> ⚠️ 前置校验（迁移前执行，防表上约束已被手工移除的异常情况）：
> ```sql
> SELECT COUNT(*) AS dup FROM (
>   SELECT `VariableKey`, `Timestamp` FROM `VariableHistory`
>   GROUP BY `VariableKey`, `Timestamp` HAVING COUNT(*) > 1
> ) t;
> ```
> 预期 `dup = 0`。若 > 0，需先按 §4.4 清洗逻辑处理（`03-阶段2` / `20260914045737` 已有同款 SQL 可复用）。

### 4.5 触发场景前置诊断（**决定一期是否有效**）

本方案一期（改索引）的前提假设是：报错源于**跨设备同名变量**（场景 A）。但报错也可能是**同一设备同一变量在同一时刻被重复写入**（场景 B，如驱动批读返回重复条目）。两种场景对一期的影响截然不同：

| 场景 | 成因 | 一期改索引是否有效 | 真正的解法 |
|---|---|---|---|
| **A 跨设备撞键** | 多设备共用同名变量键（如 `current_a`）+ 同刻采样 | ✅ 有效（不同 DeviceId 不再撞） | 一期即可 |
| **B 同设备同刻重复** | 同一 `(DeviceId, VariableKey, Timestamp)` 被写两次 | ❌ **无效**（三元组仍相同，仍撞 1062） | 必须二期幂等写入 |

**因此，动手改索引前必须先跑诊断 SQL 确认场景**：

```sql
-- 场景 A 判定：变量是否出现在多个设备下
SELECT `VariableKey`, COUNT(DISTINCT `DeviceId`) AS devs
FROM `VariableHistory`
GROUP BY `VariableKey`
HAVING devs > 1
ORDER BY devs DESC
LIMIT 20;
```

- 若 `current_a` 出现在多个 `DeviceId` → **场景 A 成立**，一期改索引即可消除报错；
- 若全部变量 `devs = 1`（每变量仅归属一台设备）→ 报错属**场景 B**，一期改索引不解决问题，应**直接上二期**（SF-1 幂等写入 + SF-3 批内去重），一期可跳过或仅作为"约束语义修正"顺带做。

> 补充：报错时间戳精确到微秒，若同一轮采集调度为多设备统一打 `now`，多设备同刻是常态；但"同设备同变量同微秒重复"需驱动批读返回重复条目才会发生。二者都需要数据佐证，不能仅凭推断下结论。

> ✅ **诊断结论（2026-09-21 已确认）**：报错变量出现在多台设备下，属**场景 A（跨设备撞键）**。据此：
> - **一期改索引即可消除当前报错**（不同 `DeviceId` 的 `current_a` 不再互撞）；
> - **二期仍建议实施**——它针对的是另一类隐患：现 `HistoryRecorder.cs:509-519` 撞 1062 时整批 `return` 会静默丢弃同批其余未入库的点（见 §5.1），该 bug 与场景 A/B 无关，改索引不消除它。

### 4.6 回滚的不对称性（**重要风险**）

升级与回滚的风险不对称，必须在运维文档中明确：

| 方向 | 约束变化 | 风险 |
|---|---|---|
| **升级**（Up） | 放宽 | ✅ 安全，零清洗 |
| **回滚**（Down） | **收紧** | ⚠️ **可能失败**：新键允许"同 `VariableKey`+`Timestamp` 不同设备"的多行共存，回滚到二列唯一时这些行会成为冲突行，索引创建报错 |

**因此回滚前必须先执行**：

```sql
-- 回滚前的存量冲突清理（保留每组 Id 最小的一行）
DELETE h1 FROM `VariableHistory` h1
INNER JOIN `VariableHistory` h2
    ON h1.`VariableKey` = h2.`VariableKey`
   AND h1.`Timestamp` = h2.`Timestamp`
   AND h1.`Id` > h2.`Id`;
```

> ⚠️ **回滚前必须先做全量备份**（`mysqldump` 或快照），上述 DELETE 是**破坏性且不可逆**的——一旦执行，被删行的数据无法从应用侧恢复。备份应先于一切回滚动作，并校验备份可恢复。

**含义**：一旦按方案 A 运行，回滚即意味着**主动丢弃跨设备同名变量中除一行外的全部历史数据**。这是本方案唯一的不可逆代价，需在审批时确认接受。

## 5. 写入路径改进（与索引修复解耦，可分两期）

### 5.1 现状缺陷

即使唯一键修好，`WriteMySqlWithRetryAsync` 的兜底逻辑仍会丢数（`HistoryRecorder.cs:509-519`）：

```
撞 1062 → IsUniqueIndexConflict → 视为已入库 → return（整批放弃）
```

- 一批 100 条中只要有 1 条冲突，MySQL 回滚整条 INSERT → EF 抛异常 → 被判定"已入库"→ `return` → **其余 99 条未入库的点一并被丢弃**；
- 且 EF 在抛异常前会打 `fail: Microsoft.EntityFrameworkCore.Update[10000]` 日志（**上层捕获了也照样打**），造成"日志报错但程序不报错"的困惑。

### 5.2 子方案对比

| 编号 | 做法 | 不丢数 | 消除日志噪音 | 改动范围 | 性能 |
|---|---|---|---|---|---|
| **SF-1** | MySQL 写入改批量 `INSERT ... ON DUPLICATE KEY UPDATE`（或空更新 `Id=Id`） | ✅ | ✅ | Infrastructure 新增方法 + WebApi 调用点 | 好（单语句批量） |
| SF-2 | 捕获 1062 后拆分为**逐条**插入，跳过冲突行 | ✅ | ❌ | 仅 `HistoryRecorder` | 差（100 次往返） |
| SF-3 | 仅 `FlushAsync` 前按三元组**批内去重** | 部分 | ❌ | 仅 `HistoryRecorder` | 好 |

### 5.3 推荐组合

**SF-1（主）+ SF-3（叠加加固）**：

1. **SF-1**：在 Infrastructure 新增批量幂等写入（如 `IVariableHistoryRepository.InsertIdempotentAsync`），用参数化 `ExecuteSqlRawAsync` 拼 `VALUES (…),(…)…`；每行 8 列（`Id` 自增不插入）× 100 条 = **800 参数**，远低于 MySqlConnector 上限。
   - 异常路径消失 → 不丢数、无 EF `fail` 日志噪音；
   - `WriteMySqlWithRetryAsync` / `ReplayRetryBufferAsync` / `TryWriteMySqlOnce` **三处**统一改走该入口，补偿与 WAL 重放一并获得真幂等。
   - **注意**：SF-1 只是**替换写入方式**（消除 1062 类异常），**不替代重试框架**——连接断开/超时等非 1062 异常仍需原有指数退避重试 + 补偿队列 + WAL 落盘（见 §5.5）。
2. **SF-3**：`FlushAsync` 入队后按 `(DeviceId, VariableKey, Timestamp)` 去重（`HashSet`），防批内自重复引发整批异常。成本极低。
3. **保留异常兜底但修正语义**：1062 分支从"整批视为已入库"改为**计数 + 告警 + 不静默 return**，避免任何残余路径继续吞数据。

### 5.4 待定语义（决策点，见 §9）

同一 `(DeviceId, VariableKey, Timestamp)` 重复写入时：

- **S1 保留首条**：`ON DUPLICATE KEY UPDATE Id=Id`（空更新），语义"重复上报忽略"；
- **S2 后到覆盖**：`ON DUPLICATE KEY UPDATE Value=VALUES(Value), RawValue=…, Quality=…`，语义"以最新为准"。

> 注：`VALUES()` 函数在 MySQL 8.0.20+ 已废弃，建议改用行别名语法 `INSERT … AS new ON DUPLICATE KEY UPDATE Value=new.Value`（需确认目标 MySQL 版本，MariaDB 不支持别名语法）。

### 5.5 工程注意点

1. **幂等写入 ≠ 免重试**：`ON DUPLICATE KEY UPDATE` 只消除 1062 唯一冲突；连接断开、超时、`max_allowed_packet` 超限等错误仍会抛出，必须**保留原指数退避重试 + 补偿队列 + WAL 落盘框架**。SF-1 替换的是 `AddRange + SaveChanges` 这个"写入动作"，不是替换 `WriteMySqlWithRetryAsync` 这个"重试包装"。
2. **`max_allowed_packet` 风险**：`DeviceKey`/`VariableName`/`RawValue` 均为 `longtext`，单条可能数 KB（`RawValue` 是完整原始报文）。100 条一批的 SQL 体积可能超过 `max_allowed_packet`（默认 4~64MB）。实现时应**按序列化后字节数估算**，动态降批（如每批控制在 4MB 内），或沿用 EF 的拆分思路。
3. **自增 Id 空洞**：`ON DUPLICATE KEY UPDATE Id=Id` 与 `INSERT IGNORE` 都会在冲突时消耗一个自增值，导致 `Id` 空洞。`Id` 为 `bigint`（上限 2^63），空洞不影响正确性，仅影响"按 Id 单调"观感（`GetBatchAfterIdAsync` 仍正确，只是跳过空洞）。可接受，需在文档注明。
4. **SF-3 批内去重的保留语义**：`FlushAsync` 按三元组去重时保留首条还是末条，需与 D4 一致（建议同为保留首条），避免"批内去重保留末条"与"落库保留首条"语义打架。

## 6. 索引布局最终态

| 索引 | 列 | 用途 | 变化 |
|---|---|---|---|
| `ux_variablehistory_key_timestamp_deviceid` | `(VariableKey, Timestamp, DeviceId)` UNIQUE | 唯一约束 + 无设备查询 | **原地升级**（原二列唯一索引） |
| `ix_variablehistory_device_variable_timestamp` | `(DeviceKey(191), VariableKey, Timestamp)` | 带设备查询 | 不变 |
| `ix_variablehistory_timestamp` | `(Timestamp)` | 保留期清理 DELETE | 不变 |

**索引数量不变（3 → 3）**，写入放大无新增。

**索引长度核算**：`VariableKey`(varchar255, utf8mb4 = 1020B) + `Timestamp`(datetime6 = 6B) + `DeviceId`(int = 4B) + 主键 `Id`(8B) ≈ **1038 字节**，远低于 InnoDB 单索引上限 3072 字节，无超长风险。

**优化器索引选择提醒**：带设备的查询（`GetLatestAsync` 传入 `deviceKey`）过滤键是 `DeviceKey`（字符串），而新唯一索引第三列是 `DeviceId`（int）——**二者不是同一字段**。因此带设备查询必须继续命中 `ix_variablehistory_device_variable_timestamp`，不能落到新唯一索引。迁移后需用 `EXPLAIN` 确认优化器选择正确；若误选新索引（扫描该 variableKey 全设备再回表过滤 DeviceKey），需评估是否加 `USE INDEX`、或改谓词用 `DeviceId` 过滤。

## 10. 未采纳的方案及理由（留档）

| 方案 | 否决理由 |
|---|---|
| 保持二列唯一 + 写入改 `INSERT IGNORE` | 数据库级约束与实际业务语义（设备×变量×时间）不符，靠写侧"绕过"掩盖模型错误；且 Influx 侧身份定义正确，MySQL 长期不一致会污染阶段4 迁移语义 |
| 用 `DeviceKey`(longtext) 建前缀唯一索引 | 前缀比较存在误判正确性风险；索引体积大；DeviceKey 可变而 DeviceId 不可变 |
| 放弃唯一约束，靠应用层内存去重 | 进程重启 / 多实例部署下失效；补偿队列与 WAL 重放路径无法覆盖 |
| 引入 `PairKey`/拼接键列 | 需新增冗余列 + 存量回填 + 全体写入路径改造，成本远高于扩列；与项目"JSON 权威、最小改动"取向不符 |
