## 一、实证结论：EF Core 对游离对象图 Remove / Update 的行为（本会话实验）

> 实验：Sqlite `:memory:`，双 DbContext（seed 写库后释放 → 新 context 模拟真实 HTTP 请求：`AsNoTracking+Include` 读游离实体 → `Remove` → `SaveChanges`），模型外键配置复刻项目（Device→Controller/Connection/Model/Area `Restrict`，Device→Binding `Cascade`，Binding→DataModel `Restrict`）。结果：

| 场景 | 操作 | 变更跟踪结果 | SaveChanges |
|---|---|---|---|
| A | `Remove(AsNoTracking+Include 全导航游离 Device)`，其 Controller/Connection/DataModel/Area/Protocol 全被**另一台设备共享引用** | 仅 `Device:Deleted`；Area/Connection/Controller/DataModel/Protocol 全部 attach **`Unchanged`** | OK；共享资源全部保留 |
| B | `Remove(tracking 无导航 Device)`（`GetByIdForUpdateAsync` 模式） | 仅 `Device:Deleted` | OK |
| C | `Remove(游离 Device，含 Binding 集合导航→共享 DataModel)`（复刻 DeviceDataModels） | `Device:Deleted` + 本设备 `Binding:Deleted`（子集合随主删除）；共享 DataModel/Connection 保留 | OK；他设备 Binding 完好 |

**推论（支撑本方案多处决策）：**

1. `RepositoryBase.DeleteAsync(entity)` 对「AsNoTracking + Include 全导航」实体执行 `Remove` 时，**reference 导航目标（父实体）只会被 attach 为 `Unchanged`，不会被删除**——共享的 Controller/Connection/DataModel/Area/Protocol 安全；被删的只有主实体 + 其级联子集合（如本设备的 DeviceDataModels 行）。
2. 因此 `DeviceDeletionService` 主删除路径**不存在**「图附加导致共享资源被删」的机制（**Bug#4 根因不成立**，见 §五）。
3. 但在**同一 DbContext 内**，先 `FindAsync`（tracking）加载某实体、再对**另一同 key 游离实例**做 `Remove`/`Update`（graph-attach）会抛 `InvalidOperationException`（identity 冲突，实验首轮即复现）——这正是 **Bug#1 的机制**。

## 二、Bug#1（P1）数据模型 PUT 500 —— 仓储缺「更新专用加载」

### 2.1 根因链（已逐行确认）

| 步骤 | 位置 | 说明 |
|---|---|---|
| ① | `DataModelRepository.cs:29-35` `GetByIdAsync` | `AsNoTracking().Include(m => m.Protocol)` → 返回**游离实体**（含游离 Protocol 导航） |
| ② | `DataModelAppService.cs:215` | `ResolveProtocolIdAsync` → `ProtocolRepository.GetByIdAsync`（基类 `RepositoryBase.cs:26-29` 用 `FindAsync`，**跟踪查询**）→ 同 key Protocol 已入 change tracker |
| ③ | `DataModelAppService.cs:225` → `RepositoryBase.cs:91-95` | `Db.Set<DataModel>().Update(entity)` **graph-attach 全图 Modified** → 试图把游离 `Protocol` 也标 Modified → 与 tracker 中同 key Protocol **identity 冲突** → `InvalidOperationException` → HTTP 500 |

**代码库早有同类解法**：`ControllerRepository.cs:36-40`、`DeviceRepository.cs:44-48`、`DeviceConnectionRepository.cs`、`DeviceDataModelRepository.cs:57-64` 均已实现 `GetByIdForUpdateAsync`（tracking、**不 Include 导航**），注释明言「使 Update(entity) 无需附加导航对象图，避免与协议存在性校验加载的 Protocol 实体产生同主键跟踪冲突」；且 Controller/Device/Connection 的 Update 与 Delete 路径均走该方法。**DataModelRepository 是全库唯一漏做该项的仓储**（`IDataModelRepository` 仍是空接口 `IEntityRepositories.cs:120`）。

### 2.2 方案 C（推荐）：补齐 GetByIdForUpdateAsync，与全库模式对齐

| # | 文件 | 改动 |
|---|---|---|
| 1 | `Domain/Interfaces/Repositories/IEntityRepositories.cs:120` | `IDataModelRepository` 增加 `Task<DataModel?> GetByIdForUpdateAsync(int id);`（仿 `IControllerRepository` 声明） |
| 2 | `Infrastructure/Repositories/DataModelRepository.cs` | 新增 `GetByIdForUpdateAsync`：`Db.DataModels.FirstOrDefaultAsync(m => m.Id == id)`（tracking、不 Include），附与 ControllerRepository 同款注释 |
| 3 | `Application/Services/DataModelAppService.cs:188` | `UpdateAsync` 改用 `GetByIdForUpdateAsync(dto.Id)`（存在性 + 更新源） |
| 4 | `Application/Services/DataModelAppService.cs:225` | `_repository.UpdateAsync(entity)` 不变——此时 entity 为 tracking 无导航实体，`Update()` 仅将本体标 Modified，不再触碰 Protocol 图，冲突消除 |
| 5 | `Application/Services/DataModelAppService.cs:227` | **返回 DTO 改为更新后重读**：`return (await GetByIdAsync(dto.Id))!;`（仿 `DeviceConnectionAppService.cs:177` / `DeviceAppService.cs:1038` 的「Update 后重读返回」）。若不重读，entity.Protocol 为 null → 响应 `ProtocolKey/ProtocolName` 空，且**改绑协议后响应仍是旧协议名**（现有隐式隐患一并消除） |
| 6 | `Application/Services/DataModelAppService.cs:237`（DeleteAsync 顺带） | `GetByIdAsync` → `GetByIdForUpdateAsync`（与 `ControllerAppService.DeleteAsync:171` 先例一致；删除只用实体 Name 文案，无导航需求） |

**不采用回归记录中的备选**：
- 方案 A（仅 `GetByIdAsync` 去 `AsNoTracking`，1 行）：可消除冲突（tracking 后同 key 走 identity map 返回同实例），但读接口改为跟踪查询与全库「读用 AsNoTracking」约定相悖；且 Update 返回 DTO 协议字段问题仍须另补重读。
- 方案 B（`RepositoryBase.UpdateAsync` 改 `Db.Entry(entity).State = EntityState.Modified`）：需全仓核查所有 `UpdateAsync`/`UpdateRangeAsync` 调用是否依赖 graph-attach 级联保存导航（Controller/Device 等大量路径依赖「本体列更新」语义，改动影响面最大），收益不高于 C。

**验证**：`dotnet build` 0 错误 → 起服务 → PUT /api/data-models/{id}（同名不改协议、改名、换协议三例）均 200 且响应含新 ProtocolKey → 回归 `10` 文档 §1.2「数据模型（4/4）」复测。

## 三、Bug#2（P1）附加绑定模型的数据点无法手工实例化

### 3.1 根因（已确认，含一处连带问题）

- 主缺陷：`DataPointMappingAppService.cs:83` 校验只认设备主模型：
  `if (mv.ModelId != device.ModelId) throw ...("不属于设备所绑定的数据模型")`
  阶段 5（多对多）后设备可绑多个模型，**附加绑定模型**的变量模板（DataPoint）是合法实例化来源，却被 400 拒绝，与 `07-阶段5` 文档「解绑前需先清理该模型下映射」语义自洽性相悖。
- **连带缺陷**：`GetByDeviceAsync` 的模板加载（`DataPointMappingAppService.cs:57-58`）同样只查主模型：
  `GetListAsync(mv => mv.ModelId == device.ModelId)` → 即使 Create 通过，附加模型映射在列表读取时 `mv` 查不到 → DTO 以空串兜底（Key/Name/DataType 丢失，`MapToDto` 回退默认值）。

### 3.2 修复方案（推荐：以绑定集合为校验/加载范围）

| # | 文件 | 改动 |
|---|---|---|
| 1 | `Application/Services/DataPointMappingAppService.cs` 构造函数 | 注入 `IDeviceDataModelRepository`（现依赖列表无此项） |
| 2 | 同上，新增私有助手 | `GetBoundModelIdsAsync(int deviceId)`：`GetByDeviceAsync` 绑定行 `Select(b => b.DataModelId)` **∪ `device.ModelId` 兜底**（兼容理论上的「绑定表缺主行」旧数据；正常路径绑定表含主行，集合无变化），返回 `List<int>` |
| 3 | 同上 `CreateAsync:83` | 校验改为 `if (!boundModelIds.Contains(mv.ModelId)) throw ...`（错误文案不变） |
| 4 | 同上 `GetByDeviceAsync:58` | 模板查询改为 `GetListAsync(mv => boundModelIds.Contains(mv.ModelId))`，随后 `ToDictionary` 组装不变 |

**决策点 D1**：绑定集合查询用现成 `GetByDeviceAsync`（返回含 DataModel 导航的完整实体，本服务仅用 Id 集，略浪费）还是新增 `GetByDeviceIdsOnlyAsync` 轻量方法？——推荐前者（数据量小、少一个仓储方法，保持接口精简）；若追求查询最小化可选后者。

**验证**：设备绑定附加模型 → POST /api/data-point-mappings 以附加模型 DataPoint 实例化 → 200；GET 该设备映射列表 → 附加模型映射 Key/Name/DataType 完整；解绑前先清理该模型映射的既有约束不受影响。

## 四、Bug#3（P2）服务重启后遗留 active 报警不闭合

### 4.1 根因（已确认，两处叠加）

| # | 位置 | 缺陷 |
|---|---|---|
| ① | `DeviceWorker.cs:42,47` `_ruleStates`/`_alarmStates` | 报警状态机为**进程内内存**，重启清零 |
| ② | `DeviceWorker.cs:551-608` `EvaluateRule` | 重启后值正常 → `matched=false` 且无 `IsActive` 态 → 不产生恢复事件；值仍越限 → `matched=true` 重新 Triggered（产生**重复触发记录**） |
| ③ | `AlarmRecorder.cs:228-247` `MarkRecoveredAsync` | 只 `OrderByDescending(TriggeredAt).First` 闭合**最新一条**未恢复；同一键若存在多条未恢复（前序恢复事件在重启窗口丢失），旧条被永远跳过 |

### 4.2 方案对比

| | 方案 1：启动预置状态机 | 方案 2：启动巡检补恢复（推荐） |
|---|---|---|
| 思路 | DeviceWorker 启动时按设备查未恢复记录，把 `_ruleStates[key].IsActive=true`（规则）/ `_alarmStates` 方向（MinMax）预置 | 独立巡检：进程启动后对 DB 中每条 `RecoveredAt==null` 记录，取**该变量当前实时值**，若已脱离报警条件则**直接补写恢复**（RecoveredAt/RecoveryValue=当前值） |
| 优点 | 恢复时间=真实回落时刻，时间轴干净 | 不动状态机、天然幂等；不依赖设备在线/变量启用（离线设备遗留同样闭合）；实现独立可测 |
| 缺点 | MinMax 方向需按当前值推断（启动时无当前值，语义绕）；设备离线/变量停用则永不触发恢复 | 恢复时间以巡检时刻为准（非真实回落时刻，偏差=重启→巡检窗口，通常分钟级，可接受） |
| 风险 | 侵入 Worker 启动路径；预置方向猜错会产生错位恢复/重复触发 | 新增一个 HostedService 与启动时序耦合点 |

### 4.3 推荐落地（方案 2）要点

1. **新增** `WebApi/HostedServices/AlarmRecoveryStartupService.cs`（`BackgroundService`）：
   - 等待 `DatabaseInitializationStatus` 就绪（复刻 `RuntimeHostedService` 的 `_dbReady.WaitAsync` 模式），再等待一个短延时（如 5s，覆盖 RuntimeManager 设备加载 + AlarmRuleEngine 首轮 30s 热载——规则判定直接用 AlarmRecord 自带 `Condition/Threshold`，不依赖规则引擎快照，延时仅为读实时快照的稳定性）；
   - 查全部 `RecoveredAt == null` 的 AlarmRecords（可按 `(DeviceKey, VariableKey, RuleId)` 分组聚合）；
   - 查这些变量在 **variablerealtime 表**的最新值（复用 VariableRealtimeRepository；不依赖内存态，规避快照落库延迟），结合 AlarmRecord 自身字段判定：
     - 规则报警（`RuleId` 非空）：`!MatchesCondition(Condition, value, Threshold)` → 已脱离；
     - MinMax 兜底（`RuleId == null`）：经 `DataPointId`（6.5 已关联）读 DataPoint 模板 `Min/Max` 判定，或退化为解析记录的 `Message`（含「超过上限 X」文案）；
   - 对已脱离的记录**批量补恢复**（仿 `AlarmRecordRepository.RecoverByDeviceAsync` 的 SQL 风格或 EF 更新），并记录巡检日志（恢复 N 条、仍 active M 条）。
2. **顺带修** `AlarmRecorder.MarkRecoveredAsync`（`AlarmRecorder.cs:228-247`）：同一键（Device+VariableKey+RuleId）一次恢复事件改为**闭合全部未恢复记录**（`ExecuteUpdate` 批量，而非 `First` 单条）。语义依据：单条规则在同一时刻只有一段越限区间，同键存在多条未恢复 = 前序恢复事件丢失（重启窗口），一次恢复代表「该变量当前已恢复正常」，闭合全部与事实一致。此改动同时消除「值正常但历史多条未闭合」的同类隐患。
3. DI 注册：`Program.cs` 或 `Application.Extensions.cs` 增加 `AddHostedService<AlarmRecoveryStartupService>()`。

**决策点 D2**：恢复事件是否**补发 SignalR 通知**（推荐：补发，与 `FireEvent` 的 `NotifyAlarmAsync` 通道一致，前端报警面板能即时看到闭合；巡检批量场景逐条补发或发汇总事件均可）——默认「补发」。
**决策点 D3**：`MarkRecoveredAsync` 是否随本批改为批量闭合（推荐：改，属 Bug#3 语义完整性一部分；若求最小改动可只做巡检、MarkRecovered 保持单条，但重启场景的「多条遗留」闭合就完全依赖巡检时序）。

**验证**：造数（写越限→触发 active → 把值改回正常 → **重启服务**）→ 启动后遗留 active 在巡检周期内自动闭合且 RecoveryValue=当前值；「值仍越限的 active」保持不闭合；控制台日志输出恢复计数。

## 五、Bug#4（P3）删除设备「共享连接/控制器被级联删除」—— 经实证疑似误判，建议验证后关闭

### 5.1 代码事实（与回归记录根因描述不符）

回归记录 `10` 文档 §五将 Bug#4 根因记为「`DeviceAppService.DeleteAsync` 未区分连接是否被其他设备引用」。实际代码：

- `DeviceAppService.DeleteAsync`（`DeviceAppService.cs:1064-1067`）只委托 `IDeviceDeletionService`；
- `DeviceDeletionService.DeleteAsync`（`DeviceDeletionService.cs:59-95`）在事务内先删设备（`:87`），再执行 `CleanupExclusiveControllerAndConnectionAsync`（`:91`）；
- 后者（`:105-128`）**明确带引用计数检查**：Connection 仅当 `无其他 Device.ConnectionId` 指向才删；Controller 仅当 `无其他设备且无其他连接` 指向才删——注释亦明言「避免误删手工共享（多设备共用连接）的资源」。

### 5.2 实证结论

本会话实验（§一）证明：`:87` 的 `RepositoryBase.DeleteAsync(entity)`（对 AsNoTracking+全导航游离 Device 执行 Remove）**只删主实体与级联子集合，不会删除 reference 引用的共享 Controller/Connection/DataModel**（attach Unchanged）。故「真共享场景删除其一」在现有代码下应保留共享资源——回归中观察到的删除更可能来自测试数据构造（被删连接/控制器当时仅被该设备引用 → 清理符合「独占资源随设备删除」设计，属**正确行为被误判为缺陷**）。

### 5.3 处置建议（决策点 D4，三选一）

- **D4-A（推荐）**：不写修复逻辑。先做一次**真共享回归验证**（API 层：两台设备经高级模式 attach 同一 Controller+同一 Connection → DELETE 其一 → GET 断言连接/控制器仍在 → 删除第二台 → 资源清理）以事实关闭 Bug#4；若验证中发现共享资源被删，再回到引用计数逻辑排查（当前代码看无需）。
- **D4-B**：D4-A 基础上**顺带稳健化**：`DeviceDeletionService.cs:61` 的 `GetByIdAsync` → `GetByIdForUpdateAsync`（`DeviceRepository` 已提供该方法）——与 Controller/DeviceConnection 删除路径（均用 ForUpdate 加载）对齐，去掉无谓的整图加载与 graph-attach，纯防御、零行为变化。
- **D4-C**：维持回归记录原判，Bug#4 并入「遗留事项：共享连接合并」（`DeviceConnectionProfile` 后续重构）一并处理，本期不动。

**发现的残余语义缺口（记录待决策，不在本批代码范围）**：worker 报警状态机（`_ruleStates`）为进程内内存且**按值变化边沿求值**，重启后为空、不按 DB 中 active 记录武装。因此：重启时值仍越限的 active（巡检正确地保持不闭合）若在**本次运行期间**值回落正常，worker 因状态未武装而**不会发恢复事件**，该记录需等下一次重启巡检才闭合。当前 D2=A「启动巡检一次」设计只覆盖启动时点，此缺口为已知边界。可选后续（需新方案审批）：A. 巡检改周期执行（如每分钟）收敛窗口；B. boot 时按 DB active 记录武装 worker 状态机；C. 维持现状（记录至下次重启，报警面板按 RecoveredAt 语义提示）。
