> 依据文档：[../数据库修改想法.md](../数据库修改想法.md)（下称"目标设计"）
> 方案基线：2026-09-03 代码库快照
> 方案性质：**纯规划文档，不含任何代码修改**

***

## 一、目标设计回顾

目标设计提出 11 张核心表，分四层：

| 层     | 表                                             | 职责                   |
| ----- | --------------------------------------------- | -------------------- |
| 设备资产层 | Area / Device / Controller / DeviceConnection | 设备在哪里、是什么、由谁控制、怎么连接  |
| 数据定义层 | DataModel / DataPoint / DeviceDataModel       | 这类设备有哪些标准数据          |
| 数据映射层 | DataPointMapping                              | 数据在 PLC/OPC UA 的实际位置 |
| 运行数据层 | DeviceDataValue / DataHistory / AlarmRecord   | 最新值、历史值、报警           |

核心思想：

1. **Controller 与 Device 分离**：Device 是业务设备（1号输送带），Controller 是控制器（S7-1500 PLC），两者是 N:1。
2. **DeviceConnection 独立**：连接参数（Host/Port/协议私有配置）从设备配置中抽出，未来可多设备共享一条连接。
3. **数据定义与数据映射分离**：DataPoint 只定义"是什么"，DataPointMapping 定义"在哪里读"。
4. **Area 树形化**：区域成为一级实体，承载 工厂→车间→产线→区域 的组织树。
5. **Device 与 DataModel 多对多**：通过 DeviceDataModel 中间表绑定，支持版本化。

## 二、现状与目标的差距总结

（详细对照见 [01-现状与目标结构对比.md](01-现状与目标结构对比.md)）

| 目标概念                    | 现状                                                                            | 差距                                                                      | 差距等级       |
| ----------------------- | ----------------------------------------------------------------------------- | ----------------------------------------------------------------------- | ---------- |
| Area（树形区域）              | `Areas` 表已存在，但为**平级结构**（仅 Name/Code/Description）                              | 缺 ParentId/AreaType/Sort/Enabled                                        | ★★ 小改      |
| Device                  | 已存在，含 AreaId/ModelId/JsonConfig/Version                                       | 缺 ControllerId/ParentId/DeviceType/Status 等                             | ★★★ 中改     |
| Controller（控制器）         | **不存在**，控制器型号混在 `DataModels.Vendor/ModelName` 中                               | 全新实体                                                                    | ★★★★ 新增    |
| DeviceConnection（连接）    | **不存在**，连接参数在 `Devices.JsonConfig`（longtext JSON），协议经 `DataModels.ProtocolId` | 全新实体 + 数据回填                                                             | ★★★★★ 最大改动 |
| DataModel               | 已存在，与协议耦合（ProtocolId 必填）                                                      | 缺 Code/Version/IsPublished；ProtocolId 应弱化/移除                            | ★★★ 中改     |
| DataPoint               | `ModelVariables` 已存在，语义基本对应                                                   | 缺 AccessMode（现为 bool IsReadOnly）/Required/Sort/Enabled                  | ★★ 小改      |
| DataPointMapping        | `DeviceVariables` 已存在，语义基本对应                                                  | 缺 ConnectionId/RawDataType/TransformConfig；已有 Address/PollingInterval 等 | ★★★ 中改     |
| DeviceDataModel（M:N 绑定） | **不存在**，现为 Device.ModelId 单模型 1:N                                             | 全新实体 + 迁移语义                                                             | ★★★★ 新增    |
| DeviceDataValue（最新值）    | **已存在**：`VariableRealtime` 表（RealtimeSnapshotService 周期批量 Upsert）             | 基本无差距，仅可选增加 DataPointId                                                 | ☆ 已覆盖      |
| DataHistory（历史）         | **已存在**：InfluxDB `variable_history`（device\_key/variable\_key tags）           | 无差距                                                                     | ☆ 已覆盖      |
| AlarmRecord             | **已存在**：`AlarmRecords` 表（含 Ack/Recover 状态机）                                   | 可选增加 DataPointId 关联                                                     | ☆ 已覆盖      |

**关键结论：目标 11 张表中有 3 张（VariableRealtime、InfluxDB 历史、AlarmRecord）已基本就绪，真正的重构工作量集中在 Controller/DeviceConnection 抽取、DeviceDataModel 多对多、Area 树形化三处。**

## 三、可行性分析

### 3.1 总体结论：**可行，且风险可控**

理由：

1. **架构方向正确且与现状兼容**：现有 `Protocol` 实体已把"协议是什么"独立出来；`DeviceVariable` 已实现"模板定义 + 设备实例覆盖"的两层结构，与 DataPoint/DataPointMapping 的思想完全一致。目标设计是在现有骨架上的"补全"，不是推翻。
2. **运行时已有清晰的接入点**：`RuntimeManager.InitializeAsync` 通过 `Device → DataModel(→Protocol) → DeviceVariable(→ModelVariable)` 一次 Include 加载完整对象图；只要新实体挂进这条加载链，驱动层（S7Driver/OpcUaDriver）几乎不用动。
3. **EF Core Migrations 机制成熟**：项目已有 31 个迁移，新增实体/加列/回填均有成熟路径，可逐步演进，不需要停机重建库。
4. **前端影响面集中在少数组件**：设备管理（DeviceManagementView）、数据模型（DataModelView）、设备变量（DeviceVariableView）三个视图 + 对应 api 封装，其余视图通过 SignalR 消费实时值，不直接依赖库表结构。

### 3.2 关键风险与对策

| #  | 风险                                                                                                     | 影响     | 对策                                                                                                  |
| -- | ------------------------------------------------------------------------------------------------------ | ------ | --------------------------------------------------------------------------------------------------- |
| R1 | **InfluxDB 历史数据连续性**：历史库以 `device_key + variable_key` 为 tag，重构若改变 Device.Key 或变量 Key 的生成规则，历史趋势将与新数据断裂 | 高      | **硬性约束：全程保持 Device.Key 与 ModelVariable.Key 既有值不变**。所有回填迁移只增列、不改既有键值。每个阶段迁移后用 InfluxDB 查询抽样验证 tag 连续 |
| R2 | **连接抽取期间采集中断**：Device.JsonConfig → DeviceConnection 迁移若与运行时改造耦合在同一批修改，出错会导致全线采集失败                      | 高      | 阶段 3 采用"**双读兼容期**"：先建表回填，运行时改为优先读 DeviceConnection、缺失时回退 JsonConfig，观察稳定后再删回退逻辑（阶段 6）               |
| R3 | **M:N 绑定改变变量解析语义**：现在 DeviceVariable 必须属于 Device 唯一模型的变量集；多模型后解析规则复杂化                                  | 中      | 阶段 5 先只允许"一个主模型（IsPrimary）+ 只解析主模型变量"，多模型变量合并留到后续版本                                                 |
| R4 | **ORM 选择的沉没成本**：目标设计示例代码使用 SqlSugar，而项目是 EF Core（31 个迁移、全套仓储）                                          | 高（若切换） | **强烈建议保留 EF Core**（见 3.3 决策 D1）。切换 SqlSugar 等于重写全部持久层 + 全部迁移史，无任何功能收益                               |
| R5 | **实体命名冲突**：新实体 `Controller` 与 ASP.NET Core 控制器概念同名，易混淆                                                 | 低      | 实体置于 `ScadaServer.Domain.Entities` 命名空间下无编译冲突；文档、注释、日志统一使用"控制器实体（Controller Entity）"措辞（决策 D2）       |
| R6 | **每设备一连接的临时态**：阶段 3 回填时每台设备生成独立 Controller + Connection，与"多设备共享控制器"的最终形态不一致                            | 中      | 这是**有意为之的过渡态**：先保证行为与现状 100% 等价（1 设备 = 1 连接），共享连接的管理界面与运行时合并放到阶段 6 之后                               |
| R7 | **前端设备表单耦合协议**：DeviceManagementView 中设备表单与数据模型联动回填协议默认值，连接抽出后交互需重设计                                    | 中      | 阶段 3 拆两步走：先在后端兼容旧 DTO（协议字段保留只读），前端第二步再改表单结构                                                         |

### 3.3 必须先确认的设计决策

| #  | 决策点                             | 建议方案                                                                                                                               | 理由                                                                                           |
| -- | ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| D1 | **ORM：SqlSugar 还是 EF Core？**    | **保留 EF Core**                                                                                                                     | 目标设计的表结构是"设计建议"而非"实现绑定"；SqlSugar 示例只是文档作者的举例。项目已有 31 个迁移、27 个仓储、完整 UnitOfWork，切换 ORM 是纯成本无收益 |
| D2 | **实体命名**                        | 新实体命名 `Controller`、`DeviceConnection`、`DeviceDataModel`；现有 `ModelVariables`/`DeviceVariables` **不改表名**（阶段 4 只加字段，表名重命名作为可选清理放阶段 6） | 改表名牵动所有查询/迁移/文档，收益仅是"名字好看"；语义映射在文档中固化即可                                                      |
| D3 | **Protocol 实体去留**               | 保留 `Protocols` 表，由 `DeviceConnection.ProtocolId` 引用（而非现在的 `DataModel.ProtocolId`）                                                  | 目标设计中 `DeviceConnection.Protocol`（S7/OPCUA）对应现有 Protocol.Key/DriverKey，语义完全吻合，复用即可           |
| D4 | **主键类型**                        | 维持现有 `int` 自增，**不改为 bigint**                                                                                                       | 改主键类型需重建全部 FK 和历史表，工业单点系统 int 容量足够                                                           |
| D5 | **时间存储**                        | 维持现有 UTC 存储 + 前端本地化显示约定                                                                                                            | 与现行规范一致                                                                                      |
| D6 | **DeviceDataValue/DataHistory** | 直接映射现有 `VariableRealtime` 表与 InfluxDB `variable_history`，不新建表                                                                      | 已满足目标设计意图（内存快照 → 批量持久化 → 时序库）                                                                |

## 六、全局不变量（所有阶段必须遵守）

1. **Device.Key 与 ModelVariable.Key 既有值永不重新生成**（InfluxDB tag 连续性命脉）。
2. **每个迁移必须先在开发库演练**，验证 `dotnet ef migrations script` 生成的 SQL 可重复执行。
3. **所有新表/新列一律可空或带默认值**，禁止出现"先加非空列"的迁移。
4. **回填迁移与结构迁移分开提交**（结构迁移可空 → 回填 → （阶段 6）收紧约束），避免大事务锁表。
5. **运行时改造遵循"新路径优先 + 旧路径回退"双读模式**，删除回退必须在观察期之后。
6. **前端 API 调用维持相对路径**，代理规则不变（`/api`、`/hubs`）。
7. **时间戳全部 UTC 存储**，前端本地化显示。
8. **每步提交前跑通**：后端 `dotnet build` + 现有测试；前端 `npm run build`。
