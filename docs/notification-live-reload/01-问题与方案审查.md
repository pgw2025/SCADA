# 01 · 问题与方案审查

## 1. 现象

- 变量值超限触发报警，**报警记录**中有该条记录（说明事件已进入报警系统）。
- 企业微信**群机器人没有收到推送**。
- 同一条 webhook 在「消息通知」界面点「发送测试消息」却**能正常收到**。

## 2. 根因链路

### 2.1 配置写入与发送读取走了两套数据源

| 环节 | 数据源 | 生效时机 |
|---|---|---|
| 保存 `PUT /api/NotificationConfig` | 写入 `appsettings.dboverride.json` 文件 | 只写文件 |
| `NotificationConfigService.GetAsync`（页面回显） | `IOptionsMonitor.CurrentValue` | 已在上一次修复动态化 |
| **发送链路**（sender / Service / Decorator） | **`IOptions<NotificationOptions>` 启动快照** | **进程启动时绑定一次，永不刷新** |

### 2.2 为什么「测试收到、正式报警收不到」

- 测试路径 `TestWeComAsync`：临时 `Options.Create({ Enabled=true, Webhook })` 构造 sender **直发**，**绕过**了父队列的渠道注册。
- 正式报警路径 `NotifyAlarmAsync` → `_queue.Enqueue`：先过 `_queue.HasEnabledChannels` 短路判断。

`ExternalNotificationService` 的渠道集合在**构造函数**里一次性构建：

```csharp
_states = senders
    .Where(s => s.Enabled)          // ① 启动时按快照过滤
    .Select(s => new SenderState { ... })
    .ToList();

public bool HasEnabledChannels => _states.Count > 0;   // ② 固定结果
```

而 `NotifyAlarmAsync`（`ExternalNotificationDecorator.cs:130-134`）的顺序是「先写记录、再判断渠道」：

```csharp
await _inner.NotifyAlarmAsync(evt);                                    // ① 报警记录先落，永远成功
if (!_queue.HasEnabledChannels || !_policy.PushAlarm) return;          // ② 快照里企微未启用 → 直接 return
```

结论：服务启动时企微 `Enabled` 还是 `false`（配置是启动之后才在页面保存的），`_states.Count == 0` → 报警被短路，**只有记录、没有推送**。重启后 `_states` 重建读到 `true`，于是能推送——与用户「重启就能收到」的观察完全一致。

### 2.3 为什么上一次修复没覆盖到这里

上一次把 `NotificationConfigService`（负责 `GetAsync` 回显）换成 `IOptionsMonitor`，只解决了「**页面读取**读回旧值」；`ExternalNotificationService`、`ExternalNotificationDecorator`、四个 sender 仍是 `IOptions` 启动快照，发送链路依旧读旧值。

## 3. 候选方案对比

### 方案 1：保持重启生效 + 提示（弃用）
保存响应/前端 toast 提示「发送渠道将在重启后生效」。
- 优点：零代码风险。
- 缺点：治标不治本，频繁改配置仍需重启。

### 方案 2：重建 `_states` 数组（弃用）
sender 改 `IOptionsMonitor`；`_states` 从可变 `List` 改为 volatile 数组，`OnChange` 触发 `RefreshChannels()` 整体替换，并管理新旧消费循环生命周期。
- 优点：思路直观。
- 缺点（致命）：
  1. **循环生命周期管理复杂**——被替换掉的 `SenderState` 的消费循环 Task 脱离 `_states`，`StopAsync` 第 157 行 `_states.Select(s => s.Loop)` 无法等待这些「僵尸循环」，停机时只能靠 `_cts.Cancel()` 兜底，可能丢在途消息；需额外维护 `_retiredLoops` 集合。
  2. **`OnChange` 由 FileSystemWatcher 驱动**，非原子写文件可能多次触发，虽可用 `SequenceEqual` 短期，但引入额外并发面。
  3. 需要「重建 Channel + 新建 SenderState + 排空旧循环」整套编排，改动面大、易错。

### 方案 2-S：sender 动态化 + 管道全量保留（选定）
- sender 改 `IOptionsMonitor`，`Enabled`/webhook 每次读取都是最新值。
- `_states` **不再按 `Enabled` 过滤**，永远保留全部 sender；「是否启用」下放到「扇出投递时」动态判断。
- `HasEnabledChannels` / `IsChannelEnabled` 改为动态读 `sender.Enabled`。

```csharp
// 全量保留（去掉 .Where(s => s.Enabled)）
_states = senders.Select(s => new SenderState { ... }).ToList();

public bool HasEnabledChannels => _states.Any(s => s.Sender.Enabled);  // 动态
public bool IsChannelEnabled(string name) =>
    _states.Any(s => s.Sender.Enabled &&
        string.Equals(s.Sender.Name, name, StringComparison.OrdinalIgnoreCase));

// FanoutAsync 投递前动态跳过
foreach (var state in _states)
{
    if (!state.Sender.Enabled) continue;   // 动态
    ...
}
```

- 优点：
  - **零 Channel 重建、零 volatile 数组、零 OnChange 订阅**（没有 FileSystemWatcher 抖动问题）、**零循环生命周期管理**。
  - `StopAsync` 照旧遍历全量 `_states`，无僵尸 Task。
  - 重试链路 `RetryAsync → IsChannelEnabled(log.Channel)` 依赖的 `IsChannelEnabled` 动态化后天然生效——渠道禁用后重试会被前置校验拦截。
- 代价（可接受）：未启用渠道也建 Channel/消费循环（空转，读空 Channel，开销可忽略；`RateBucket` 只在真正投递时才消耗）。

## 4. 选定理由

方案 2-S 是「让数据流动态化、而非让拓扑动态化」的取舍：
- 兼容性最好——不触碰 Channel/循环/停机顺序这些高风险区。
- 改动最小——8 个文件，每个都是「把启动快照换成 `IOptionsMonitor` 的动态读取」，模式高度一致。
- 无并发风险——不引入锁、不重建共享状态。

## 5. 生效边界

详见 [README §5](../README.md)。要点：**渠道开关/webhook、模板、Push* 策略开关即时生效；队列容量与每分钟限流仍重启生效**（它们参与 Channel/RateBucket 构造，属于构造期参数）。
