# 数据模型「历史存储策略」配置交互优化方案

> 状态：方案设计（未实施）
> 日期：2026-09-12
> 范围：数据模型页面「添加/编辑变量」弹窗中，历史存储策略（StoreMode / DeadBand / StoreIntervalMs）的配置交互
> 原则：**本方案只做设计，不修改代码**；仅涉及前端表单 `DataModelView.vue` 一处，不动后端 / 数据库 / 协议

---

## 1. 背景与问题

用户在数据模型页面添加变量时，遇到三类困惑：

| # | 用户诉求 | 现象 |
|---|---|---|
| 1 | 选择「存储历史数据」后，无法理解各存储模式能配什么 | 存储模式下拉框只有四个选项，选择后**没有任何对应的参数输入框** |
| 2 | 选择「变动存储」时，无法设置「值变化多少才存储」 | 死区阈值被放在另一个「工业级参数」区，与历史存储区割裂，用户意识不到它正是变化存储的触发阈值 |
| 3 | 选择「定时存储」时，无法设置「定时的时间是多少」 | `StoreIntervalMs`（存储周期）在前端**没有输入控件**，永远走默认值 300000ms（5 分钟） |

**核心结论**：后端存储能力完整（`DeadBand` 变化阈值、`StoreIntervalMs` 存储周期均已实现，并有 `VariableValueProcessorTests` 单元测试兜底）。问题 100% 出在**前端表单的参数缺失 + 信息割裂**，属于纯 UX 缺陷，不涉及功能缺失。

## 3. 设计原则

**「存储策略」作为一个整体配置块，选择模式后，该模式对应的参数就地展开 / 收起**，让用户一眼知道「当前模式能调什么、参数起什么作用」。核心是三点：

1. **参数随模式联动显隐**，而不是所有字段平铺、模式切换不动其他控件。
2. **死区阈值归入历史存储区**，并改名「变化阈值（死区）」，附解释文案。
3. **「定时存储」补出存储周期输入**，用工业用户熟悉的「数值 + 单位」而非裸毫秒。

## 4. 推荐交互结构

```
存储历史数据  [☑]

存储策略      [变化存储 ▾]

  ┌─ 变化存储 · Change ───────────────────┐
  │ 变化阈值（死区）  [ 1.0   ]            │
  │ 兜底周期          [ 5 分钟 ▾ ]          │
  │ 说明：|新值−上次存储值| > 阈值才写；    │
  │       长时间不变则每兜底周期强制存一条  │
  └────────────────────────────────────────┘

  ┌─ 定时存储 · Cycle ────────────────────┐
  │ 存储周期          [ 5 ] [ 分钟 ▾ ]     │
  └────────────────────────────────────────┘

  ┌─ 不存储 · None ───────────────────────┐
  │ （仅驻留内存，不写时序库，无参数）      │
  └────────────────────────────────────────┘
```

## 5. 三个具体问题的解法

### 问题 1：变化存储无法设置「变化的值」

- **方案**：把「死区阈值」从「工业级参数」区**移入「历史存储」区**，改名「**变化阈值（死区）**」，仅在 `StoreMode === Change` 时显示。
- **解释文案**：「只有当新值与上次存储值的差的绝对值**超过**该阈值时，才写入一条历史记录；设为 0 表示任何变化都记录。」
- **配套**：`StoreIntervalMs` 在 Change 模式下是「兜底周期」——值长时间不动也会每隔该周期强制存一条，避免趋势断档。应一并显示，文案标为「兜底周期」。

### 问题 2：定时存储无法设置定时时间

- **方案**：`StoreMode === Cycle` 时显示「**存储周期**」输入项，二选一：
  - **选项 A（推荐）**：「数值 + 单位下拉」（秒 / 分 / 时），内部换算成 ms 写入 `StoreIntervalMs`。工业用户习惯按秒 / 分 / 时思考，体验最好。
  - **选项 B**：裸毫秒输入框 + 实时换算提示（如「300000 ms = 5 分钟」），贴近后端字段、改动更小。
- 后端已有下限约束（`StoreIntervalMs ≥ 1000ms`），前端换算后应同样校验下限。

### 问题 3：压缩 / 聚合存储是空壳

- **方案**：前端暂**不展示**（或置灰标注「规划中」）`Compressed`、`Aggregated` 两个选项，待后端算法落地后再开放，避免「选了但没生效」的错觉。

## 6. 优先级与工作量

| 优先级 | 改动 | 说明 |
|---|---|---|
| **P0** | 补「定时存储周期」输入 | 用户最痛的点，也是最小改动 |
| **P0** | 死区阈值挪入历史存储区 + 改名「变化阈值」 | 让变化存储真正可调 |
| **P1** | 变化存储补「兜底周期」 | 同为 `StoreIntervalMs`，Change 模式下文案改为「兜底周期」 |
| **P1** | 隐藏 / 置灰 `Compressed`、`Aggregated` | 避免空壳误导 |
| **P2** | 变量列表「历史存储」列精细化 | 显示「变化存储 · 死区1.0」或「定时 5 分钟」，便于核对 |

总工作量约 **0.5~1 人日**（纯前端表单，集中在 `DataModelView.vue` 一个文件）。

## 8. 实施原则

1. **只动前端**：所有改动集中在 `Client/src/components/DataModelView.vue`，不动后端 DTO / 实体 / 运行时。
2. **字段映射不新增**：复用已有 `StoreMode` / `DeadBand` / `StoreIntervalMs` 三个字段，不引入新字段、新迁移。
3. **下限校验对齐**：前端周期换算后应遵守后端 `StoreIntervalMs ≥ 1000ms` 的下限。
4. **不破坏现有保存链路**：`varIsStored`、`varStoreMode`、`varStoreIntervalMs`、`varDeadBand` 的赋值 / 回填 / 保存逻辑（L311-400）保持不动，仅补模板输入控件。
