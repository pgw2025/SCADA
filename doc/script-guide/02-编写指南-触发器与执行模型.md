# 02 · 编写指南：触发器、授权与执行模型

> 本文讲清「脚本在什么时刻被谁调用、能碰哪些数据、跑在哪个线程上、跑挂了会怎样」。
> 理解执行模型，比会写 JS 更重要——系统脚本 90% 的"玄学问题"都出在这一层。

---

## 一、四种触发类型

| 触发类型 | 调用钩子 | 驱动来源 | 必填元数据 | 典型场景 |
|---|---|---|---|---|
| `Manual` 手动 | `run()` | 编辑器「运行」按钮 / `POST /api/SystemScript/{id}/run` / HMI 按钮 / 计划任务 / 事件联动 | 无 | 人工干预、按钮联动、被其它流程调用 |
| `Periodic` 周期 | `run()` | 调度循环 Tick（约 250ms）比对下次运行时间 | 执行间隔（秒，≥1） | 巡检、轮询统计、心跳检测 |
| `Schedule` 定时 | `run()` | Cron 表达式匹配（**时区固定 Asia/Shanghai**） | Cron 表达式 | 每日报表、班次切换、定时清零 |
| `OnChange` 变量变化 | `onChange(ev)` | 变量变化事件总线（采集线程发布） | 监听设备键 + 监听变量键 | 越限联动、报警响应、边缘触发控制 |

### 1.1 周期触发（Periodic）

- 下次运行时间 = **本次到点时刻 + 间隔**（不是"本次执行完 + 间隔"）。
  所以脚本执行耗时 1.5s、间隔 1s 时，不会积压——因为触发会被 `[BUSY]` 丢弃（见 §3.3）。
- 调度精度受 Tick 周期影响，约 **250ms** 量级。不要指望用它做毫秒级精确定时。
- 调度循环启动时会计算 `NextUtc = now + interval`，即**启用后第一个间隔才首跑**，不是立刻跑。

### 1.2 定时触发（Schedule，Cron）

使用 **Cronos** 库解析，时区固定为 `Asia/Shanghai`。

```
格式（6 段，含秒）：
  ┌───────── 秒 (0-59)
  │ ┌─────── 分 (0-59)
  │ │ ┌───── 时 (0-23)
  │ │ │ ┌─── 日 (1-31)
  │ │ │ │ ┌─ 月 (1-12)
  │ │ │ │ │ ┌ 星期 (0-6, 0=周日)
  * * * * * *
```

| 表达式 | 含义 |
|---|---|
| `0 */5 * * * ?` | 每 5 分钟的第 0 秒 |
| `0 0 8 * * ?` | 每天 08:00:00 |
| `0 30 8,20 * * ?` | 每天 08:30 与 20:30（班次切换） |
| `0 0 0 1 * ?` | 每月 1 号 00:00:00（月报） |
| `0 0 * * * ?` | 每小时整点 |
| `0 15 9 ? * MON` | 每周一 09:15 |

> **注意**：Cron 表达式非法时，脚本**本次不进入调度**（静默不跑），只在服务端日志里留一条 Warning。
> 保存前点「校验」，会用 Cronos 严格解析并给出错误。

### 1.3 变量变化触发（OnChange）

触发判定顺序（全部满足才入队）：

```
采集线程发布变量变化事件
  │
  ├─① 脚本 TriggerType == OnChange 且 Active 且未熔断？
  ├─② WatchDeviceKey + WatchVariableKey 与该事件完全匹配？（Ordinal 比较）
  ├─③ 死区：|新值 - 旧值| > DeadBand ？（DeadBand 为空则跳过此判据）
  └─④ 冷却：(now - 上次触发时刻) ≥ CooldownMs ？
        │
        └─ 全部通过 → 入队（微秒级返回，脚本不在采集线程上执行！）
```

三个参数怎么配：

| 参数 | 建议值 | 说明 |
|---|---|---|
| `DeadBand` | 模拟量：**量程的 0.5%–2%**；数字量：留空 | 防抖动。温度量程 100℃，填 `0.5` 比较合适 |
| `CooldownMs` | 默认 500；高频抖动源可到 2000 | 防回声与风暴。过小会导致写操作引发的变化再次触发自己 |
| `TimeoutMs` | 默认 2000 够用 | 真要下发多个写操作才需要调大 |

**⚠️ 回声陷阱**：`onChange` 里 `write()` 了**被监听的那个变量**本身，会立刻再次触发自己。
必须靠「状态判断 + 死区 + 冷却」三件套隔离：

```js
function onChange(ev) {
  // 只响应上升沿，且只在泵当前是停止状态时才动作
  if (!(ev.value > 80 && ev.previous <= 80)) return;
  if (read("TANK01", "CoolingPump") === true) return;   // 已经开了，别重复写
  write("TANK01", "CoolingPump", true);
}
```

## 二、元数据字段全表与取值范围

编辑器里的每个输入框，对应 `SystemScript` 实体一个字段。保存前由 `ScriptValidationService` 校验，
**`Error` 级问题会阻止保存**（前端先调 `/api/SystemScript/validate`）。

| 字段 | 表单名称 | 取值范围 | 校验规则 | 说明 |
|---|---|---|---|---|
| `Name` | 脚本名称 | ≤100 字符 | 必填 | — |
| `Code` | 脚本代码 | 无长度限制（DB `text`） | 必填 + Jint 语法解析 | 只解析不执行 |
| `TriggerType` | 触发类型 | `Manual`/`Periodic`/`Schedule`/`OnChange` | 必须是合法枚举名 | — |
| `IntervalSeconds` | 执行间隔 | 1 – 86400 | Periodic 必填 ≥1 | 单位秒 |
| `CronExpression` | Cron 表达式 | ≤100 字符 | Schedule 必填 + Cronos 可解析 | Asia/Shanghai |
| `WatchDeviceKey` | 监听设备键 | ≤64 字符 | OnChange 必填 | 与设备 `Key` 完全一致，大小写敏感 |
| `WatchVariableKey` | 监听变量键 | ≤64 字符 | OnChange 必填 | 与变量 `Key` 完全一致 |
| `DeadBand` | 死区阈值 | 任意 double | 选填，空 = 任意变化 | 仅 OnChange 生效 |
| `CooldownMs` | 冷却时间 | **100 – 60000** | 默认 500 | 仅 OnChange 生效 |
| `TimeoutMs` | 执行超时 | **500 – 30000** | 默认 2000 | 引擎侧还会再 Clamp 到同一区间 |
| `ScopeRead` | 读授权 | ≤1000 字符 | 选填，**空 = 拒绝全部** | `devA;devB;devC` |
| `ScopeWrite` | 写授权 | ≤2000 字符 | 选填，**空 = 拒绝全部** | `devA.var1;devA.var2` |
| `Active` | 启用 | bool | — | 停用后不进调度、不订阅 OnChange |
| `Version` | 版本 | int | 每次保存 **+1** | 执行记录里会存版本快照 |
| `FailureCount` / `Tripped` | 失败计数 / 熔断 | — | 引擎维护 | 保存时自动清零 |

### 校验的 6 类检查

1. 名称非空
2. 触发类型合法
3. 触发类型专属字段（间隔 / Cron / 监听键 / 冷却范围）
4. 超时范围 500–30000
5. **代码语法**：把代码包进 `(function(){ ... })` 只解析不执行——校验阶段绝不会运行你的代码
6. **软提示（Warning，不阻止保存）**：
   - 未声明对应钩子函数 → `未声明钩子函数 run()，该触发类型下脚本不会执行任何逻辑`
   - 代码里有 `read(` 但 ScopeRead 为空
   - 代码里有 `write(` 但 ScopeWrite 为空

> 第 6 类的钩子检测是**宽松子串匹配**（源码里查找 `function run`），写成
> `var run = function(){}` 或 `const run = () => {}` **检测不出来**（会给误报告警），
> 但运行时 `HasFunction` 是查全局值，**这两种写法运行时是有效的**。
> 建议老老实实写 `function run() {}`，人与机器都好读。

## 三、执行模型（重点）

### 3.1 线程模型：为什么脚本绝不能阻塞采集

```
DeviceWorker 采集线程 ──发布变化事件──┐
ScriptEngineHost 调度 Tick 线程 ──────┼──► 有界队列（默认容量 256）
Manual/Test (HTTP 线程) ─────────────┘         │
                                               ▼
                                    专用消费线程 ×N（默认 2，LongRunning）
                                               │
                                    同步执行 Jint 沙箱 + 写桥阻塞
```

**设计动机**：`write()` 是同步阻塞的真实网络 IO（上界 6s）。如果脚本在采集线程上跑，
一次慢写入就能拖停该设备的整个采集循环。所以所有执行都被推到**专用消费线程**上，
事件回调与调度 Tick 只做「入队」，始终保持微秒级返回。

对你的影响：

- 脚本**可以放心做多个 `write()`**，不用担心拖垮采集；
- 但消费线程只有 2 条（可配置），**脚本跑得慢会占用线程**，触发多了会丢队列；
- 同一脚本**串行**，不同脚本**并行**（最多 N 条同时跑）。

### 3.2 队列与丢弃

| 配置项 | 默认值 | 范围 | 说明 |
|---|---|---|---|
| `Scripting:QueueCapacity` | 256 | 8 – 10000 | 队满即丢弃新触发（`FullMode=Wait` + `TryWrite` 返回 false） |
| `Scripting:Consumers` | 2 | 1 – 16 | 专用消费线程数 |
| `Scripting:WriteBridgeTimeoutMs` | 6000 | 500 – 60000 | 单次 `write()` 同步等待上界 |

丢弃时：计数 +1，日志限流告警（30s 内最多一条），若为 Manual/Test 则立即返回 `Skipped` 结果。
**自动触发的丢弃不会写执行记录**——只在服务端日志里能看到：

```
脚本派发队列已满（容量 256），触发被丢弃：ScriptId=3 Trigger=Periodic；累计丢弃 12 次
```

### 3.3 并发互斥：`[BUSY]`

同一脚本 ID 在 `_inflight` 里存在租约时，新的触发**直接跳过**（不是排队）：

```
执行记录 Result = Skipped，Error = [BUSY] 上一次执行尚未结束，本次触发被跳过
```

**`[BUSY]` 不计入失败计数**，不会导致熔断。这是保护性的，不是错误。
但它意味着：**周期设得比脚本耗时短，你只会看到一部分执行**。看到大量 `[BUSY]` 就说明间隔该调大或脚本该优化。

### 3.4 超时：三层防御

| 层级 | 阈值 | 触发后果 |
|---|---|---|
| 脚本执行超时 `TimeoutMs` | 500–30000ms，默认 2000 | Jint 抛超时异常 → 结果 `Timeout` → 计入失败 |
| 写桥超时 `WriteBridgeTimeoutMs` | 默认 6000ms | `write()` 返回 `false`，脚本可继续跑；底层变孤儿任务 |
| 挂死看门狗 | 固定 **120s** | 兜底未知阻塞源。强制熔断脚本 + 释放租约 + 落 `Timeout` 记录 |

看门狗释放租约后**被占用的消费线程无法回收**（.NET 没有 `Thread.Abort`）。
所以：**不要让脚本接近 120s**。真有长任务就拆成多个周期脚本 + 变量记状态。

### 3.5 熔断：连续失败 3 次自动停摆

```
失败（抛异常 / 超时）→ FailureCount +1
                    ├─ < 3：继续调度
                    └─ ≥ 3：Tripped = true → 调度器跳过（Skipped / [TRIPPED]）
```

| 操作 | FailureCount | Tripped |
|---|---|---|
| 执行成功 | 清零 | 保持 |
| 执行失败 / 超时 | +1 | ≥3 置 true |
| `Skipped`（BUSY/TRIPPED/队列满/未运行） | **不变** | 不变 |
| **保存脚本**（新增或编辑） | 清零 | **false** |
| 「复位熔断」按钮 / `reset-tripped` | 清零 | false |
| 手动「运行」 | 视执行结果 | **可绕过**（即使已熔断也会跑） |

> 因为保存会复位熔断，**线上脚本出问题后先别急着改代码**——先去看执行记录里的 `Error` 列，
> 否则一保存就把现场证据（FailureCount/LastError）清掉了。

### 3.6 无状态性（最重要的一条）

**每次执行都新建一个 `ScriptSandbox`，执行完即弃。** 因此：

```js
var counter = 0;                  // ❌ 每次执行都是 0，累加无效
var lastAlarmTime = null;         // ❌ 每次执行都是 null

function run() {
  counter++;
  log(counter);                   // 永远是 1
}
```

**要跨执行保存状态，只能写进变量**（并授予写授权）。见 [示例 12（滑动滤波）](./examples/12-指数平滑滤波.js) 与
[示例 14（能耗累计）](./examples/14-能耗累计与定时清零.js)。

配合这条，还有一个**顶层代码陷阱**：

```js
// 顶层代码每次执行都会跑一遍
var CONFIG = { max: 80 };          // ✅ 常量声明，无害

log("初始化");                      // ❌ 输出会被清空，永远看不到
write("DEV", "Reset", false);      // ☠️ 危险！每次执行都会真实下发一次写操作

function run() { /* ... */ }
```

**规则：顶层只放 `function` 声明与常量，其它一律放进钩子。**

## 四、授权模型（ScopeRead / ScopeWrite）

### 4.1 两个授权串的语法

```
ScopeRead  = "TANK01;PUMPGRP;KILN01"                 设备键，分号分隔，粒度=设备
ScopeWrite = "TANK01.CoolingPump;TANK01.ValveIn"     "设备键.变量键"，粒度=变量
```

- 解析规则：`Split(';', RemoveEmptyEntries | TrimEntries)`，即**自动去空项与两端空格**；
- 比较用 `Ordinal`——**大小写敏感、无通配、无前缀匹配**；
- **空串或全空白 = 拒绝全部**；
- 写授权**不支持设备级**（设计上禁止写 `TANK01` 就想写它所有变量）。

### 4.2 越权行为对照表

| 调用 | 越权时返回值 | 输出缓冲追加 | 是否计入失败 |
|---|---|---|---|
| `read()` | `null` | `[DENIED] read X.Y：设备 [X] 不在读授权列表` | 否（本次仍 Success） |
| `getQuality()` | `"Unknown"` | `[DENIED] getQuality X.Y：...` | 否 |
| `write()` | `false` | `[DENIED] write X.Y：不在写授权列表（需精确到 设备键.变量键）` | 否 |

**关键：越权不会让脚本失败，只会让它"安静地什么都不做"。**
排查脚本无效果时，第一件事就是看输出里有没有 `[DENIED]`。

### 4.3 最小权限原则

只勾真正用到的：

- 只读不写 → 只配 ScopeRead（ScopeWrite 留空，防止误写）
- 只写不读 → 只配 ScopeWrite（但控制脚本通常两边都要，因为要先读状态）
- 一个脚本管一台设备 → 不要为了省事把所有设备都勾上

### 4.4 删除变量时的联动清理

删除设备变量时，`ScriptVariableCleanupHelper` 会自动：

1. **停用**以该 `设备键.变量键` 为 OnChange 监听目标的脚本，并在 `LastError` 注明
   `监听变量已被删除，脚本已联动停用（X.Y）`；
2. 从所有脚本的 `ScopeWrite` 中**剔除**该条目。

**注意它不会自动停用引用了该变量的 `read()` 调用**——那些 `read()` 会开始返回 `null`。
所以删变量后请人工复查引用它的脚本。

## 五、试运行（dry-run）与手动运行的差异

| 维度 | 试运行 Test | 手动运行 Manual |
|---|---|---|
| 需要保存 | 否 | 是（需要有 ID） |
| 读取变量 | **真实读取** | 真实读取 |
| 写入变量 | **不真写**，输出 `[DRY-RUN] 写入 X.Y = v`，返回 `true` | 真实写入 |
| 落执行记录 | 否 | 是 |
| 更新熔断/失败计数 | 否 | 是 |
| 绕过熔断 | 是 | 是 |
| OnChange 脚本 | 传入 监听设备键+变量键 构造 `ev`，调 `onChange(ev)` | 调 `run()`（OnChange 脚本手动跑会 Skip） |
| 等待上界 | 120s（含排队） | 120s（含排队） |

> 试运行时 `write()` 返回 `true`（假装成功），所以**不要用 `if (write(...))` 的分支在试运行里验证后续逻辑**——
> 它永远走成功分支。

## 六、最佳实践清单

### ✅ 推荐

1. **每个读值都判质量**（`getQuality(...) === "Good"`）再使用。
2. **早返回**：条件不满足立刻 `return`，别嵌套一堆 `if`。
3. **控制输出限幅**：`Math.min(max, Math.max(min, v))`，别把未限幅的计算值直接下发。
4. **用 `log()` 打关键决策点**：输入值、判断结果、写入结果。排查时这就是黑匣子。
5. **关键写操作检查返回值**并记录失败原因。
6. **常量提取到顶层**（`var MAX_TEMP = 80;`），便于批量修改。
7. **状态存变量**，接受无状态性。
8. **超时设够**：一次 `write` 最坏 6s，写 3 个变量就把 `TimeoutMs` 提到 20000 左右。
9. **先试运行再上线**，试运行不会有任何副作用。
10. **周期宁长勿短**：看到 `[BUSY]` 就调大间隔。

### ❌ 反模式

| 反模式 | 后果 | 正确做法 |
|---|---|---|
| 用 `console.log()` | `ReferenceError` → 3 次熔断 | `log()` |
| `var` 变量跨执行累加 | 永远是初始值 | 写进变量持久化 |
| 顶层写 `write()` | 每次执行都真实下发一次 | 放进钩子 |
| 顶层写 `log()` | 输出被清空，白写 | 放进钩子 |
| 不判质量直接算控制量 | 用坏数据控制物理设备 | 先 `getQuality` |
| 死循环 / 无限递归 | 超时或递归超限 → 熔断 | 加迭代上限 |
| OnChange 里写回被监听变量 | 回声风暴 | 沿判断 + 状态判断 + 冷却 |
| 周期 1s 但脚本要 3s | 大量 `[BUSY]`，实际执行频率远低于预期 | 调大间隔或优化脚本 |
| 用 Promise / async | 静默失效，代码不执行 | 全同步写法 |
| 一个脚本塞 500 行业务 | 超时、难排查、故障面大 | 按设备/功能拆分 |
| 脚本里做高频换算 | 走队列，延迟 250ms 级 | 用变量的工程换算表达式 |
| 授权全勾图省事 | 越权风险，误写其它设备 | 最小权限 |

## 七、脚本的三条外部触发入口

除了编辑器里的「运行」和自动调度，脚本还能被三处引用：

### 7.1 HMI 画面按钮（运行态）

组态编辑器里给按钮控件配置动作 `buttonMode = 'runScript'` + `props.targetScriptId = <脚本ID>`。
运行态点击按钮 → `POST /api/ScriptRuntime/{id}/run`。

- **权限**：`Operator` 与 `Admin` 均可（与变量写入口径一致），`Viewer` 被拒 403。
- 这意味着**操作员可以在画面上点按钮跑脚本**，脚本的 `ExecutedBy` 记录为操作者用户名。
- 脚本本身不要求 TriggerType 必须是 Manual——任何脚本都能被按钮触发，但只有声明了 `run()` 的才有逻辑可执行。

### 7.2 事件联动（EventPanel）

在事件联动配置里添加动作「运行系统脚本」，选择目标脚本 ID。
事件（如报警触发）发生时执行脚本。

### 7.3 计划任务（ScheduledTask）

计划任务类型 `execute_script`，参数 JSON：

```json
{ "scriptId": 12 }
```

由 `ExecuteScriptTaskExecutor` 调用 `RunAsync`，执行人记为 `计划任务:{任务名}`。
任务成功/失败判定：结果为 `Success` 或 `Skipped` 视为成功，其余抛异常（由计划任务框架记录失败）。

> 三种入口都走同一条链路：**入队 → 专用线程 → 沙箱 → 落记录 → 推送**。
> 因此它们共享熔断状态、并发互斥（`[BUSY]`）与授权检查。
> 一个外部入口频繁触发，同样会让自动调度吃到 `[BUSY]`。
