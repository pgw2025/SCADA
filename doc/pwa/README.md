# 前端 PWA 改造（Progressive Web App）方案文档

## 1. 背景与目标

当前前端（`Client/`，Vue 3 + Vite 6 + TypeScript）是纯浏览器 SPA：无 manifest、无 Service Worker、无图标资产，不具备安装能力与离线能力；报警通知依赖用户停留在页面内（SignalR + 站内通知中心）。

本方案将前端改造为 PWA，实现四个目标（经与用户确认全选）：

1. **可安装 + 原生体验**：添加到桌面/主屏，独立窗口、启动画面、全屏运行，像本地 App 一样使用；不拆分独立轻量入口，保持现有完整 SPA 形态。
2. **离线可用（核心壳）**：Service Worker 预缓存 App Shell，断网/弱网时壳界面与已缓存页面秒开；实时数据仍依赖网络。
3. **报警推送通知**：Web Push 推送，即使页面关闭/浏览器退出，报警触发也能弹系统级通知；与现有报警/通知体系联动。
4. **离线数据兜底**：断网时用 IndexedDB 快照展示最近一次设备/变量/报警数据，联网后自动恢复刷新。

**硬前提已确认**：生产环境已具备 HTTPS（PWA 的 SW 与 Push 强制要求）。

## 4. 核心设计决策（速览）

| # | 决策 | 理由 |
|---|---|---|
| D1 | SW 采用 **`injectManifest` + 自定义 `sw.ts`**（而非 `generateSW` 全自动生成） | P4 推送需要在 SW 内写 `push`/`notificationclick`/`pushsubscriptionchange` 自定义事件处理器，generateSW 不支持；一步到位避免阶段返工 |
| D2 | SW 更新策略采用 **`prompt` 模式**（新版本就绪后提示用户手动刷新，而非 autoUpdate 静默重载） | 组态大屏/报警监控长驻无人值守，发版瞬间静默重载会打断盯屏操作工（画面闪断、上下文丢失） |
| D3 | 推送订阅与**登录会话解耦**：订阅绑定「用户+浏览器」，登录时换绑、登出时**保留** | 报警推送的价值恰恰在"人不在系统前"；登出即清订阅 = 推送只在活跃会话内有效，等于没做 |
| D4 | API 运行时缓存采用**白名单**（设备/变量/报警/组态等只读 GET），显式排除 `/api/Auth/*`、用户管理、系统配置、`/open/*`、`/hubs/*` | 全量缓存 `/api/*` 会把带账号上下文的个性化数据（如按授权过滤的工程列表）泄漏给下一个账号（车间公用一体机 kiosk 场景）；缓存 `/me` 会让已吊销会话离线"复活" |
| D5 | 登出 / 换号登录 / 401 强登出三条路径统一触发 **`CLEAR_USER_DATA`**：SW 删 api-runtime 缓存 + 页面清 IndexedDB 快照 | 跨账号数据安全三道防线之一（与 D4 白名单、快照 userId 命名空间互为兜底） |
| D6 | 推送落地页**按订阅者角色计算**（Admin → `/alarm-management`；Operator/Viewer → `/scada-view`），且通知正文本身携带报警摘要（设备/变量/级别/时间） | `/alarm-management` 是 `ADMIN_ROLES` 限定路由，操作工点击会被守卫弹回 `/scada-view`，推送闭环断裂；不新建只读报警页，规避「报警管理唯一入口」约束冲突 |
| D7 | 后端推送作为**第三个 `IExternalMessageSender` 渠道**接入现有通知管线（与钉钉/邮件并列），不直接 hook `AlarmRuleEngine` | 现有 `ExternalNotificationService` 已具备有界队列/渠道隔离/限流/超限合并/指数退避/优雅停机全套治理；`ExternalNotificationDecorator` 已有事件过滤+模板渲染+去抖，白得这些能力且通知行为跨渠道一致 |
| D8 | `ExternalMessage` 增加可选结构化字段（`Severity` + `Tokens` 上下文字典），由装饰器填充 | Web Push 需要结构化数据构造 payload 与过滤（解析 Markdown 文本太脏）；可选字段向后兼容，钉钉/邮件渠道不受影响 |
| D9 | IndexedDB 快照写入**节流**：定时器（默认 10s）一拍 + `visibilitychange`/`pagehide` 强制落盘，绝不逐条 SignalR 推送即写 | 吸取「高频更新需 batching pump」教训，防止高频变量更新打爆主线程 |
| D10 | 离线兜底只承诺「壳 + 最近快照」，UI 显示「离线模式 · 数据截至 HH:mm:ss」时间戳 | SCADA 本质是实时联机系统，离线快照不是实时值；明确新鲜度防止操作工误判 |
| D11 | 通知权限请求必须由**用户手势触发**（设置页显式开关），不首屏自动 `requestPermission()` | 浏览器策略对无手势权限请求趋于拦截，且体验差 |
| D12 | SW 监听 `pushsubscriptionchange` 自动续订并重新绑定 | 浏览器推送订阅会静默过期（Chrome 数月不用即失效），不处理则报警推送悄悄失联——对报警系统是隐性事故 |
| D13 | `.NET` 侧 Web Push 库选型 `WebPush`（web-push-csharp，NuGet），阶段五第 1 步先做**真机技术预验证**再全面实施 | .NET 生态无官方一等库，社区库对新版浏览器 RFC 8291（aes128gcm）支持度必须先验证 |
| D14 | VAPID 密钥存 `appsettings.json`（生产经 override/环境变量覆盖），**单实例部署**为前提，密钥轮换 = 全部订阅失效（运维红线） | 多实例需共享密钥；轮换会让所有 `PushSubscription` 失效，必须记录在运维文档 |

## 5. 边界与不做的事

- **不拆分轻量安装入口**：PWA 保持现有完整 SPA 形态（用户已确认）。
- **不缓存 SignalR 实时通道**：`/hubs/*` WebSocket 归 `withAutomaticReconnect` 自管，SW 不介入。
- **不新建只读报警页**：操作工推送落地到 `/scada-view`（既有路由），通知正文承载报警摘要（见 D6）。
- **不做离线写操作**（配置修改/报警确认等离线排队同步）：工业系统写操作离线语义复杂且风险高，超出本期范围。
- **不修改现有后端通知管线行为**：装饰器/队列/既有渠道的既有逻辑零变更，仅做加法（新渠道 + DTO 可选字段）。
