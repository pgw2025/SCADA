# 01 - 现状分析与方案审查

> 本文档记录 PWA 改造前的代码库现状事实（作为设计依据），以及 v1 方案的审查结论与 v2 修订。所有文件引用均基于改造前的代码状态。

## 1. 前端现状事实

### 1.1 技术栈与工程结构

| 项 | 事实 | 出处 |
|---|---|---|
| 框架 | Vue 3.5 + TypeScript 5.8 + Vite 6 | `Client/package.json` |
| 路由 | `vue-router` 4，`createWebHistory()`（HTML5 history 模式） | `Client/src/router/index.ts` |
| 状态 | Pinia 风格 store（`scadaStore`/`deviceStore`/`alarmStore`/`userStore`/`systemStatusStore` 等，经 `Client/src/store/index.ts` 统一导出） | `Client/src/store/` |
| HTTP | 单一 axios 实例（无 baseURL，相对路径），统一 JWT 注入与 401 处理 | `Client/src/api/http.ts` |
| 实时 | SignalR `/hubs/scada`，`withAutomaticReconnect`，token 从 localStorage 取 | `Client/src/services/signalRService.ts` |
| 构建 | `vite build` 产出 `Client/dist/`，生产由 nginx/反代托管（vite.config.ts 注释自述） | `Client/vite.config.ts` |

### 1.2 与 PWA 相关的关键现状

1. **无任何 PWA 基础**：`Client/public/` 目录不存在；`index.html` 无 `<link rel="manifest">`、无 favicon、无 apple-touch-icon；全库无 service worker 代码。图标资产需从零制作。
2. **入口加载链**：`index.html` 内置 boot-loading 启动动画（深浅色自适应）→ `main.ts` 的 `boot()` 先 `initializeAuth()` 回源 `/me` → `router.isReady()` → 挂载。SW 注册应插入此链路（挂载后异步注册，不阻塞首屏）。
3. **鉴权与 token**：JWT 存 `localStorage['scada_access_token']`（`TOKEN_KEY`）；`http.ts` 响应拦截器在 401 且非 Auth 流程请求时**清除 token 并重置登录态**（三条登出路径之一）；`initializeAuth` 对网络错误**沿用本地快照**（离线启动可进入已登录壳界面——这是离线兜底的现有有利条件）。
4. **路由角色边界**：
   - `/` 公开（App.vue 渲染登录界面）；
   - `/alarm-management`、`/notification-center`、`/settings-center` 等管理页均 `roles: ADMIN_ROLES`（仅管理员）；
   - `/scada-view` 与 `/scada-view/:projectId` 所有已登录角色可访问，后者 `standalone: true`（无系统菜单，纯播放器）。
   - **对推送的影响**：通知点击落地页不能统一指向 `/alarm-management`（操作工会被守卫弹回），见 v1 审查问题 P5。
5. **SignalR 事件面**（快照数据来源）：`ReceiveVariableUpdate`（变量值）、`ReceiveDeviceStatus`（设备状态）、`ReceiveAlarm`（报警事件）、`ReceiveSystemAlarm`（系统告警）、`ReceiveScriptExecution`（脚本执行）。
6. **Vite 手动分包**：`widget-templates/builtinSeeds/builtinRenderers/widgetRegistry` 强制并入 `widget-template` chunk（消除 Rollup 循环引用 warning）。**PWA 预缓存会缓存所有 chunk，需关注 dist 体积**。
7. **dev 代理**：`/api`、`/open`、`/hubs`（含 ws）代理到 `http://localhost:5555`。生产由 nginx 处理同路径转发。
8. **`package.json` 脏依赖（脚手架残留）**：项目名 `react-example`，混入 React 19、`express`、`@google/genai`、`lucide-react` 等与实际（Vue 应用）无关的依赖。PWA 改造仅新增 `vite-plugin-pwa`（devDependency），**清理脏依赖不在本期范围**，但安装时需注意 peer 依赖与 Vite 6 的版本匹配。

### 1.3 未验证的部署假设（阶段一第 1 步落实）

| 假设 | 风险 | 验证动作 |
|---|---|---|
| nginx 已有 SPA `try_files` 回退（托管 `dist/`） | 若无回退，深链刷新 404；SW 离线导航兜底救不了在线深链 | 索取/检查 nginx 配置 |
| `sw.js` 可设置 `no-cache` 响应头、manifest 可返回正确 `Content-Type` | SW 被 HTTP 缓存卡住旧版本，更新流程失效 | nginx 增加 location 规则 |
| 部署在根路径（非子路径） | 影响 `start_url`/`scope`/图标绝对路径 | 确认部署 URL |
| 后端单实例部署 | VAPID 私钥本地持有的前提；多实例需共享 | 确认部署形态 |
| HTTPS 证书浏览器受信 | 用户已确认具备 HTTPS；自签/内网 CA 需单独验证推送可用性 | 真机访问验证 |

## 2. 后端现状事实（本方案最重要的现状）

### 2.1 外部通知管线（已建成，Web Push 的集成点）

后端已存在一条**完整的外部通知管线**，本方案不重造，直接作为渠道接入：

```
采集/报警管线（VariableValueProcessor / AlarmRuleEngine / 设备状态 / SystemLogRecorder）
        │ 调用
        ▼
IScadaNotificationService（接口）
        │ 实现为
        ▼
ExternalNotificationDecorator（装饰器，Server/ScadaServer.WebApi/Services/）
  ├─ 内包裹 SignalRNotificationService（站内实时推送，行为不变）
  ├─ 按策略过滤：变量更新不外发；设备状态仅 Offline(可配)/Fault 外发且按设备去抖；
  ├─ NotificationTemplateEngine 用可配置模板渲染 Title/Markdown/HtmlBody（占位符：deviceKey/variableName/level/threshold/actualValue/time…）
  └─ 非阻塞 Enqueue(ExternalMessage) 入有界主队列（DropWrite）
        │ 扇出
        ▼
ExternalNotificationService（HostedService，Server/ScadaServer.WebApi/HostedServices/）
  ├─ 主队列（有界 DropWrite）→ 扇出循环
  ├─ 每启用渠道独立有界通道 + 独立消费循环（渠道完全隔离）
  ├─ 每渠道固定窗口限流（RateBucket，MaxPerMinutePerChannel）
  ├─ 超限消息合并计数（下一条捎带说明）
  ├─ 失败重试（指数退避）；优雅停机（扇出 ≤3s + 发送 ≤22s，契合 ShutdownTimeout=30s）
        │ 渠道
        ▼
IExternalMessageSender[]（Name/Enabled/SendAsync）
  ├─ DingTalkRobotClient（已实现）
  └─ EmailSender（已实现）
```

**关键结论**：把 Web Push 实现为第三个 `IExternalMessageSender`，可直接复用限流、超限合并、退避重试、渠道隔离、优雅停机、事件过滤、模板渲染、设备状态去抖——不需要在报警管线里另起炉灶。这印证并强化了 v1 审查中的优化建议。

### 2.2 现有管线的两个限制（设计需要解决）

1. **`ExternalMessage` 是广播模型，无接收人字段**（`Category`/`Title`/`MarkdownText`/`HtmlBody`/`CreatedAtUtc`）。钉钉 webhook/邮件收件人是渠道级配置，天然广播；而 Web Push 必须按「订阅 + 订阅者角色」逐条定向。
   → **解法**：DTO 增加可选结构化字段（`Severity`、`Tokens`），`WebPushSender` 内部查询有效订阅并逐订阅构造 payload（含角色感知落地 URL）。见详细设计 §5。
2. **`ExternalMessageCategory` 无严重度**（Alarm/DeviceStatus/SystemAlarm/SystemError/ScriptExecution）。推送过滤需要级别维度（如仅 ≥Error 推送）。
   → **解法**：装饰器构造 Alarm 消息时填充 `Severity`（来自报警级别枚举），WebPushSender 据此过滤。

### 2.3 配置体系

- 主库连接配置在 `appsettings.dboverride.json`（最后加载覆盖）。VAPID 密钥同法：基线 `appsettings.json` + 生产 override。
- 时间戳约定全系统 UTC，前端本地化显示——推送 payload 时间字段沿用 UTC，SW 显示时转换。

## 3. v1 方案审查：发现的问题

### 3.1 设计级问题（5 个，v2 已修订）

| # | 问题 | v1 原设计 | v2 修订 |
|---|---|---|---|
| P1 | **SW 模式与推送冲突** | P0–P2 用 `generateSW`（全自动），P3 推送需自定义 `push`/`notificationclick` 处理器，generateSW 做不到，P3 要整体迁移 SW 架构返工 | P0 起即用 **`injectManifest` + 自定义 `sw.ts`**（D1） |
| P2 | **「登出清空推送订阅」与推送初衷矛盾** | 登出清订阅防串号 → 推送只在活跃会话有效，页面关闭/浏览器退出后收不到通知，报警推送等于没做 | 订阅与登录会话**解耦**：登录时换绑当前账号、登出**保留**订阅（D3） |
| P3 | **跨账号数据泄漏（安全）** | SW 缓存全量 `/api/*` GET + IndexedDB 全量业务快照，存的是账号个性化数据（含按授权过滤的工程列表）；车间公用一体机换号后，新账号离线时可读到前一账号视角的数据 | 三道防线：登出/换号/401 三路径统一 `CLEAR_USER_DATA` 清缓存+清快照；API 缓存改**白名单**；快照按 userId 命名空间（D4/D5） |
| P4 | **更新策略自相矛盾** | `autoUpdate` + "提示用户手动刷新" 互斥：autoUpdate 是新 SW 激活后自动重载页面，长驻大屏被发版打断 | 改 **`prompt` 模式**：`onNeedRefresh` 回调展示横幅，用户择机应用（D2） |
| P5 | **推送落地页权限缺口** | 通知点击统一跳 `/alarm-management`，该路由 `ADMIN_ROLES` 限定；Operator/Viewer 点击被守卫弹回 `/scada-view`，看不到报警详情，闭环断裂 | 落地页**按订阅者角色计算**（后端逐订阅生成 payload）：Admin→`/alarm-management`，Operator/Viewer→`/scada-view`；且通知正文自带报警摘要，不依赖落地页也能获得关键信息；不新建只读报警页（守「报警管理唯一入口」约束）（D6） |

### 3.2 未验证假设（3 个，转为阶段一/阶段五的验证步骤）

| # | 假设 | 处置 |
|---|---|---|
| A1 | nginx SPA 回退 / SW 缓存头 / 部署路径 | 阶段一第 1 步「生产环境前置确认」，不通过则先修部署 |
| A2 | .NET Web Push 库可用性（RFC 8291 aes128gcm 对新浏览器） | 阶段五第 1 步「真机技术预验证」，先跑通一条真实推送再实施（D13） |
| A3 | 单实例部署 / VAPID 密钥管理 | 阶段一确认；多实例需共享密钥；轮换=订阅全失效，记运维红线（D14） |

### 3.3 优化点（13 项，已吸收进 v2）

1. 推送挂点改到现有通知管线（→ 已升级为 D7 核心架构，因后端管线比 v1 设想的更完整）。
2. IndexedDB 快照写入节流（定时 + pagehide 落盘），不逐条 SignalR 推送即写（D9）。
3. NetworkFirst 加 `networkTimeoutSeconds: 3`（车间弱网防挂起）。
4. `/open/*`（开放 API 网关）显式排除缓存。
5. 离线横幅带「数据截至 HH:mm:ss」时间戳（D10）。
6. 通知权限由用户手势触发（D11）。
7. 推送频率治理：级别过滤（默认 ≥Error 可配）、同规则 `tag` 折叠、Recover 通知可选。
8. SW 监听 `pushsubscriptionchange` 自动续订（D12）。
9. iOS 边界写进使用说明：iOS 16.4+ 且**仅已安装到主屏的 PWA** 支持 Web Push。
10. 图标资产从零制作（192/512/maskable/favicon/apple-touch-icon）。
11. `maximumFileSizeToCacheInBytes` 控制预缓存体积（懒加载 chunk 全量预缓存）。
12. 快照「存储被回收」降级：快照只是加速器不是依赖，丢失时冷启动必须正常。
13. `package.json` 脏依赖（react-example 残留）不在本期清理，但新增依赖时注意 peer 匹配。

## 4. v2 修订后的方案形态

v1 → v2 的阶段结构对照：

| v1 阶段 | v2 阶段 | 主要变化 |
|---|---|---|
| P0 基础 | 阶段一 + 阶段二 | 新增「前置确认」与「图标资产」独立步骤；SW 直接 injectManifest |
| P1 原生体验 | 并入阶段二 | iOS 安装引导、standalone 适配 |
| P2 离线壳 | 阶段三 | 白名单、prompt 更新、CLEAR_USER_DATA、离线横幅 |
| P3 前端推送 | 阶段四 | 订阅生命周期解耦、用户手势权限、自动续订、角色落地 |
| P4 后端推送 | 阶段五 | 挂 `IExternalMessageSender` 渠道（非 hook AlarmRuleEngine）；库预验证前置；`ExternalMessage` 结构化扩展 |
| P5 离线快照 | 阶段六 | 节流写入、换号清空、回收降级、时间戳横幅 |
| （无） | 阶段七 | 端到端验收：跨账号安全专项、兼容性矩阵、发布演练 |
