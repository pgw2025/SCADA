# 01 · 方案审查与修正

> 本文记录「连接配置级单例共享」最初草案的代码级审查结论：**方向正确、耦合点定位准确，但存在 1 处重大过设计与 3 个实质性缺口**。修正结论直接构成 [02-执行计划.md](02-执行计划.md) 的输入。
> 审查基于 2026-09-04 的代码现状（`feature/runtime-refactor` 分支）。

***

## 0. 已验证的事实基础（草案说对的部分）

| 事实 | 证据 |
|---|---|
| 驱动绑单设备：`ConnectAsync(IRuntimeDevice)` 入参是设备运行时 | `ScadaServer.Domain/Interfaces/IProtocolDriver.cs:27` |
| 每设备各建驱动：`CreateDriver` + `ConnectAsync(runtime)` 逐设备执行 | `ScadaServer.Runtime/RuntimeManager.cs:476-481`（`BuildAndRegisterDeviceAsync`） |
| 数据层多对一已成立，无需迁移 | `Device.ConnectionId` FK + `DeviceConnection` 实体；`DeviceAppService.ResolveAttachConnectionAsync` 明确「可能与其他设备共享」 |
| 快照/历史/报警/推送按设备粒度组织，保留设备运行时可保数据归属正确 | `DeviceWorker` 全链路以 `_runtime.Device.Id/Key` 落库（InfluxDB tag：`device_key`+`variable_key`） |
| 两个真实驱动已并发安全 | `S7Driver`：全程 `_plcLock` 串行化 + 锁内复检终态；`OpcUaDriver`：Session 快照 + IO 引用计数（`AcquireSessionForIoAsync`/`ReleaseSessionIoAsync`） |
| 读/写接口本来就是变量粒度 | `ReadAsync(IRuntimeVariable)` / `WriteAsync(IRuntimeVariable, object)` 均不带设备参数 |

***

## 1. 问题 A（最大）：阶段 3「调度上移、共享 Worker」是过度设计

草案阶段 2/3 提出「驱动不再自己轮询，轮询调度上移到 `ConnectionSession`，由共享 Worker 调度该连接下全部设备变量」。

**该前提不成立**：驱动从来就不轮询——轮询一直在 `DeviceWorker`（`ScadaServer.Runtime/Devices/DeviceWorker.cs:105-336`）。更重要的是 Worker 内嵌大量**设备级业务状态**，合并到连接级意味着全部按设备命名空间重做：

- `_alarmStates`：Min/Max 兜底报警去重状态机（L43）
- `_ruleStates`：规则报警防抖/去重状态机（L48，key = `variableKey#ruleId`）
- 历史写入死区判定（`IsEffectiveChange`，L456）
- `ReconnectAfterConsecutiveFailures` 断线判定（L54）
- 实时快照 / 历史入队 / SignalR+MQTT 推送的完整链路

而读/写接口已经是变量粒度且驱动并发安全——**多设备共享一个驱动实例时，各自 Worker 并发调用同一驱动是安全的**（S7 串行锁天然排队；OPC UA 引用计数保护会话）。

**修正**：最小正确改造 = 只共享 Driver 实例，`DeviceWorker`/`DeviceScheduler` 结构不动。草案中标注为「最大工作量」的阶段 3 整体删除，替换为「会话级重连归口」（见问题 B）与「Worker 批读启用」（见问题 D）。

***

## 2. 问题 B（真缺口）：重连触发权错配

现状断链判定在 Worker 内：`ConsecutiveFailureCount >= 3` → `NeedsReconnect = true` → 调度器触发 `ReconnectDeviceAsync(deviceId)` → **销毁该设备驱动**（`DeviceWorker.cs:304-311`、`RuntimeManager.cs:284-324`）。

共享驱动后会出现两类事故：

1. **无辜拖累**：设备 A 判定断线并 Dispose 共享驱动时，设备 B 的 Worker 正在用同一驱动读数据——B 被拖成连续失败，又独立触发一次重连。
2. **并发重连风暴**：同一连接下多台设备同时失败 → 多个 `ReconnectDeviceAsync` 并发对同一会话重建，无去重。

草案阶段 5 只写了「重连粒度改为连接级」，**没有给出触发机制的重设计**——这是必须补的核心设计，不是实现细节：

- 通讯失败信号从 Worker 上抛到会话（聚合）；
- 会话统一判定断连、**探测确认**（避免「全部变量地址配错」的设备反复触发健康连接的重建——现状本身就是每 3 轮重建一次的 flapping 缺陷）、**闸门去重**（同一时刻至多一次重建）；
- **设备运行时不随会话重建**：只换驱动，变量值/报警计数/RunState 全部存活，重连窗口内快照不消失（顺带消灭 `runtime 重连窗口 404` 的根因，而非继续用 `_reconnecting` 补丁掩盖）。

## 3. 问题 C（缺口）：生命周期三处未定义

| # | 缺口 | 现状证据 | 必须补的规则 |
|---|---|---|---|
| C1 | 引用计数 | `RemoveDeviceAsync` 无条件 Dispose 驱动（`RuntimeManager.cs:357`） | 会话「首设备挂载创建、末位设备离场销毁」；中间启停设备只挂载/卸载 |
| C2 | 写入门禁 | `WriteVariableAsync` 检查 `runtime.Driver == null` 与 `ConnectionState`（`RuntimeManager.cs:721-724`） | 门禁改为查询所属会话状态；否则会话重建中写入会绕过门禁或误判 |
| C3 | ConfigJson 热编辑 | 最近刚交付「被引用连接仍可编辑参数」功能（`DeviceConnectionAppService.UpdateAsync` 允许改 ConfigJson） | 改 ConfigJson / ReconnectIntervalMs → 触发会话热重建；`IsEnabled` 翻转 → 停/启会话。**`DeviceConnection.IsEnabled`/`ReconnectIntervalMs` 目前运行时根本没有消费**（重连退避硬编码 5s：`DeviceScheduler.cs:61`），会话层是让它们首次生效的正确位置 |

## 4. 问题 D（被低估）：吞吐悬崖

Worker 现状是**逐变量一次网络往返**（`DeviceWorker.cs:167`：`await _runtime.Driver.ReadAsync(vr)`），`ReadBatchAsync` 虽在接口中且 `S7Driver` 已实现地址分组批读（`S7Driver.cs:455`），**但 Worker 根本没调用它**。

改造前每设备独享一条连接、各自并行；共享后 N 台设备的全部轮询挤一条连接、一个锁串行。按 5ms RTT 估算，两台各 100 变量 @100ms 周期的设备根本跑不完。因此：

> **「跨设备/设备内合批」不是中远期优化，批读（至少设备内批读）应与连接共享绑定交付**，作为吞吐补偿。草案把它放在「容易出错、建议后置」的位置是误判——S7Driver 的批读已实现且经过地址分组设计，风险主要在 Worker 侧的故障隔离语义适配（见 03 文档 §7）。

## 5. 次要修正

| 项 | 草案表述 | 实际情况与修正 |
|---|---|---|
| 驱动面 | 暗示多协议驱动 | 实际 3 个：S7 / OpcUa / Virtual；Modbus、MQTT 工厂抛 `NotSupportedException`（`ProtocolDriverFactory.cs:63-64`）。改造面更小，VirtualDriver 平凡 |
| 驱动对 `IRuntimeDevice` 的依赖 | 未验证 | 全部使用面仅为 `ConfigJson` + `Key`（S7 日志）/`Id`（Virtual）。`IRuntimeConnection` 只需 `ConnectionId/Key/ConfigJson` 三个成员，签名切换干净 |
| OPC UA 订阅 | 列为顾虑 | `SubscribeAsync/UnsubscribeAsync` 全仓**无运行时调用方**（休眠路径），接口原样保留、零改造 |
| `_reconnecting` 占位 | 改为连接级 key | 保留 per-device 占位不动；会话级重连不再移除设备运行时，该窗口本身趋于消失，P6 评估删除（见 03 文档 §5.4） |
| 地址解析上移 | 阶段 4 要求「地址解析从驱动内上移到设备层」 | 不必要：`RuntimeVariable`（来自 `DataPointMapping`）已持有地址，驱动按 `variable.Address` 解析，链路本就正确。删除该项 |
| 日志契约 | 未提 | 项目硬约束要求通讯错误日志含 Device 字段；共享后驱动日志上下文变为「连接 + 触发设备」，需同步更新约束条目（memory） |

## 6. 关键决策（D1～D12）

| # | 决策 | 理由 |
|---|---|---|
| D1 | **Worker 保持每设备一个，只共享驱动实例** | Worker 内嵌设备级报警/死区/防抖状态机；驱动读写接口本就是变量粒度且并发安全；合并收益为零、风险极高 |
| D2 | 驱动连接签名：`ConnectAsync(IRuntimeDevice)` → `ConnectAsync(IRuntimeConnection)` | 驱动真实依赖面只有 `ConfigJson`+`Key`；连接参数的真相源本来就是 `DeviceConnection`，而非设备 |
| D3 | 会话生命周期：首设备挂载创建、末位离场销毁（引用计数）；中间启停只挂载/卸载 | 消除 C1；保证删除/禁用单设备不影响同连接其他设备 |
| D4 | 重连归口会话：Worker 断线信号上抛 → 会话聚合判定 → `IsAliveAsync` 探测确认 → 闸门去重重建；**设备运行时不随会话重建** | 消除 B 类事故与并发风暴；顺带修复现状 flapping 缺陷；运行时存活=快照/变量值/报警计数不丢 |
| D5 | 重建顺序闸门：取消挂载 Worker → 等待退出 → Dispose 旧驱动 → Connect 新驱动 → 扇出状态 → 调度器自然重派 | 杜绝「Worker 正在用旧驱动时被脚下拆除」（沿用 `DeviceScheduler.StopAsync` 已验证的顺序模式） |
| D6 | 配置热更新：ConfigJson/ReconnectIntervalMs 编辑 → `ReloadConnectionAsync` 会话热重建；`IsEnabled` 翻转 → 停/启会话 | 消除 C3；与已交付的「连接参数可编辑」功能闭环 |
| D7 | `DeviceConnection.IsEnabled` / `ReconnectIntervalMs` 在会话层消费（首次生效） | 这两个字段目前运行时无消费方；会话是它们的正确宿主 |
| D8 | 写入门禁：`WriteVariableAsync` 的 `Driver==null` 检查改为经 `DeviceRuntime.Driver` 转发属性读会话驱动；`ConnectionState` 门禁保留（扇出来源改会话） | 消除 C2；改动最小（`Driver` 改为 `Session?.Driver` 转发属性，Worker/写链路零改动） |
| D9 | 批读绑定交付：P5 启用 `ReadBatchAsync`（设备内批读），失败降级为逐变量读；跨设备合批明确不做（本期） | 消除吞吐悬崖 D；跨设备合批收益递减、风险高，列为后续可选优化 |
| D10 | OPC UA 订阅路径零改造（休眠代码），接口原样保留 | 全仓无调用方；本期不引入订阅语义设计 |
| D11 | 数据库零迁移 | `DeviceConnection` 已具备全部字段；改造纯运行时层 |
| D12 | 日志契约：驱动通讯错误日志上下文 = 连接（Key/IP/参数）+ 触发设备；更新项目 memory 约束 | 遵守既有硬约束（日志含 Device/IP/Address/Operation/Exception） |

***

## 7. 修正后改造量评估

相对草案「阶段 3 最大工作量」的估计，修正后：

- **删除**：Worker 合并、调度上移、地址解析上移、`_reconnecting` 连接级化、双轨兼容开关（遵循项目「避免两份实现漂移」惯例，一刀切）；
- **新增**：会话重连归口（闸门+探测）、配置热重建、批读 Worker 适配、`IsAliveAsync` 探测成员；
- **净改造量约为原草案的一半**，且核心风险（重连语义）从「隐含假设」变为「显式设计」。
