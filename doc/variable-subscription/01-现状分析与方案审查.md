# 01 - 现状分析与方案审查

> 本文档记录变量订阅更新功能的现状代码事实、v1 方案审查发现的问题，以及 v2 方案对每个问题的修订。行号基于编写方案时的代码版本，实现时以实际代码为准。

## 一、现状代码事实

### 1.1 采集主链路（全部为轮询）

| 环节 | 位置 | 说明 |

### 1.2 订阅实现现状（闲置）

- `Server/ScadaServer.Infrastructure/Communication/OpcUaDriver.cs`（约 L421-L588）：完整实现——按 `PollingIntervalMs` 分组建 `Subscription`，`MonitoredItem` 回调驱动更新；

### 1.5 写入路径与回声抑制（已确认自洽，无需改动）

- 绑定写：`VariableBindingEngine` 写前置 `LastBindingWriteValue`（约 L252-L253），回读同值抑制重复广播；
- 用户写：`RuntimeManager.WriteVariableAsync`（约 L822-L941）先行更新 `Value` 且 `IsChanged=false`，订阅回推同值不会重复广播；
- 绑定引擎对 `VariableChangeSource` 只判 `BindingWrite`（约 L182），新增枚举值 `Subscription` 无破坏。

## 二、v1 方案审查发现的问题

### P1（必须修正，不改会导致功能错误）

| # | 问题 | 根因 |
|---|---|---|
| P1-1 | **纯订阅设备断线永远显示在线**：`DeviceWorker` 空转分支无条件置 `Connected`，每 2 秒覆盖会话故障扇出的 Error；且 v1 将看门狗列为可选、与"删除无条件赋值"自相矛盾 | 空转分支的历史 hack 未随连接共享架构（挂载时状态由会话同步）清理 |
| P1-2 | **混合设备误重连**：轮询变量全部失败（如坏地址）连续 3 轮 → `NeedsReconnect` → 调度器 `ReconnectDeviceAsync` 路径 A 无条件 `session.ReconnectAsync()` 整体重建会话——即使订阅数据流完全健康。殃及同连接其他设备 | `anySuccess` 只由轮询产生，订阅流量未计入通讯成功判定 |
| P1-3 | **回调签名与路由设计矛盾**：v1 一边提议回调传 `IRuntimeVariable` 对象，一边要求协调器按 InstanceId 路由到"当前"运行时。重载窗口内旧回调持有的是已替换的死对象，值永远到不了前端 | 订阅回调生命周期长于 VariableRuntime 实例（重载整体替换对象） |
| P1-4 | **订阅失败回退轮询不可实现**：`UpdateMode=Subscription` 持久化于 DB，而 Worker 的 `due` 集合只收集 Polling 变量，"回退"后无人读取这些变量 | v1 未定义回退的落地机制 |

### P2（并发/性能缺口，需随核心阶段一并实现）

| # | 问题 | 说明 |
|---|---|---|
| P2-5 | **通知推送策略退化**：v1 改为"单条 fire-and-forget"，订阅高频回调下每条通知一个并发 IO 任务，SignalR/MQTT 慢时任务堆积 |
| P2-6 | **报警状态并发化未处理**：`_alarmStates`/`_ruleStates` 从"仅 Worker 单线程"变为轮询线程 + 订阅回调线程双写 |
| P2-7 | **卸载时退订的锁范围遗漏**：`UnmountAsync` 持会话锁；若锁内调驱动退订（网络 IO 秒级），阻塞同连接所有设备的挂载/重连。v1 只对重连写了"锁外执行"纪律，漏了卸载 |
| P2-8 | **启动期订阅抖动**：按设备顺序注册，每台挂载触发一次驱动订阅往返；同连接 N 台设备 = N 轮往返 |
| P2-9 | **回调线程纪律未声明**：通知回调运行在 OPC UA 协议栈线程，禁止阻塞、禁止抛异常；运行时侧未写明 |

### P3（细节建议）

| # | 问题 | 修订 |
|---|---|---|
| P3-10 | v1 Step 4.6"订阅后 ReadAsync 拉初值" | 删除：OPC UA 规范中 MonitoredItem 创建时服务端默认推送一次初始值通知 |
| P3-11 | `_monitoredItems.Any(...)` O(n²) 去重 | 改 HashSet 索引（大点表订阅是主战场，必须改） |
| P3-12 | 能力判定未定义机制（AppService 为 Scoped，不能实例化驱动判能力） | 工厂加 `SupportsSubscription(protocolKey)` 纯查询 |
| P3-13 | 订阅按 `PollingIntervalMs` 分组建多条 Subscription，间隔种类多时订阅数膨胀 | 列为后续优化（单 Subscription + 每 item 独立 SamplingInterval）；默认场景无差别 |
| P3-14 | 方案只有集成验证，缺单测 | 补 Processor 等价性单测（阶段三重构的最大回归风险点） |
| P3-15 | 变量级 `ConnectionId` 覆盖列运行时不读 | 校验按设备默认连接，假设记录在案 |

### 审查中确认无需修改的点

- 回声抑制跨轮询/订阅/写入三路径自洽（见 1.5）；
- 报警状态在设备重载时丢失——现状 Worker 重启同样丢失，无回归；
- 驱动 `_lifecycleLock` 不会反向获取会话锁，无死锁环（仅需防"持会话锁做驱动 IO"的阻塞）；
- S7/Virtual 的 no-op 订阅实现与新契约兼容；
- 阶段一/二/三可独立先行落地的判断成立。
