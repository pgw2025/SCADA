# 03 - 详细设计

> 本文档为执行计划（02）的支撑设计，定义关键接口、数据流、生命周期与并发纪律。代码块为**设计示意**（签名与结构为准，命名以实现时实际代码风格对齐）。

## 1. 数据模型

### 1.1 枚举与实体

```
Domain/Enums/UpdateModeEnum.cs
    Polling = 0        // 自主轮询（默认，存量数据语义不变）
    Subscription = 1   // 订阅推送（仅 OPC UA）

DataPointMapping（设备变量实例实体）
    + UpdateMode : UpdateModeEnum  // DB 列 INT NOT NULL DEFAULT 0，无索引
```

字段语义要点：

- **PollingIntervalMs 在两种模式下复用**：轮询模式 = Worker 读取间隔；订阅模式 = OPC UA 服务端采样/发布间隔（驱动的订阅分组键，语义自然衔接，前端文案区分）。
- 存量兼容：新列默认 0（Polling），旧数据无需回填任务。

### 1.2 运行时变量身份

```
IRuntimeVariable
    + InstanceId  : int             // => Instance?.Id ?? 0，即 DataPointMapping.Id
    + UpdateMode  : UpdateModeEnum  // => Instance?.UpdateMode ?? Polling
```

**InstanceId 是订阅体系的唯一身份**（项目约定：变量全局身份 = `DeviceKey + VariableKey`，但该组合在驱动层不可枚举匹配监视项；`DataPointMapping.Id` 数据库自增、跨设备全局唯一、且恰为 `DeviceRuntime.Variables` 字典键，天然适合作为驱动回调路由键）。

## 2. 接口契约

### 2.1 驱动订阅契约（IProtocolDriver）

```csharp
Task SubscribeAsync(IEnumerable<IRuntimeVariable> variables,
                    Action<int, object?, VariableQuality> onValue);
Task UnsubscribeAsync(IEnumerable<IRuntimeVariable> variables);
```

契约要点：

| 约束 | 说明 |
|---|---|
| 回调身份 | 第一个参数 = `IRuntimeVariable.InstanceId`；**驱动不得在回调闭包中持有 `IRuntimeVariable`/`VariableRuntime` 引用**（回调生命周期长于运行时对象——设备重载会整体替换 VariableRuntime 实例） |
| 回调线程 | 协议栈线程：禁止阻塞、禁止抛异常（调用方负责兜底，驱动侧也需保证 SDK 异常不外溢） |
| 失败语义 | SubscribeAsync 失败：**回滚本地新增项后抛异常**；不重试、不降级 |
| 幂等性 | UnsubscribeAsync 对未知 InstanceId 静默忽略；离线时仅做本地清理 |
| 空闲语义 | 驱动未连接时 SubscribeAsync 静默返回（协调器靠下次同步收敛，不视为错误） |

### 2.2 驱动能力查询（IProtocolDriverFactory）

```csharp
bool SupportsSubscription(string driverKey);   // OPCUA→true；S7/VIRTUAL/未知→false
```

纯静态查询、不实例化驱动；AppService（Scoped 生命周期）与前端表单共用同一判定源。

### 2.3 值处理管线（IVariableValueProcessor）

```csharp
public interface IVariableValueProcessor
{
    Task ApplyPolledAsync(DeviceRuntime runtime, VariableRuntime vr, object? rawValue, DateTime now);
    Task ApplySubscribedAsync(DeviceRuntime runtime, VariableRuntime vr, object? value, VariableQuality quality, DateTime now);
    void StopDevice(int deviceId);
}
```

注册为**单例**（全部依赖均已是单例）。两个入口汇入同一核心：

```
核心管线（顺序与现有 DeviceWorker 严格一致）：
  1. 质量判定      Polling: rawValue==null → CommunicationError
                  Subscription: quality==Bad → CommunicationError（丢弃值，保留旧值为僵尸值）
  2. 工程换算      VariableScaling.ToEngineering
  3. 锁内内存更新   runtime.Lock: Value/Quality/UpdateTime/IsChanged/回声抑制
  4. 变化总线      changeBus.Publish(…, source)   // source = Polling / Subscription
  5. 通知入队      通知泵（§5）
  6. 历史存储      TryRecordHistory（死区/变化存储/周期存储）
  7. 实时快照      TryUpdateRealtime
  8. 报警判定      TryCheckAlarm（持 DeviceRuntime._alarmSync，见 §6）
```

设计原则：**管线生命周期独立于 `DeviceWorker`**（订阅回调可能跨 Worker 重启窗口存活），这是管线从 Worker 抽出为进程级单例的根本原因（决策 D2）。

## 3. 订阅协调器（ConnectionSession 内聚）

### 3.1 组成

```csharp
class ConnectionSession
{
    // 注入（构造函数新增）：
    private readonly IVariableValueProcessor _processor;

    // 订阅状态：
    private readonly ConcurrentDictionary<int, (int DeviceId, VariableRuntime Vr)> _subscriptionRoutes;
    private int _syncScheduled;          // Interlocked 去抖标志
    private DateTime _lastSyncFailureUtc;  // 失败退避计算
    private TimeSpan _syncRetryBackoff;    // 初始 30s，翻倍至 5min 封顶

    // 对外：
    public void ScheduleSync();                       // 去抖 100ms，fire-and-forget
    private async Task SyncSubscriptionsAsync();      // 差量同步（锁外执行）
    private void OnSubscriptionValue(int id, object? v, VariableQuality q);  // 驱动回调
}
```

### 3.2 差量同步流程

```
SyncSubscriptionsAsync()
  ├─ if (_disposed) return
  ├─ 期望集 = _mounted.Values
  │      .SelectMany(rt => rt.Variables.Values
  │          .Where(v => v.IsEnabled && v.UpdateMode == Subscription)
  │          .Select(v => (rt.Device.Id, v)))
  ├─ toAdd    = 期望集中 instanceId ∉ _subscriptionRoutes
  ├─ toRemove = _subscriptionRoutes中 instanceId ∉ 期望集
  ├─ toRemove 非空 → await Driver.UnsubscribeAsync(toRemove 的 Vr 快照)
  ├─ toAdd    非空 → await Driver.SubscribeAsync(toAdd, OnSubscriptionValue)   // try-catch → §3.4
  ├─ 更新 _subscriptionRoutes
  └─ catch: 记录失败 → ScheduleSync 退避重试
```

关键点：

- **全程不持会话 `_lifecycleLock`**（驱动 IO 秒级，持锁将阻塞同连接所有设备的挂载/重连/卸载——统一纪律：会话锁内不做任何驱动 IO）。
- 同步期间的挂载/卸载变化不回滚本次结果，由下一次 `ScheduleSync` 收敛（最终一致）。
- 驱动未连接（重建中）时 Subscribe 静默返回：路由表未更新 → 下次同步重试，自愈。

### 3.3 去抖调度

```
ScheduleSync()
  ├─ Interlocked.Exchange(ref _syncScheduled, 1) == 1 → return（已有待执行同步）
  └─ _ = RunDelayedAsync():
        await Task.Delay(100ms)         // 合并窗口：启动批量挂载/级联卸载合并为一次
        Interlocked.Exchange(ref _syncScheduled, 0)
        if (!_disposed) await SyncSubscriptionsAsync()   // 异常内部兜底
```

- 调用方**从不 await**：`ScheduleSync` 永远同步立即返回——保证可在会话锁内安全调用（如 `ReconnectCoreAsync` 收尾），实际同步执行时锁已释放（100ms 窗口 > 任何持锁临界区）。
- 100ms 合并窗口使"服务启动 N 台设备顺序挂载"收敛为个位数次驱动往返（P2-8）。

### 3.4 订阅失败与退避重试

```
catch (ex) during SubscribeAsync:
  ├─ toAdd 变量（锁内）: vr.Quality = CommunicationError   // 前端可见质量降级
  ├─ Warning 日志（连接 Key/Endpoint/变量数/InstanceId 范围/Exception）
  ├─ _syncRetryBackoff = min(_syncRetryBackoff*2 或 30s 起, 5min)
  └─ 延时 _syncRetryBackoff 后 ScheduleSync()（成功一次后复位为 30s）
```

**不回退轮询**（决策 D4）：`UpdateMode=Subscription` 是用户显式配置，隐式降级会造成"看似订阅、实际轮询"的不可预期行为；质量降级 + 前端可见 + 日志可查 + 自动重试是行为可预期的最小闭环。

### 3.5 驱动回调路由（OnSubscriptionValue）

```
OnSubscriptionValue(instanceId, value, quality)
  └─ try（协议栈线程，全程兜底）:
      1. _subscriptionRoutes.TryGetValue(instanceId) → 无: return（已退订）
      2. _mounted.TryGetValue(deviceId) → 无: return（设备已卸载）
      3. runtime.Variables.TryGetValue(instanceId) → 无: return（重载窗口/变量已删）
      4. 通讯打点（§7）: LastCommunicationTime=now; ConsecutiveFailureCount=0;
         ConnectionState==Error → Connected（状态自愈）
      5. _ = _processor.ApplySubscribedAsync(runtime, vr, value, quality, now)
```

三次字典查找完成"回调 → 当前活运行时"的解析，天然吸收所有生命周期竞争（对象已死即静默丢弃，P1-3 修订的核心）。

## 4. 生命周期接线总图

```
事件                          动作                              执行上下文
─────────────────────────────────────────────────────────────────────────────
BuildAndRegisterDeviceAsync   Session.ScheduleSync()            RegisterDevice 之后（Variables 已填充）
  （设备挂载/重载/启动恢复）
UnmountFromSessionAsync       Session.ScheduleSync()            UnmountAsync（锁内）返回之后
  （设备卸载/重载卸载旧运行时）  Processor.StopDevice(deviceId)    RemoveDeviceAsync 内
ReconnectCoreAsync 成功       _subscriptionRoutes.Clear()       会话锁内（纯内存，安全）
  （会话重建换驱动）             Session.ScheduleSync()            实际同步在 100ms 后锁外执行
会话 Dispose                  _disposed=true，待执行同步 no-op    驱动 Dispose 自带订阅清空
变量配置变更(UpdateAsync)     ReloadDeviceAsync → 卸载旧+重建新   走上面挂载/卸载两条路径，无需专设
```

**必须 `Clear()` 路由表的原因**：会话重建后新驱动的订阅集合为空；若路由表保留旧记录，差量同步会误判"已订阅"而漏订全部变量——这是最隐蔽的漏订缺陷，属于 P1 级纪律。

## 5. 通知泵（Processor 内部）

```
ConcurrentDictionary<int deviceId, Channel<VariableNotification>>
  - Bounded(2048, FullMode=DropOldest)
  - 每设备单消费任务：循环 await reader.ReadAsync → NotifyVariableUpdateAsync（try-catch Warning）
  - 丢弃计数：每 100 条记一次 Warning（设备 Key + 累计丢弃数）
  - StopDevice: writer.Complete() → 等待消费任务退出（3s 超时放弃）→ 移除字典项
```

设计动机（决策 D7）：轮询路径原本每轮批量 fire-and-forget 一次；订阅回调逐条到达，若逐条 fire-and-forget，高频变化 × 慢 MQ（网络发布秒级）会产生并发任务堆积。泵将"生产"（回调/轮询线程，非阻塞入队）与"消费"（每设备串行 IO）隔离，且提供背压观测点（丢弃计数）。

轮询路径同样入队（不再自建批量推送任务）：每设备顺序保证、两路径行为统一。

## 6. 报警状态并发化

```
DeviceRuntime
  + private readonly object _alarmSync = new();
  + private readonly Dictionary<…> _alarmStates;    // 自 Worker 迁移
  + private readonly Dictionary<…> _ruleStates;     // 自 Worker 迁移
```

- 访问方：轮询线程（Processor.ApplyPolledAsync）与订阅回调线程（ApplySubscribedAsync）双写。
- 临界区 = `_alarmSync` 保护的字典读写 + 规则求值，**纯内存操作**（通知/落库均 fire-and-forget，禁止临界区内网络 IO）。
- 与 `runtime.Lock` 分离：不扩大既有锁临界区、不产生锁序耦合（`_alarmSync` 无出边，不可能死锁）。
- 重载清零行为与现状（Worker 重启清零）等价，无回归。

## 7. 通讯健康判定（混合设备防误重连）

### 7.1 数据流

```
订阅回调到达 → runtime.LastCommunicationTime = now
              → runtime.ConsecutiveFailureCount = 0        （二级防线）
              → ConnectionState==Error → Connected          （状态自愈）

Worker 轮次收尾（全失败判定前）→ 主防线：
    设备存在启用订阅变量
      && runtime.LastCommunicationTime.HasValue
      && (now - LastCommunicationTime) < 订阅新鲜度阈值
    ⇒ 视为本轮通讯有证据：跳过置 Error / 跳过 ConsecutiveFailureCount++ / 跳过 NeedsReconnect

    订阅新鲜度阈值 = max(30s, 3 × 设备订阅变量最大采样间隔)
```

### 7.2 为什么不用"值陈旧度"判定断线

OPC UA 数据变更订阅只在**值变化**时产生通知（无变化时服务器仅发 keep-alive，不进入回调）。静态值变量数小时无回调完全正常。因此断线检测必须以**驱动状态**（`IsAliveAsync`：内部 `_state == Connected && _session.Connected`）为准，值新鲜度仅用于混合设备的"通讯有证据"判定（此时订阅若真断流，看门狗兜底）。

### 7.3 恢复路径矩阵

| 故障场景 | 检测方 | 恢复动作 | 恢复后订阅 |
|---|---|---|---|
| 短暂断网（KeepAlive 窗口内） | 驱动 KeepAlive | 驱动内 `Session.ReconnectAsync` | SDK 自动转移，无需协调器 |
| 连接死亡（驱动内重连 5 次失败→Disconnected） | Worker 看门狗（纯订阅/空转设备）或轮询读失败链（含轮询变量设备） | `SignalConnectionFailureAsync` → 探测死亡 → `ReconnectCoreAsync` 整体重建 | 新驱动空订阅 → 路由表 Clear + ScheduleSync 全量重订（§4） |
| 设备级故障（连接健康、单设备坏地址） | 主防线拦截（不升级为会话重建） | 无（设备保持在线，变量级报错日志可见） | 不受影响 |
| 订阅建立失败（节点不存在等） | 协调器 catch | 质量降级 + 退避重试（§3.4） | 修复配置后自动恢复 |

## 8. 看门狗设计（Worker 空转分支）

```
Worker 循环，due.Count == 0 时：
  ① 删除原有：_runtime.ConnectionState = Connected      （无条件赋值 → 移除，P1-1）
  ② if (now >= nextWatchdogTime):
        nextWatchdogTime = now.AddSeconds(5)
        driver = _runtime.Driver
        if (driver != null && !await driver.IsAliveAsync())      // 纯内存探测，契约禁止网络 IO
            try { await _runtime.Session.SignalConnectionFailureAsync(deviceId) }
            catch (ex) { Debug 日志 }                             // 会话级重连归口（内部闸门+再探测）
  ③ 休眠至下一到期变量或 2s 上限（现状不变）
```

- `IsAliveAsync` false 的两种含义统一收敛到 `SignalConnectionFailureAsync`：内部先探测（alive → 设备级故障不重建；dead → 闸门去重后会话重建）。多设备并发断线由闸门收敛为一次重建序列。
- 阈值 5s：探测为纯内存检查，开销可忽略；检测延迟（断线→Error）≈ 5~15s，优于"永远在线"。
- 空转设备（无任何启用变量）同样受益：原 hack 删除后状态由会话挂载/扇出同步，看门狗保证死亡可发现。

## 9. 锁序与并发纪律（实现时逐条对照）

| # | 纪律 | 违反后果 |
|---|---|---|
| L1 | 会话 `_lifecycleLock` 临界区内：**禁止任何驱动 IO**（Read/Write/Subscribe/Unsubscribe/Connect） | 同连接所有设备挂载/重连/卸载被秒级阻塞 |
| L2 | `ScheduleSync()` 一律 fire-and-forget，任何调用点不得 await 其完成 | 锁内 await 同步 = L1 违反 + 潜在死锁 |
| L3 | 驱动 `_lifecycleLock` 不反向获取会话锁（现状已满足，新代码保持） | 死锁环 |
| L4 | `OnSubscriptionValue` 协议栈线程：全程 try-catch、无阻塞等待、无网络 IO | 协议栈卡死/崩溃 |
| L5 | `_alarmSync` 临界区纯内存；`runtime.Lock` 临界区纯内存（现状保持） | 锁持有时间不可控 |
| L6 | 订阅失败置质量 `CommunicationError` 需在 `runtime.Lock` 内写 `Value` 相关字段 | 与轮询/其他回调竞争写 |
| L7 | 路由表 `_subscriptionRoutes` 只在同步任务与 Clear 点写入，回调只读 | 回调内写路由 = 协议栈线程竞争 |

## 10. 配置与校验链

```
前端编辑弹窗（updateMode 下拉）
  └→ DataPointMappingAppService.UpdateAsync
        ├→ UpdateMode==Subscription 时校验：
        │     Device → DeviceConnection（设备默认连接）→ Protocol.Key
        │     → _driverFactory.SupportsSubscription(key) == false ⇒ BusinessException
        └→ entity.UpdateMode 持久化 → ReloadDeviceAsync（热生效，无重启）
              ├→ 卸载旧运行时 → Unmount → ScheduleSync（退订旧模式项）+ StopDevice
              └→ 重建挂载 → RegisterDevice → ScheduleSync（订阅新模式项）
```

校验取"设备默认连接"：变量级 `ConnectionId` 覆盖列运行时当前不读（现状），校验与运行时行为保持同一假设（P3-15，已在代码注释与本设计记录；若未来启用变量级连接覆盖，校验与运行时需同步修改）。
