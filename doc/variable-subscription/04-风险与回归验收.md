# 04 - 风险与回归验收

## 一、风险清单与缓解措施

### R1. 阶段三管线重构引入行为回归（发生概率：中 / 影响：高）

**风险**：`VariableValueProcessor` 从 `DeviceWorker` 搬迁值消费管线（换算/回声抑制/历史/报警/通知），任何顺序或条件差异都会影响**全部变量**（不只是订阅变量）。

**缓解**：
- 搬迁遵循"等价移动"纪律：处理顺序、锁边界、fire-and-forget 语义逐行对照（Step 3.1）；
- Step 3.7 等价性单测先行覆盖回声抑制/死区/报警去重/质量降级；
- 阶段三独立落地、独立验证（此阶段不动采集范围，轮询行为应完全不变）；
- 集成验证 V1 显式对比轮询路径改造前后行为。

### R2. 会话重建后订阅漏订（发生概率：中 / 影响：高）

**风险**：会话重建换驱动后，若 `_subscriptionRoutes` 未清空，差量同步误判"已订阅"导致全部漏订；或重订被安排在会话锁内造成阻塞/死锁。

**缓解**：
- 设计 §4 已将 `Clear() + ScheduleSync()` 固化为 `ReconnectCoreAsync` 收尾的强制步骤（Step 4.2），并写入代码注释；
- 锁序纪律 L1/L2 逐条对照（设计 §9）；
- 集成验证 V6（拔网线重建）、V11（服务重启恢复）双重覆盖。

### R3. 共享连接下订阅/轮询/重连三方竞争（发生概率：中 / 影响：中）

**风险**：去抖同步与挂载/卸载/重连并发交错，出现短暂重复订阅或漏订窗口。

**缓解**：
- 协调器设计为最终一致（快照竞争由下次同步收敛，设计 §3.2）；
- 驱动订阅项幂等（重复 InstanceId 去重）+ 退订幂等；
- 验证 V4（热切换 100 次循环）、V10（增删 100 次循环监视项精确回收）。

### R4. 订阅模式断线检测盲区（发生概率：低 / 影响：中）

**风险**：看门狗依赖 `IsAliveAsync`（驱动内存状态）。若驱动内部状态与实际连接不一致（SDK 异常路径），纯订阅设备断线检测延迟增大。

**缓解**：
- `IsAliveAsync` 同时校验 `_state == Connected && _session.Connected`，覆盖驱动内重连放弃路径（Disconnected）；
- 保守评估检测延迟 5~15s 并写入验收预期（V8），不承诺亚秒级；
- 混合设备另有轮询读失败链作为第二检测通道。

### R5. 通知泵丢弃造成数据缺口（发生概率：低 / 影响：低）

**风险**：高频变化 + 下游 IO 慢时，2048 容量 DropOldest 丢通知（前端实时值跳变）。

**缓解**：
- 丢弃计数 Warning 提供观测点；**历史存储走 Influx 直写不经过泵**，历史曲线无缺口，仅实时推送受影响；
- 容量与丢弃阈值可调；长跑验证（Step 7.4）确认 500 变量 × 1Hz 零丢弃。

### R6. 已知残留行为（接受，不修复）

| 现象 | 原因 | 处理 |
|---|---|---|
| 混合设备轮询变量全失败且订阅健康时，设备状态在 Error/Connected 间抖动 | 主防线（Step 4.7）已拦截 Error 置位与重连，仅订阅回调的自愈置 Connected 与轮次失败日志并存 | 状态推送经 RuntimeManager 去重；本质是坏地址配置错误，可见故障呈现可接受（设计 §7.1） |
| 全部轮询变量坏地址的设备周期性触发会话重建 | **现状既有行为**（调度器 `ReconnectDeviceAsync` 路径 A 无条件 `session.ReconnectAsync`，`SignalConnectionFailureAsync` 的 IsAlive 探测结论未反馈到该路径），非本方案引入 | 记录在案，不在本功能范围内修复；如需修复另行立项（在 `ReconnectDeviceAsync` 路径 A 前增加 IsAlive 预检） |
| 旧版前端缓存未提交 `updateMode` 时保存会将 Subscription 重置为 Polling | DTO 缺省值语义 | 前后端同版本部署（既有发布流程），风险极低，DTO 注释记录假设 |

### R7. OPC UA SDK 订阅转移假设（发生概率：低 / 影响：中）

**风险**：驱动内自动重连依赖 SDK 的订阅转移（`Session.ReconnectAsync` 保留 Subscription/MonitoredItem）。特定 SDK 版本或服务器行为不满足时，短断恢复后订阅静默失效。

**缓解**：Step 2.6 固化假设与验证方式；集成验证 V7 显式覆盖；失效兜底为会话级重建路径（V6 已验证）——最坏情况退化为"短暂断网也走整体重订"，功能不丢失。

### R8. 数据库迁移风险（发生概率：低 / 影响：中）

**风险**：`DataPointMappings` 大表加列锁表时间；迁移与代码版本不匹配部署。

**缓解**：单列 `INT NOT NULL DEFAULT 0` 加列（MySQL 8 Instant DDL，秒级）；迁移与代码同包发布（既有流程）；迁移含可回滚 Down。

## 四、发布与回滚

1. **发布顺序**：后端（含迁移）与前端同版本发布；服务重启即完成迁移与订阅恢复（无需手工步骤）。
2. **回滚策略**：代码回滚至上一版本即可——`UpdateMode` 列对旧代码无感知（多余列不影响 EF 读写）；旧版本恢复轮询采集，订阅模式的变量回到轮询（`due` 收集不过滤时全量轮询），数据不中断。
3. **灰度建议**：先在测试连接上启用 1~2 个订阅变量观察（V1~V3、V9），再逐步放量。
