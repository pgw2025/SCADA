# 01 现状分析与方案审查

> 本文记录：当前画面列表的实现现状、上一版方案评审发现的缺陷、以及据此修订后的最终决策。实施细节见 `02-详细设计.md`。

## 1. 现状梳理（已代码核对）

### 1.1 数据模型

- 后端实体 `ScadaPage`（`Server/ScadaServer.Domain/Entities/ScadaPage.cs`）：字段为 `Id/ProjectId/Name/IsHome/Platform/Width/Height/BackgroundJson/AdaptMode/LayersJson` + `[NotMapped] Components`。**无 ParentId / 分组 / 排序字段**。
- 存储：MySQL（Pomelo Provider）+ EF Core，独立表 `ScadaPages`；`ScadaProject.Pages` 是 `[NotMapped]` 导航，工程与页面经 `ProjectId` 关联。
- 唯一分组维度是 `Platform`（Desktop/Mobile/Popup）。

### 1.2 渲染与状态

- 画面列表渲染在 `Client/src/components/ScadaTopologyView.vue`（约 1405–1590 行），按 `Desktop/Mobile/Popup` 三组平铺 `v-for`。
- 分组数据来自 `Client/src/store/scadaStore.ts` 的 `desktopPages/mobilePages/popupPages` 三个 computed（`currentProject.pages` 按 platform filter）。
- 无 Pinia/Vuex，用 `ref`/`computed`；`selectedPageId` 驱动选中，`currentPlatform` 随选中页同步。

### 1.3 持久化编排（关键约束）

- 前端 `scadaService.ts` 采用「实体双轨 id（uid 字符串 ↔ serverId int）+ 父级先落库 + 600ms 防抖 PUT + 失败重试」的成熟模式（`ensurePageSaved` / `persistPageUpdate` / `persistPageDelete` 等）。
- 整树由 `ScadaProjectAppService.GetTreeAsync`（`Server/ScadaServer.Application/Services/ScadaProjectAppService.cs`）一次返回 `ScadaProjectFullDto`（当前仅 `Project` + `Pages`，**无 folders**）。

### 1.4 后端分层与直连点

- 仓储基类 `RepositoryBase<TEntity,TKey>`（含 `Insert/Update/Delete/DeleteRange/GetList`）；空接口定义集中在 `Domain/Interfaces/Repositories/IEntityRepositories.cs`（`IScadaPageRepository : IRepository<ScadaPage,int>` 在第 175 行）。
- 仓储 DI：`WebApi/Extensions/Database.Extensions.cs`（第 66 行 `AddScoped<IScadaPageRepository, ScadaPageRepository>`）。
- 应用服务 DI：`WebApi/Extensions/Application.Extensions.cs`（第 63–64 行注册页面/工程服务）。
- 控制器：`ScadaPageController`（`RequireAdmin` Policy + `IOperationAuditService` 审计）。
- 事务：`IUnitOfWork.ExecuteInTransactionAsync`（MySqlRetryingExecutionStrategy 内执行）。

## 2. 上一版方案评审发现的 P0 缺陷

| # | 缺陷 | 影响 | 修订决策 |
|---|---|---|---|
| P0-1 | **Platform 范围矛盾**：文件夹表 Platform 只写 Desktop/Mobile，树语义又含 Popup | 实现时卡在「第三组做不做」 | **文件夹仅 Desktop/Mobile，Popup 不建文件夹、保持单层** |
| P0-2 | **整树 DTO 与映射缺 folders**：`ScadaProjectFullDto` 无 Folders，前端 `fromProjectFullDto`/`toPageDto`/`fromPageDto` 无 folderId/sortOrder | 字段加载/保存即丢失 | 补全 `Folders` 列表 + 全部映射函数增加 folderId/sortOrder |
| P0-3 | **文件夹双轨 + 落库回填缺失**：只写了 `proj.folders`，无 ensure/persist | 新建文件夹刷新即丢 | 新增文件夹 `ensureFolderSaved`/`persistFolderCreate/Update/Delete` |
| P0-4 | **同父级排序语义未定义**：reorder 用混合 `[{folderId\|pageId}]` 暗示混排 | 拖拽落点判定混乱 | **文件夹与画面两套独立 SortOrder，文件夹段恒在上** |

## 3. 其它需明确/优化的点

| # | 问题 | 修订结论 |
|---|---|---|
| C1 | 存量 `SortOrder` 回填 0 会打乱现有顺序 | 迁移按当前查询顺序（Id 升序）回填递增 SortOrder，保持现状顺序 |
| C2 | 导出 `TransferPageDto` 无 folderId，导入归属丢失 | 迁移文件不含文件夹，**导入画面一律落根级**（`FolderId=null`） |
| C3 | cascade 的「至少一个页面」是全局还是按端 | **沿用现状全局 guard**（`pages.length>1`），前端+后端双保险；不新增按端约束 |
| C4 | 命名唯一性仅前端校验 | 后端在应用服务层校验「同 ProjectId+Platform+ParentFolderId 下重名」返回 400；根级重名因 MySQL 唯一索引对 NULL 放行，**不建库级唯一索引**，仅应用层校验 |
| C5 | 删除文件夹上提子项的排序键未写死 | 定稿：子项按原 SortOrder 升序、整体追加到目标父级「文件夹段/画面段」末尾 |
| C6 | reparent 上提后父级排序冲突 | 删除后对目标父级做一次 `RenormalizeOrder`（按段分别从 1 连续重排） |

## 4. 修订后的最终决策

- **数据模型**：新增 `ScadaPageFolders` 表（自引用支持嵌套）+ `ScadaPages` 增 `FolderId(int?)`、`SortOrder(int)`。
- **适用范围**：文件夹仅 `Desktop`/`Mobile`；`Popup` 维持现状单层。
- **删除**：`DELETE /api/ScadaPageFolder/{id}?mode=reparent|cascade`，默认 reparent（内容上提），cascade 可选（连同画面/子文件夹删除，不可恢复）。
- **排序**：同父级下「文件夹段」与「画面段」各自独立 SortOrder，UI 文件夹段固定在前；`reorder` 端点按段全量覆盖。
- **前端**：手写递归树 + 原生 HTML5 DnD；文件夹 uid/serverId 双轨；`folderId`/`parentFolderId` 前端存 uid（对齐 `layerId` 字符串 uid 惯例），后端存 int FK，映射函数负责转换。
- **兼容**：存量画面落根级，首页唯一性、Platform 过滤、组件绑定、剪贴板、导入导出均不感知文件夹。
